## 2026-09-11 · Ревью старого кода шестью агентами и фиксы: 149 находок, 4 критичных

**Сделал.** По вопросу владельца «весь код прошёл насквозь?» — честный ответ был «нет»: вторым агентом читались

каталог и кабинет (27), каркас и безопасность (15). Итог: 149 находок, 4 критичных, ≈40 высоких; три домена
независимо нашли одну и ту же утечку сумм помощнику. Затем контракт v0.28.0 одним пакетом (до фиксеров, чтобы все
правили под сгенерированные типы) и шесть фиксеров по непересекающимся файлам — каждая находка с тестом, красным
без фикса; свод регулярки uuid (32 копии → `isUuid`), коды ответов в контракте, адаптация девяти старых тестов,
сертифицировавших дефекты, — моё. Живая проверка после зелёных прогонов нашла ещё два дефекта, оба мои: выход
висел на `serviceWorker.ready` без регистрации (ERR-0232) и 409 на гашение своей сессии оставлял её живой после
«выхода» (ERR-0233) — решение по Д1-19 отменено. Коммиты: `8cf90ef`/`8c89f46` (контракт), `1624d17`
(код, 91 файл), `27e8164` (после живой проверки), записи — отдельно. Прогоны: бэкенд 65 · 748 | 10, фронт 38 · 579,
tsc/eslint 0, сборка чистая. ERRORS: ERR-0219…ERR-0240 (R-230…R-236).

**Почему так.** (1) Ревью и фиксы — разные агенты: ревьюер без права правки не «дочинивает» под свою гипотезу,
фиксер получает решение по каждой находке от оркестратора, а не выбирает сам (правило 11 FIX-RULES). (2) Файлы
между фиксерами не пересекаются — шесть параллельных правок одного файла невозможно свести; всё, что легло на стык
(`slots.ts` для Д4-01, строки в `jobs/index.ts`, `stage5`), сделал сам после их завершения. (3) Миграции — ни одной:
стоп-условие владельца; там, где честное решение только миграцией (чат по сделке, счётчик автобуса по персонам,
ключ отзыва гостя по `guests.id`, `deals.package_id`), сделан обход в обработчике и записан хвост. (4) Контракт
правился до фиксов и один раз после (коды ответов) — генераторы в тех же коммитах. (5) Живая проверка после
агентов обязательна (R-234/R-235): зелёные тесты каждой стороны порознь не доказали ни поток выхода, ни отсутствие
service worker.

**Альтернативы.** (1) Один большой агент на весь старый код — отклонено: контекст не вместит 18 000 строк, а
ревью фич 001 показало, что 20 находок на 1 000 строк — норма. (2) Чинить в том же агенте, что нашёл, — отклонено
(см. «почему так», п. 1). (3) Миграции «раз уж нашли» — отклонено: стоп-условие, и без владельца схему не трогаю.
(4) Оставить 409 на гашение своей сессии и добавить `POST /auth/logout` — отклонено: это правка контракта ради
кнопки, которая и так работала; вернул прежнее поведение.

**Владельцу** (`tasks/todo.md`, хвосты ревью): четыре миграции, повторный вход мягко удалённого (восстановление или
отказ до SMS), лимиты OTP по номеру+IP, порог рейтинга по отзывам пар, `myHotelId`/`tz`/`comment`/системный признак
сообщения в контракте, правка и удаление столов, напоминание гостям только паре, телефон гостя только паре,
словарь ухода с платформы, воронка кабинета по периодам, поле `blocked` в анкете, «ожидается» по `done`.

с допущениями вместо вопросов, планы с воротами, задачи; сверка всех трёх одним независимым агентом — четыре

отмены с другого устройства все экраны отвечали «не найдено» без выхода); отмена не трогает выполненные сделки;
уборка удаляет отменённые свадьбы старше `WEDDING_ARCHIVE_DAYS` (365, не меньше 30, партия 100) со следом в
журнале. **004:** версия справочника — отпечаток содержимого; сохранение поверх чужой правки — 409 и
«Перечитать». Контракт: 119 путей / 157 операций / 55 схем. Попутно: `sw.js` кэшировал ответы API (ERR-0204),
журнал сделки при отмене свадьбы писал новое состояние вместо исходного (ERR-0206), один русский ключ словаря
на два смысла (ERR-0207), кэш даты переживал отмену свадьбы — главная считала дни до свадьбы, которой нет; нашла
живая проверка (ERR-0208). Живьём проверено всё: заявка подтверждена и отклонена с уведомлениями, подрядчики

колонка `updated_at`: без миграции (стоп-условие) и с видимостью правок мимо панели. Уборка архива —
единственное необратимое действие ночи: только отменённые свадьбы, срок из настройки с нижней границей, партия,
строка журнала на каждую — и включена она решением владельца выбрать эту фичу (RELEASE-BLOCKERS №10).
Экран отмены — состояние `/settings`, не новый маршрут: экран 45 плана.

**Альтернативы.** (1) Spec Kit как есть (`.specify/`) — владелец выбрал свой цикл, решение 04.09 подтверждено.
(2) Одна очередь на анкеты и заявки — отклонено: заявка живёт дольше анкеты в модерации, а отклонить документы,
не снимая анкету, было нечем. (3) Причина отмены свадьбы — у пути нет тела; расширять контракт и продукт без
владельца не стал. (4) Синхронное уведомление подрядчикам при отмене свадьбы — дубль с рассылкой событий
сделок; оставлено ей (работает при Redis, №2).

**Ревью утром 08.09** (второй агент, только код): 14 находок, 1 критичная — уборка архива падала на первой же
свадьбе с отзывом пары (`reviews.deal_id SET NULL` против `CHECK`) и переставала работать навсегда; 2 высоких —
версия справочника читалась не из того снимка, что данные; тест уборки без отзыва в фикстуре. Всё закрыто кодом

## 2026-09-07 · Админка: пять экранов Плана §19.10 за одну сессию, по циклу спеки

**Сделал.** Фича 001 (`tasks/фичи/001-админка/`): спека без техники с допущениями A1–A12 вместо вопросов

Три коммита: `814bd77` (контракт, признак сотрудника, `GET /admin/categories`, каркас), `a57b575` (экраны и
сервер), этот (документы). Тесты: бэкенд 596 → 608, фронт 371 → 390, каждый дефект доказан красным без фикса.
Живая проверка сотрудником (`+79972874000`, `is_staff` включён в базе): снятие анкеты с причиной, блокировка по
жалобе с заметкой, словарь синонимов («фотосессия» → поиск находит фотографов), карточка свадьбы по причине —
каждое действие оставило строку `audit_log` с актором, уведомления подрядчикам ушли без заметки модератора,
дашборд после двух решений сдвинулся ровно на единицу по трём показателям. Тёмная тема — четыре экрана глазами.

фазы 1 их файлы не пересекаются. Проверка — другими методами и другими руками: сверка спеки третьим агентом,
прогоны и diff — сам, живьём — сам. Кнопка «Открыть карточку» шлёт запрос из обработчика, а не через состояние и
`useApi`: инвентарь карт честно назвал бы её «только экран», а R-176 требует, чтобы кнопка делала написанное сама.
Санкции по жалобе уведомляют подрядчика, неприменимые к цели отвергаются 422: иначе «Предупредить» — кнопка без
адресата, а «Заблокировать» сообщение — ложь на кнопке.

**Альтернативы.** (1) Узнавать права пробным запросом в панель и чтением 403 — отклонено: код `forbidden` общий
с «нет согласия», меню ходило бы в админку при каждом открытии. (2) Экран категорий без словаря — отклонено:
`PUT` заменяет словарь целиком, экран без чтения стирал бы строки, которых никто не видел; вместо этого метод
`GET` у того же пути. (3) `CHECK` на `complaints.resolution` по цели — отложено: миграция под стоп-условием
сессии, правило живёт в обработчике, строка владельцу. (4) Привести План приложения к факту (ч. 12.1, список 67
экранов) — не делал: какие из тринадцати недостающих экранов вычеркнуть — решение владельца, не документа.
(5) Свои определения агентов (`.claude/agents/tili-implementer.md`, `tili-reviewer.md`, `model: opus`,
`effort: max`) написаны, но в текущей сессии не подхватываются — заработают со следующей; здесь их роль сыграли
`general-purpose` с моделью Opus и тем же текстом правил.

**Связанные ошибки.** ERR-0195…ERR-0199 (R-207…R-211): признак в базе без пути наружу; замена целиком без чтения
и `object` без свойств в контракте; санкция без адресата и действие без действия; ручная копия схемы тела

## 2026-09-05 · Восемь решений владельца — и что из них вышло кодом

**Сделал.** Опрос по накопившимся решениям (все ответы — в `tasks/todo.md`), затем
семь из них закрыты кодом: сумма платежей в сделке, журнал сделки, резерв 10% в бюджете,
массовое напоминание гостям — на сервере и на экранах.

**Почему так.**

- **Категорий не 25, а 35 — и так было.** Прежде чем менять справочник, я его посчитал:
  в `categories.json`, в базе и в моке фронта уже 35. Расхождение жило только в двух
  документах. Работа свелась к правке бумаг вместо миграции, которой боялись полгода.
- **Оплаченное считает сервер.** Сохранённая в сделке сумма разошлась бы с платежами на
  первом же возврате — та же ошибка, что уже случилась во фронте с «потрачено» (ERR-0012).
- **Журнал открыт обеим сторонам.** Он существует ради спора, а в споре две стороны.
  Автор события назван ролью: чужой идентификатор наружу не уходит.
- **Резерв — строка, а не категория.** Категории делят сто процентов между собой; резерв
  внутри них означал бы, что часть сметы просто уменьшили.
- **Массовое напоминание не трогает тех, кто ссылку уже открыл.** Перевыпуск гасит токен
  гостя и уводит за собой всё, что он выбрал, — резерв подарка в том числе. Это единственная
  причина, по которой рассылка неполная, и сервер называет её отдельным числом, а не прячет.

**Альтернативы.**

1. *Считать оплаченное на клиенте по списку платежей* — отклонено: второй расчёт тех же
   денег разойдётся с серверным, вопрос только когда.
2. *Резерв как шестая категория с долей 10%* — отклонено: пришлось бы пересчитать доли
   остальных пяти, то есть молча изменить план бюджета у всех пар.
3. *Массово перевыпускать ссылки всем молчунам* — отклонено, см. выше: тихая потеря
   гостевых резервов, о которой никто не узнает.
4. *Отдавать журнал только паре* — отклонено: подрядчику он нужен ровно там же.

**Связанные ошибки.** Новых нет. Правило R-160 из перепроверки этапа 8 применено сразу:
всё, что сервер начал отдавать, в тот же день показано на экране.

## 2026-09-05 · Перепроверка этапа 8: отзыв, который никто не читал

  соседних экранах.

   там, где мы «просто украшали».
2. *Показывать форму отзыва всегда, а отказ объяснять после отправки* — отклонено: правило
   известно заранее, и сказать его до заполнения дешевле, чем после.
3. *Не трогать `/after`, он числится за этапом 6* — отклонено: отзыв гостя — это этап 8, а

4. *Оставить кнопку ZIP-архива до появления хранилища* — отклонено: она сообщала «ссылка
   отправлена», хотя письма не было (R-161).

(2) Вынести цикл глобальным скиллом на все проекты — отклонено на этом шаге: правила пришлось бы писать общими, без привязки к `openapi.yaml`, инвариантам и R-MAP/R-BTN, а именно привязка и составляет половину пользы. (3) Ограничиться спекой и задачами, без вопросов и сверки — отклонено: дыру «требование без задачи» тогда не ловит никто, а это самая дорогая из тех, что цикл вообще способен поймать. (4) Влить правила прямо в `CLAUDE.md` — отклонено: он грузится в каждую сессию, а цикл нужен в одной из пяти. Ушло отдельным документом с одной строкой-указателем, как и остальные источники правды.

(5) Сверка перед реализацией, read-only, с таблицей покрытия «требование → задачи» и уровнями КРИТИЧНО/ВЫСОКИЙ/СРЕДНИЙ/НИЗКИЙ — единственный шаг, который ловит требование, под которое никто не завёл задачу.

**Ворота инвариантов вместо конституции.** Spec Kit проверяет план против `constitution.md`, которую сам же и создаёт пустой. Здесь эта роль отдана `CLAUDE.md` §5 (12 инвариантов) и R-01…R-15: нарушение либо получает написанное обоснование в таблице плана, либо план переделывается. Смягчать и переосмысливать инвариант внутри фичи нельзя — устарел сам инвариант, это отдельный разговор с владельцем и запись сюда (R-15).

**Идентификаторы латиницей** (`US1`, `FR-001`, `T001`) при русском тексте вокруг. Кириллические `Т`, `Р`, `С`, `А`, `Е` неотличимы от латинских на глаз, и `grep` по такому ID однажды молча вернёт пустоту.

**Альтернативы.** (1) Поставить spec-kit в проект и жить с двумя источниками правды — отклонено по причине выше. (2) Вынести цикл глобальным скиллом на все проекты — отклонено на этом шаге: правила пришлось бы писать общими, без привязки к `openapi.yaml`, инвариантам и R-MAP/R-BTN, а именно привязка и составляет половину пользы. Вернуться к этому после обкатки на первой фиче. (3) Ограничиться спекой и задачами, без вопросов и сверки — отклонено: дыру «требование без задачи» тогда не ловит никто, а это самая дорогая из тех, что цикл вообще способен поймать. (4) Влить правила прямо в `CLAUDE.md` — отклонено: он грузится в каждую сессию, а цикл нужен в одной из пяти. Ушло отдельным документом с одной строкой-указателем, как и остальные источники правды.

**Не проверено на деле.** Цикл пока не прогнан ни на одной фиче. Первая — админка (5 экранов, План §19.10): бэкенд под неё готов, фронт не начат.

## 2026-09-04 · Этап 6: действия пользователя уходят на сервер

**Сделал.** Бронь, отмена, оплата, переходы сделки, чек-лист, гости, бюджет,
столы, тайминг и дата свадьбы перестали быть состоянием одного браузера.
Каждое действие уходит на сервер, и список после него перечитывается ответом,
а не подкручивается на месте.

**Почему перечитываем, а не правим у себя.** Соблазн велик: обновить свою
копию быстрее и выглядит отзывчивее. Но `tileState` слота, `spent` бюджета и
сроки задач считает сервер, и повторить эти правила на клиенте значит завести
второй набор, который разойдётся с первым на первом же непредусмотренном
переходе. Разойдётся молча: экран будет показывать правдоподобное число.
Исключение оставлено ровно одно — сердечко избранного, где цена ошибки нулевая,
а задержка заметна.

**Ошибку не глотаем.** Действия этого этапа необратимы на той стороне: бронь
занимает дату в чужом календаре, оплата фиксирует деньги. Поэтому галочка
успеха ставится только после ответа сервера, а отказ показывается словами.
До этого `setAdded(true)` стоял в обработчике безусловно — экран рапортовал об
успехе даже тогда, когда бронировать было нечего.

**Что оказалось выдумкой.** Этап начинался как «подключить кнопки», а
превратился в вычистку обещаний, которых система не выполняет:

- график платежей «50% сейчас, 50% за неделю до даты» с вечной отметкой
  «✓ Оплачен» — считался на клиенте, ни одна сумма не была связана со сделкой;
- «Эскроу: деньги заморожены на платформе» — эквайринга в MVP нет (План §3.2),
  деньги идут между парой и подрядчиком напрямую;
- «Автоматически уйдёт кейтерингу и площадке 1 июня» — такой рассылки нет;
- «Автоплан готов: конфликтов нет» — стояло в разметке всегда;
- значок горячего у гостя выдавался хешем от его имени и подписывался
  «из опроса меню»;
- «8 гостей не ответили» считало до восьми независимо от списка.

Каждое из этих мест выглядело работающим и не падало ни в одном тесте. Общего
у них одно: число или факт брались не оттуда, откуда человек ожидает.

**Три ошибки нашлись не в коде экрана, а под ним.** Шаблонный тайминг
записывался по UTC (ERR-0123) — и, что важнее, эта ошибка была зеркальна
ошибке чтения (ERR-0122): пока стояли обе, время выглядело верным, и починка
одной обнажила вторую. Первая простановка даты не заводила сроки, а пыталась
их сдвинуть (ERR-0124) — у пары, ответившей в квизе «дату пока не знаем»,
чек-лист навсегда оставался без дедлайнов. И `Task.due` сервер считал, но не
отдавал (ERR-0125): я принял отсутствие поля в контракте за отсутствие данных
и написал это в комментарии к экрану.

**Утечка доступа под видом синонима.** «Удалить своего подрядчика» вызывало
общую отмену сделки. На экране результат тот же — плитка пустеет. Разница
невидима: удаление гасит выданную подрядчику ссылку-приглашение, отмена нет, и
человек, которого убрали из свадьбы, продолжал видеть её дату, тайминг и чат
(ERR-0126). Отсюда правило R-144: два пути с одинаковым видимым результатом
сравниваются по обработчикам, а не по названиям.

**Что решил не делать.** (1) Не стал добавлять в контракт «сколько уже
оплачено по сделке» — поле нужно, но это решение владельца, а не побочный
эффект этапа; экран показывает факт оплаты, а не выдуманный остаток.
(2) Не стал рисовать резерв «непредвиденное» 10% (План ч. 283) на клиенте:
по плану это категория бюджета, которую заводит сервер, и посчитать её в
браузере значит показать деньги, которых никто не отложил. (3) Не стал
трогать мок-контент профиля пары и приглашений — это этапы 7 и 11, и смешивать
их с записями означало бы коммит, который нечем проверить.

**Альтернатива, которую отклонил.** Оптимистичный интерфейс с откатом при
ошибке — быстрее на глаз и стандартен для списков. Отклонён для всего, что
касается денег и чужого календаря: откат после успешной галочки человек читает
как сбой приложения, а не как «бронь не прошла», и звонит подрядчику, будучи
уверенным, что дата за ним.

**Проверено.** Каждое действие прогнано в браузере и подтверждено запросом в
базу, а не только тестом. Это дало половину находок этапа: тесты были зелёными
и там, где бронь не уезжала вовсе.

**Сделал.** Этап 2 плана миграции: `/auth` ходит в `POST /auth/otp` и `/auth/otp/verify`, согласие на ПДн уезжает на сервер, выход гасит сессии, удаление аккаунта идёт запросом.

## 2026-09-04 · Фронт впервые сходил в бэкенд

**Сделал.** Этапы 0 и 1 плана миграции (`MIGRATION-PLAN.md`). Поднял тестовое окружение и написал слой запросов `app/src/lib/api/`.

То есть подтверждена была маршрутизация, но не бизнес-логика. Начинать миграцию на такой опоре — значит списывать каждую будущую ошибку на свой новый код, не зная, работает ли старый. **Docker отклонён не по вкусу, а по факту.** Движок не поднимался: сокет `dockerInference` ломался в момент создания, файл нельзя было ни удалить, ни открыть. **Почему слой запросов один и типизированный.** Пути и тела берутся из `openapi.yaml` через сгенерированный `schema.ts`: опечатка в адресе становится ошибкой сборки, а не 404 в проде. Ошибки сети, таймаута и приложения приходят экранам в одном виде — экрану незачем знать, отвалился ли fetch или пришёл 500.

**Обмен refresh — одним промисом на все параллельные запросы.** Контракт говорит: refresh одноразовый, повторное предъявление гасит все сессии пользователя. Без сведения обменов десять запросов после протухшего токена дают десять обменов, девять из которых сервер обязан счесть кражей. Это не оптимизация, а условие корректности.

**`/health` внесён в контракт — смена решения.** В `routes/health.ts` стоял комментарий «В контракте этих путей нет — они не часть продукта, а эксплуатация». Теперь фронт зовёт `/health`, чтобы отличить «нет сети» от «сервер лежит»: при живом Wi-Fi и упавшем бэкенде `navigator.onLine` говорит «онлайн», и приложение молча показывает пустые экраны.

**Отклонённая альтернатива.** Можно было оставить health вне контракта и ходить в него мимо типизированного слоя. Не стал: тогда во фронте появляется второй способ делать запросы, и первое исключение из правила «сеть только через `api/`» открывает дорогу остальным. Цена решения — два пути в контракте, которые не являются продуктом; она меньше.

**Прокси, а не прямой адрес.** Запросы идут на `/api` и уезжают прокси Vite на 3001. В разработке нет преграды CORS, в проде адрес задаётся `VITE_API_URL`, и код запросов не меняется. Порт 3001, а не 3000: 3000 занят самим сервером разработки.

## 2026-09-04 · Конец сплошного прохода по бэкенду

Дочитаны последние девять файлов маршрутов. Итог всего прохода: 13 находок, все закрыты. Здесь — про четыре последние и про то, чем закончился метод.

**Я повторил ошибку, о которой сам написал правило.** ERR-0099 — рассылка текста сообщения помощнику — была закрыта в `chats.ts`. Вторая такая же рассылка живёт в `slots.ts`, и я её не искал: исправил место вызова, а не класс. Свод по `kind: 'chat'` занял одну команду и нашёл оба места сразу — я сделал его только сейчас, на финальном проходе. R-113 требовал сплошного свода для чужого кода; R-120 распространяет его на собственные фиксы: вопрос «сколько всего таких мест» задаётся ДО фикса.

Это второй раз за сессию, когда свод оказался у́же дефекта: сначала он искал только адреса и пропустил тела (ERR-0104), теперь — только один файл. Оба раза причина одна: я останавливался, найдя достаточно, вместо того чтобы очертить границу класса.

**Три находки — про то, что действие не доведено до конца.** Ответ подрядчика из кабинета лидов писал в чат, но никого не звал (ERR-0107). Отзыв согласия отзывал согласие, но мог не удалить аккаунт (ERR-0108). Сохранение анкеты удаляло пакеты, но могло не вставить новые (ERR-0109). Разные места, одна форма: половина действия выполнена, вторая может не выполниться, и промежуточного состояния в продукте не предусмотрено.

Отсюда R-121 и R-122. Второе банально — «многошаговое изменение это транзакция», — но признак в нём небанальный: шаги связаны, если откат любого из них в одиночку оставляет систему в состоянии, которого не бывает в норме. По этому признаку `PATCH /users/me` транзакции не требует, а отзыв согласия требует, хотя запросов там столько же.

**Чем закончился метод.** Здесь у меня сначала стояло «все находки пришли со сплошного чтения, ни одна — с поиска по шаблону». Это неправда, и я её поправил разбором по ходу работы (ERR-0111): минимум три находки нашлись именно грепом — `Math.random` в коде приглашения, сырой `localStorage`, единственное `date_trunc('day')` во всём бэкенде.

Верное деление другое:

- **Греп находит присутствие плохого образца** — 3 находки. Образец либо есть в файле, либо нет, запрос формулируется за секунду.
- **Структурный перебор** — 4 находки. Не «найди строку», а «перечисли все элементы множества и проверь каждый»: все параметры маршрутов, все поля тела. Греп здесь инструмент перечисления, а не поиска.
- **Сплошное чтение** — 12 находок. Ловит отсутствие: нет условия по свадьбе, нет транзакции, нет уведомления.

Отсутствие грепом действительно не ищется — но это половина утверждения, а не всё. `ERR-0105` показывает почему: греп по `where id = $1` даёт сотни законных попаданий, а дефектом строку делает то, что тремя строками выше стоит `delete … where wedding_id = $1`. Сигнал — несимметричность с соседом, и она не выражается текстовым запросом.

Практический вывод: заводя аудит, сначала ответь, ищешь ты присутствие или отсутствие. Ошибка выбора дорога в обе стороны — читать подряд ради `Math.random` значит потерять день, грепать ради пропущенной транзакции значит получить ложное «проверил».

Второй по силе источник — комментарии. Пять находок из тринадцати это расхождение кода с комментарием, который стоит прямо над ним. В этом проекте комментарии описывают намерение, а не пересказывают код, — и потому проверяемы. R-114 про это.

**Чего не сделал.** Условие по свадьбе в опросе меню (ERR-0105) и лимит холодных обращений (ERR-0100) тестами не закрыты: нужны две свадьбы в живой базе. Это известный пробел, а не забытый — записан в обеих находках.

**Связанные ошибки.** ERR-0106 … ERR-0109, ERR-0099 (первое место той же утечки), ERR-0104 (первый узкий свод).

## 2026-09-04 · `day.ts` и разбор собственного свода

Самый большой файл маршрутов (895 строк) дал две находки, и вторая вскрыла ошибку в моём же методе.

**Свод искал не там.** В ERR-0098 я вывел правило: дефект, встреченный второй раз, чинится сплошным сводом. Свод сделал — по параметрам АДРЕСА. Идентификатор приходит ещё и полем ТЕЛА, и там всё то же самое: семь мест, где строка уходит в колонку `uuid` без проверки. Правило сработало наполовину, потому что я взял один вход из трёх.

Хуже того, свод был технически неполным: регулярное выражение якорилось на начало строки и не видело поля, объявленные в одну строку. И название общего шаблона — `UUID_PARAM` — закрепляло ту же слепоту: оно называет один вход из трёх. Переименовал в `UUID_ID`; имя без слова PARAM теперь стоит в коде с объяснением, почему.

Отсюда R-118. Он не отменяет R-113, а чинит его: свод по одному входу — половина свода.

**Соседняя правильная строка усыпляет.** `PUT /menu-poll` обновлял блюда без условия по свадьбе, хотя удаление строкой выше ограничено ею явно. Глаз читает «здесь про свадьбу» и переносит это на следующий запрос. Все остальные записи в файле ограничены свадьбой без исключения — выпала ровно та ветка, рядом с которой стояло правильное условие. R-119 про это.

Достижимость честно ограничена: идентификаторы блюд — `uuidv7`, не угадываются. Получить чужой можно, состоя в той свадьбе, — то есть это про координатора, ведущего несколько свадеб, а не про случайного посетителя. Записал это в находку прямым текстом, чтобы severity не выглядела больше, чем она есть.

**Про метод.** Оба раза дефект нашёлся не поиском по шаблону, а сплошным чтением подряд. Поиск нашёл бы `where id = $1` — и утонул бы в сотнях законных совпадений; отличить законное от незаконного можно только зная, что рядом стоит `wedding_id`, а здесь нет. Это довод в пользу того, что сплошной проход по коду стоит своего времени, а не заменяется грепом.

**Связанные ошибки.** ERR-0104, ERR-0105, ERR-0098 и R-113 (свод, который сработал наполовину).

## 2026-09-04 · Два решения владельца по итогам аудита

Аудит упёрся в два вопроса, которые кодом не решаются: где проходит граница роли и что доложить в контракт. Оба вынесены владельцу, оба решены.

**Сдвиг тайминга дня X закрыт до пары и координатора.** Матрица ловила его общим правилом по префиксу `timeline` и отдавала всей команде, хотя соседний план Б закрыт до `DAY_COMMAND` с прямым объяснением: «активация рассылает уведомление всем и переписывает планы на день». Сдвиг делает ровно это — двигает все не начавшиеся блоки, пишет в журнал рассылок и шлёт КРИТИЧЕСКОЕ уведомление гостям и подрядчикам, то есть мимо тихих часов.

Сам я это не чинил и правильно сделал: доводы были с обеих сторон. Помощник на площадке первым видит опоздание — это довод за доступ. Промах по кнопке в час ночи будит полторы сотни человек и отменяется ничем — это довод против, и он тяжелее, потому что запрет обратим, а разосланный push нет. Владелец выбрал запрет. Обычная правка расписания (`PUT /timeline`) осталась всей команде — иначе помощник перестал бы вести тайминг вообще, и лечение вышло бы хуже болезни.

**Состояние запроса на отмену доложено в контракт.** `cancelRequestedBy` и `cancelRequestedAt` в схеме `Wedding`, видны только паре. Это то самое, чего не хватало в ERR-0101: срок годности снял необратимость, но второй партнёр всё равно подтверждал вслепую — показать «первый уже запросил» фронту было нечем. Протухший запрос отдаётся пустым: отдавать состояние, которое не действует, значит предупреждать о том, чего нет.

Отзыв запроса владелец отложил: передумавший ждёт 72 часа. Согласен — это удобство, а не безопасность, и новый путь в контракте ради него сейчас не окупается.

**Что из этого следует для метода.** Оба вопроса выглядели как дефекты и дефектами не были: в первом не хватало решения о границе роли, во втором — поля в контракте. Разница между «код не делает того, что обещает» и «продукт не решил, что обещать» — не формальность: во втором случае молчаливая правка выдаёт мнение агента за решение владельца. R-15 в проекте написан именно про это, и здесь он сработал.

## 2026-09-04 · Сплошной проход по бэкенду: четыре находки в ядре и чатах

Владелец попросил пройти весь код по порядку. Прошёл ядро, доменные модули, фоновые задачи и девять файлов маршрутов — 35 файлов. Четыре находки, все закрыты: утечка переписки в уведомлении (ERR-0099), лимит холодных обращений, бьющий по ответам клиентам (ERR-0100), вечный запрос на отмену свадьбы (ERR-0101), сутки лимита push по UTC вместо часов пользователя (ERR-0102).

**Три из четырёх — расхождение кода с комментарием, который стоит прямо над ним.** «Получатели — те же, кто видит чат» — а получатели все подряд. «Ответ в уже начатой переписке ограничения не знает» — а знает. Колонка `cancel_requested_at` заведена под срок годности — и не читается. Это меняет способ читать код: комментарий рядом с логикой надо проверять как утверждение, а не считать пояснением. Отсюда R-114.

**Один и тот же класс всплыл в третий раз.** ERR-0099 — снова список, дублирующий источник правды, после `redact.ts` (ERR-0097) и схем `params` (ERR-0098). Правило R-112 уже написано, и здесь оно просто применилось: рассылка спрашивает роли у `rolesSeeing`, выведенной из той же `VISIBLE`, по которой работает доступ. Новых правил на этот случай не заводил — их и так становится многовато.

**Границы суток посчитал в приложении, а не в SQL.** Соблазн был написать `at time zone $3` — короче и очевиднее. Отклонено: имя зоны проверяется по ICU (`knownTimeZone`), а списки зон ICU и PostgreSQL совпадают не обязательно. Расхождение уронило бы весь путь уведомления ради экономии десяти строк. `localDayBounds` переиспользует `toLocal`/`fromLocal`, то есть тот же код, что уже сторожат тесты тихих часов.

**Проверил, что не сломал живой тест, который не могу запустить.** `audit7` утверждает «не больше трёх push в сутки», группируя по `date_trunc('day')` — то есть по UTC, а я перевёл лимит на местные сутки. Разошлись бы они, если бы уведомления одной пачки лежали в разные моменты; они лежат в одном, поэтому обе раскладки дают одинаковые группы. Это рассуждение, а не запуск: живые наборы требуют `TEST_DATABASE_URL`.

**Альтернативы.** (1) Срок годности запроса на отмену сделать настраиваемым — отклонено: ещё одна переменная окружения ради значения, которое совпадает с уже существующим сроком мягкой брони. (2) Добавить путь отзыва запроса и отдать состояние в карточке свадьбы — не сделано намеренно: это новые поля и путь в контракте, то есть решение владельца (инвариант 9, R-15). Срок годности снимает необратимость, но не заменяет их. (3) Считать лимит холодных обращений по таблице лидов вместо первых сообщений — отклонено: лид заводится и при броне из каталога, к переписке отношения не имеет.

**Что осталось непокрытым тестом.** Лимит холодных обращений живёт целиком в SQL, и проверить его без живой базы нечем. Вынести в чистую функцию не получилось бы без переписывания запроса в код — это дороже, чем польза. Пробел известный, записан в ERR-0100.

**Пятая находка пришла из чтения соседних файлов подряд, а не из поиска.** Список гостей отдавал всей команде одноразовые ссылки всех гостей (ERR-0103), хотя выдача таких ссылок закрыта для помощника отдельным правилом матрицы — решением владельца, записанным прямо в коде. Заметно это стало только потому, что `invites.ts` читался следом за `guests.ts`: там ровно тот же вопрос решён верно, поле с кодом фильтруется по роли. Два файла рядом, одна задача, разные ответы — сплошной проход показывает такое, а точечный поиск по шаблону нет.

Отсюда R-117: матрица доступа закрывает ПУТИ, а ключи утекают ПОЛЯМИ ответа. Закрыв роли действие, надо проверить, не отдаёт ли его результат соседний маршрут на чтение.

**Связанные ошибки.** ERR-0099 … ERR-0103, ERR-0026 (роли и деньги), ERR-0097 и ERR-0098 (тот же класс списков), ERR-0019 (токен гостя паре не отдаётся никогда).

Две находки. Маскирование секретов в логе пропускало пять форм адресов (ERR-0097) и ещё три параметра-`uuid` уходили в запрос без проверки (ERR-0098).

**Третий случай одного дефекта — повод перестать чинить точечно.** Непроверенный `uuid` в адресе я закрывал уже дважды: в подарках (ERR-0093) и в курсоре (ERR-0096). Оба раза по найденному месту. **Отрицательные результаты этого захода.** Удаление аккаунта по 152-ФЗ доведено до конца: мягкое на 30 дней и фоновая задача `cleanup` раз в час действительно добивает строки. «Выйти везде» не выгоняет текущую сессию. (2) Маскировать по регулярному выражению на «похоже на токен» вместо имени параметра — отклонено: длинная случайная строка и `uuid` свадьбы неразличимы, а `uuid` в логе нужен. (3) Оставить шаблон `uuid` копией в каждом файле маршрутов — отклонено по причине, ради которой всё это и делалось.

## 2026-09-04 · Второй заход аудита: одна находка на шести маршрутах

Разобрал то, что в первом заходе осталось непрочитанным: деньги и сделки, миграции, гонки, тихие часы, service worker, страницы фронта. Нашлась одна вещь — курсор пагинации пропускал произвольную строку в запрос с приведением типа и давал 500 сразу на шести маршрутах (ERR-0096).

**Отрицательные результаты стоят того, чтобы их назвать.** Я заподозрил двойной счёт в бюджете: у `deals` нет уникальности по `slot_id`, значит два одновременных «Забронировать» могли повесить на слот две сделки, и обе попали бы в сумму. Не подтвердилось — вставка сделки и захват слота условным `update … where deal_id is null` идут одной транзакцией, проигравший откатывается целиком. Тихие часы прогнал по десяти случаям от Калининграда до Камчатки и по границам суток: инварианты держатся. Четырнадцать делений во фронте — все либо с проверкой, либо знаменатель константа. Это не потерянное время: непроверенное «вроде нормально» и проверенное «нормально» — разные вещи, и второе можно записать.

**Универсальность помощника оказалась ложной.** `decodeCursor` принимал произвольное значение сортировки, и разбор шёл по последнему разделителю именно ради этого. Но курсор выдаём мы сами и всегда в одном из двух видов — ISO-время или число. Свобода, которой никто не пользовался, была дырой, и в тестах она стояла как заявленное свойство.

**Почему 400, а не 422.** В ERR-0093 такой же случай закрылся схемой и ответом 422. Здесь схема не годится: курсор приходит строкой запроса и разбирается своим кодом. Ответ оставлен прежним — 400 `bad_cursor` с текстом «начните листать заново»: он уже был в контракте для испорченного курсора, и заводить рядом второй код ради той же ситуации незачем.

**Вид ключа — параметром, а не автоопределением.** Соблазн был угадывать по значению: похоже на дату — считаем датой. Отклонено: `20260904` — и число, и дата, и угадывание разошлось бы с тем, к какому типу приводит конкретный запрос. Маршрут знает свой тип, он его и называет; по умолчанию время, потому что так листают пять маршрутов из шести.

**Альтернативы.** (1) Проверять только идентификатор как uuid, ключ сортировки оставить как есть — отклонено: половина дыры закрыта, `дата|валидный-uuid` по-прежнему роняла бы запрос. (2) Ловить ошибку приведения типа от базы и переводить в 400 — отклонено: запрос всё равно выполняется, ошибка всё равно попадает в лог, а разбирать текст ошибки драйвера ради кода ответа хуже, чем проверить формат заранее. (3) Подписывать курсор, чтобы чужой не разбирался вовсе — отклонено как несоразмерное: курсор не секрет, он не даёт доступа, задача была не в подделке, а в падении.

**Правку существующего теста помечаю отдельно.** «Значение сортировки может содержать разделитель» в `core.test.ts` утверждало ровно ту свободу, которая и была дефектом. Тест переписан на противоположное. Это сужение контракта, а не подгонка проверок под свой код, — но такие правки должны быть видны, поэтому то же самое записано в ERR-0096.

**Связанные ошибки.** ERR-0096, ERR-0093 (тот же класс, другое место входа).

## 2026-09-03 · Аудит на баги и дыры: шесть находок, все закрыты

Сплошной разбор `app/src` и `backend/src` — 176 файлов поиском, 27 прочитаны целиком. Правило разбора: находка попадает в отчёт, только если открыт конкретный файл и сформулирован сценарий поломки. Всё, для чего сценарий не складывался, выброшено — иначе отчёт превращается в список подозрений, по которому нельзя работать.

**Найдено и закрыто.** Два P0: `Math.random` в коде ссылки-приглашения (ERR-0090) и белый экран при заблокированных данных сайта (ERR-0091). Два P1: петля экрана ошибки из того же корня и потеря до трёх суток в обратном отсчёте (ERR-0092). Два P2: 500 вместо отказа на кривом идентификаторе подарка (ERR-0093) и таймер перехода, переживающий экран (ERR-0094).

**Обе дыры P0 — не пробелы в знаниях, а разрывы в уже принятом стандарте.** `randomInt` стоит в двух соседних генераторах с прямым комментарием «предсказуемый код — это вход в чужой аккаунт»; защита хранилища стоит в четырёх местах из шести, включая шим в `index.html`. Оба раза правило в проекте было, и выпало ровно одно место. Отсюда способ искать: сравнивать однотипные места между собой, а не проверять каждое в одиночку — одинокое исключение из своего же правила заметнее, чем абстрактно «небезопасный код».

**Отсчёт проверен запуском, а не рассуждением.** Скрипт прогнал реальные пары дат и напечатал «25 дней при реальных 28» — после этого стало видно, что ошибка не в арифметике остатка, а в откате якоря. На глаз эта разница неотличима: комментарий в коде описывает правильное намерение, а код делает другое.

**Проверка идентификатора — схемой, а не строкой в обработчике.** Первая версия отвечала 404, и `routing.test.ts` поймал нарушение инварианта 10 (см. ERR-0093). Схема `params` оказалась не обходным путём, а более верным ответом: 422 «неверный формат» и 404 «не нашли в базе» — разные случаи, и смешивать их не следовало с самого начала.

**Альтернативы.** (1) Чинить хранилище одной обёрткой на уровне модуля (перехват `window.localStorage`) — отклонено: прячет проблему от чтения кода, а `usePersist` уже был законным местом для этой ответственности. (2) Оставить `Math.random`, увеличив длину кода — отклонено: длина не лечит предсказуемость, а рассуждение про длину и было причиной ошибки. (3) Оставить в отчёте находки без сценария поломки (сравнение хешей кода не за постоянное время, `useBusy` без очистки таймера) — отклонено: сценарий не строится, значит это не находка.

**Регрессии.** 11 тестов, каждый падал бы до своего фикса: `backend/test/audit13.test.ts` (5), `app/src/lib/audit13.test.tsx` (8), `app/src/lib/navTimers.test.tsx` (3). Проверка: фронт — tsc, 212 тестов, eslint, сборка; бэк — tsc, 111 тестов (364 требуют живой базы), eslint.

## 2026-09-03 · Контраст пастельных заливок: шесть токенов вместо подкрутки палитры

**Сделал.** Завёл шесть токенов заливочного текста (`--rose-ink`, `--sage-ink`, `--honey-ink`, `--blue-ink`, `--lav-ink`, `--track-ink`) и перевёл на них 60 мест. Убрал все 23 хексовых цвета текста из классов. `contrast.test.ts` переписан со сплошным сканом пар «заливка + текст» в обеих темах.

**Шло в два захода.** Сначала — только розовая пара по присланному списку, остальное вынес владельцу вопросом по R-15: расширение палитры не моё решение. Владелец ответил «делай как нужно в прод-уровнях» — после этого разобраны все заливки.

**Почему отдельные токены, а не затемнение `*-deep`.** Там, где `*-deep` стоят сейчас, они корректны: 4.55–4.58 на `--bg`. Затемнение ради заливки испортило бы сотню мест, где всё в порядке, и увело бы палитру от утверждённой владельцем (план ч. 10.2). Значения `*-ink` подобраны скриптом: оттенок и насыщенность те же, двигалась только светлота — до первого шага с контрастом ≥4.6. В тёмной теме `--sage-ink`, `--honey-ink` и `--track-ink` совпали с уже существующими значениями, то есть тёмная тема визуально не изменилась вовсе.

**Хардкоды оказались не косметикой.** 23 цвета текста были вписаны хексом мимо токенов. В светлой теме часть проходила норму, поэтому их никто не трогал. В тёмной те же места давали 1.57–2.36, а подпись на фото — 1.00, то есть была невидима. Это не «неаккуратно написано», это неработающий экран в тёмной теме. Поэтому запрет `text-[#rrggbb]` вынесен в отдельный тест, а не оставлен на внимательность.

**Почему тест сплошной, а не список пар.** Первая версия проверяла одну пару `--rose-ink`/`--rose-soft`. Так тест защищает ровно то, что уже починено, и молчит про следующую такую же ошибку. Сплошной скан считает каждую пару из классов в обеих темах, и список исключений в нём пуст — это и есть доказательство, что чинить больше нечего. Проверен обратным ходом, а не на глаз.

**Альтернативы.** (1) Затемнить `*-deep` до нормы на заливке — отклонено, см. выше. (2) Убрать пастельные заливки под текстом — отклонено: заливка несёт смысл (занято, отклонено, превышено, зарезервировано), это не декор. (3) Оставить хексы, добавив их в список исключений теста — отклонено: список на 23 строки перестаёт что-либо ловить, а тёмная тема так и осталась бы сломанной.

**Граница работы.** Нетекстовые хардкоды (`bg-[#C98A8A]`, `ring-[#C98A8A]`, рамки) не трогал: для них норма 3:1, а не 4.5, и переписывать полсотни мест без выигрыша по контрасту — риск ради аккуратности. Записано в ERR-0095 отдельным пунктом.

**Связанные ошибки.** ERR-0008 (там `*-deep` посчитаны под `--bg`), ERR-0095.

## 2026-09-03 · Телефон подрядчика в анкете

Владелец попросил показывать номера подрядчиков в анкетах. Поля не было вообще: ни в базе, ни в контракте, ни в моке — подрядчик известен только номером входа (`users.phone`, OTP).

**Отдельное поле, а не номер входа.** Номер, которым человек вошёл, часто личный, и публикация его в анкете — раскрытие персональных данных, на которое нужно согласие. Поле, которое подрядчик заполняет сам, и есть это согласие; заодно у мастеров рабочий номер обычно отдельный. Пустое поле остаётся пустым и после брони — подстановки логина нет.

**Видно после брони — решение владельца.** Возражение, которое я высказал: у нас в чатах стоит детектор увода сделки мимо платформы, а комиссия со сделок записана точкой монетизации (План ч. 16); открытый номер её обнуляет. Сегодня это ничего не стоит — MVP по плану бесплатный, — но отыгрывать назад через год дороже. Владелец выбрал «после брони», и это же совпало с тем, как продукт описан в документах: «контакты команды» живут в дне X, а не в каталоге.

**Право даёт сделка, а не роль.** Номер видят все участники свадьбы, у которой есть сделка `booked`/`paid_deposit`/`done` с этим подрядчиком: в день X координатору и помощнику звонить по тому же поводу, что и паре. Отмена сделки закрывает номер обратно — повода звонить больше нет.

**Пустое поле в ответе, а не отсутствие поля.** До брони `phone` приходит `null`. Это «ещё рано», а не «номер не указан»: клиент показывает вместо него объяснение и кнопку «Написать».

**Правка старого теста.** `audit3` требовал, чтобы слова `phone` не было в теле ответа вовсе. Требование было верным по смыслу («не раздаётся из каталога»), но проверяло форму: теперь проверяется значение — постороннему `null`, и живого номера в теле нет.

**Итог:** бэк 462 → 469 тестов, фронт 192 → 195, контракт 0.23.

## 2026-09-03 · Даты и календари: от квиза до календаря подрядчика

Вопрос владельца («в онбординге свадьбы только на 2027 год») оказался верхушкой: дату нельзя было выбрать нигде, а на сервере её правка ломала всё производное.

**Симптом и корень — в разных слоях.** Во фронте дата была константой мока, и потому в квизе стояли три готовые строки. На сервере дата принималась как надо, но `PATCH /weddings` менял только колонку: занятость подрядчика оставалась на старом дне, а на настоящий день свадьбы у него было свободно. Проверено на живой базе, а не вычитано в коде — и это единственный способ такое поймать: обе двери в поле выглядят одинаково правильно.

**Каскад переноса вынесен в модуль, оба пути зовут его.** Альтернатива — запретить `date` в PATCH и оставить только `/reschedule` — отклонена: контракт объявляет это поле с самого начала, и клиент вправе им пользоваться. Запрет означал бы «работает не так, как написано».

**Диапазон даты — решение владельца: год назад, пять лет вперёд.** Назад нужен: раздел «После свадьбы» и отзывы работают и у тех, кто пришёл после праздника. Вперёд пять лет — дальше площадки бронь не держат, а 9999 год ломает расчёт сроков молча.

**Дата проверяется календарём, а не длиной строки.** Шаблон `\d{4}-\d{2}-\d{2}` стоял в четырёх местах и пропускал 30 февраля — каждое отвечало 500. Один помощник вместо четырёх шаблонов.

**Свой календарь, а не вендоренный.** `ui/calendar.tsx` из shadcn собран на токенах `bg-background`/`text-foreground`, которых в этом проекте нет — он отрисовался бы бесцветным. `DatePicker` написан в стиле `CityPicker`: те же переменные, тот же полноэкранный оверлей, `Escape` закрывает. Зависимостей не добавлено — `react-day-picker` так и остался неиспользованным.

**Названия месяцев и дней недели даёт Intl, а не словарь.** Склонения («14 июня», а не «14 июнь») идут оттуда бесплатно; в словарь пришлось бы вносить 19 строк на язык и следить за падежами.

**Ответы квиза перестали выбрасываться.** Это не побочная правка: квиз проходят ради плана свадьбы, а `finishOnboarding()` ставил флаг и забывал всё остальное.

**Ошибка по дороге.** `git stash` ради проверки «а были ли ошибки линтера до меня» унёс шесть файлов правок; эхо «восстановлено» соврало, потому что стояло после `;`. Вернул из стеша целиком, записал правилом (ERR-0089).

**Итог:** бэк 453 → 462 теста, фронт 181 → 192, контракт 0.22.

## 2026-09-03 · Иерархия переписки: чат команды и чат исполнителей

Вопрос владельца о том, кто кому пишет, вскрыл расхождение с документом и добавил одну сущность.

**Подрядчик вернулся в чат команды.** §3.11 перечисляет участников `team` дословно: пара, помощники и забронированные подрядчики. В коде подрядчиков там не было — а «Иерархия управления днём X» отдаёт координатору команду подрядчиками именно в этом чате. То есть роль координатора была описана, но исполнить её было негде: он писал каждому отдельно. Кандидат в общий чат не входит — только тот, кто уже забронирован: §3.11 говорит про «забронированных», и кандидату чужая кухня не нужна.

**Чат исполнителей (`crew`) — новая сущность, решение владельца.** Координатор и забронированные подрядчики, пара не состоит. Смысл рабочий: фотограф с декоратором договариваются, во сколько ставить свет, и не грузят этим пару — за то координатора и нанимают.

**Пара видит факт, но не переписку.** Из двух вариантов — полностью невидимый чат или видимая строка без содержимого — владелец выбрал второй, и это правильно: скрытый чат становится скандалом ровно в тот день, когда о нём узнают. Строка отдаётся запросом списка, а на чтение переписки пара получает 403 с объяснением устройства, а не «этот чат не для вашей роли»: она чат видит, и стандартный отказ читался бы как поломка. Последняя реплика и счётчик непрочитанных для неё заменены подписью — они выдали бы ровно то, что решено не показывать, и звали бы туда, куда всё равно не пустят. Уведомления о таких сообщениях паре не приходят по той же причине.

**Тиль координатора не заменяет** — это записано в документе прямым текстом, и код с ним согласен: у Тиль нет модели, отвечает честной заглушкой, чат виден только паре. Без координатора командует пара.

**Заодно:** кнопки SOS в дне X на бэкенде нет вовсе — пути нет в контракте, хотя в Бизнес-логике пункт помечен как готовый. Ушло в «Хвосты».

**Итог:** 447 → 453 теста, контракт 0.21, чат исполнителей заводится тем же триггером, что и командный, — на второй брони.

## 2026-09-03 · Подготовка к прод-релизу, волны 2–4

Продолжение волны 1 (часовые пояса и выгрузка). Восемь находок закрыты кодом, две решены владельцем.

**Пустые поля перестали притворяться данными.** Четыре поля контракта всегда возвращали пустое значение: отзывы в карточке, чат своего подрядчика, дата рассылки опроса, даты под мягкой бронью. Каждое выглядело как рабочее — и именно поэтому прожило по нескольку этапов. Теперь есть механическая проверка: живой ответ сверяется с набором полей схемы (`prod5.test.ts`). Она не заменяет чтение кода, но снимает целый класс: «объявили и забыли».

**Чат своего подрядчика привязан к слоту, а не к подрядчику.** Своей анкеты у него нет по определению — он приходит по ссылке. Заводить ради него `vendor`-чат без `vendor_id` значило бы ослабить ограничение, которое держит смысл вида для всех остальных. Отдельный вид `external` со своим `CHECK` дешевле. Отправитель у его сообщений пустой: аккаунта нет, а выдумывать ему пользователя — это половина учётной записи с правами, входом и восстановлением, которых у него не будет. Чтобы пустой отправитель читался однозначно, в этом виде чата отключено системное предупреждение об уходе мимо платформы — своему подрядчику оно и по смыслу не адресовано: комиссии с него нет.

**Мягкая бронь считается, а не хранится.** Держать «под вопросом» в таблице занятости значило бы закрывать дату под договорённость, которой ещё нет. Считается из сделок в переговорах со сроком.

**Отказ Redis: три поломки вместо одной.** Проверка отказом (адрес задан, службы нет) нашла то, чего не видели ни тесты с живым Redis, ни тесты вовсе без него: каждый запрос висел, сервер не стартовал, отправка сообщения падала. Причина у всех одна — настройка клиента, выбранная под требование BullMQ, которое к этому клиенту не относится. Отдельный вывод: пока соединение ни разу не устанавливалось, счётчик повторов ioredis не работает, поэтому ожидание ограничено на месте вызова.

**Заголовки безопасности — своим хуком, без helmet.** Здесь отдаётся только JSON, и осмысленны пять заголовков. Отдельная зависимость ради пяти строк — это ещё одно звено цепочки поставки. Главный из пяти — `no-store`: гость ходит по личному токену В АДРЕСЕ, и ответ, осевший в кеше промежуточного узла, это чужие данные, выданные следующему.

**Проход глазами подрядчика нашёл две дыры за час.** Договор он оформить не мог, хотя план описывает этот шаг именно с его стороны; изменений пары не видел вовсе, хотя §13.2 требует обратного и карточка в кабинете существует. Оба места проверялись по нескольку раз — но всегда ролью пары. Отсюда правило: сценарий проходится той ролью, от лица которой он написан.

**Решения владельца 2026-09-03.** Лайки «Вдохновения» переносятся на сервер (истории остаются во фронте — сервер хранит только идентификаторы и не притворяется владельцем каталога). Цену сделки можно править до внесения аванса: раньше для этого приходилось отменять сделку, а отмена освобождает дату в календаре подрядчика.

**Отклонено.** Уведомление вместо «Обновлений от пар»: оно уходит в общий список и тонет между «новое сообщение» и «гость ответил», а подрядчику нужно не узнать, а учесть. Хранение чек-листа плана Б отдельной сущностью: это задачи, и второй способ отмечать задачу разошёлся бы с первым при первой правке.

**Что осталось за кодом.** Возвращающийся гость (тайминг, стол, маршрут) и гостевая сторона чата дня X описаны в плане, но их нет ни во фронте, ни в контракте — записаны в «Хвосты», а не выдуманы.

**Итог:** 411 → 447 тестов, контракт 0.15 → 0.20 (111 путей, 142 операции), 5 миграций.

## 2026-09-03 · Этап 9: эксплуатация и 152-ФЗ

Новых путей нет — этап про то, что происходит с данными и со стендом.

**Репетиция восстановления сделана скриптом, а не абзацем.** `restore-drill.sh` проходит весь путь аварии: копия, ЧИСТАЯ база, разворачивание, сверка. Пустая схема — самый частый вид «успешного» восстановления: команда отработала, файл прочитался, данных нет. Скрипт считает таблицы, миграции и строки и падает, если их мало. Первый прогон против живой базы: 60 таблиц, 13 миграций, 18 486 пользователей, 5 секунд.

**Удаление аккаунта проверено обходом всей базы.** Список колонок берётся из `information_schema`, а не из памяти: тест ищет идентификатор в каждой uuid- и текстовой колонке всех таблиц. Проверка «мы вроде всё удалили» ничего не стоит — а эта находит забытую таблицу сама, включая ту, которую заведут на следующем этапе. Через 31 день не остаётся ничего, кроме журнала аудита; до 31-го аккаунт ещё возвращается.

**Runbook — семь сценариев и таблица локаций.** Локации заполняются из панели Timeweb с датой проверки: строка без даты означает «не проверено». Это единственный способ поймать площадку вне РФ — по работающему приложению она неотличима, а 152-ФЗ требует хранения в России.

**Sentry подключён после решения владельца.** Уходят только неожиданные ошибки: `AppError` — это ответ приложения, и слать 404 значит заполнить панель опечатками пользователей, в которых настоящее падение не найти. Отдельно шлются падения фоновых задач: их никто не видит, и без отчёта они обнаруживаются по тому, что перестали приходить push — то есть через сутки. Адрес в отчёте маскируется тем же кодом, что и в логе: Sentry чужой сервис, и гостевой токен из пути туда уехать не должен.

**Что в runbook честно названо отсутствующим:** статус-страница (внешняя служба) и автопереключение на резервную БД (восстановление ручное).

**Итог:** 403 → 411 тестов.

## 2026-09-03 · Закрытие этапа 8: три дыры в абзацах, которые цитировал состав

Состав этапа цитирует §19.4 одной строкой — про пять первых сообщений в день. Абзац, из которого взята цитата, содержит ещё несколько правил, и в состав они не попали. То же с §18.2: оттуда взяты отзывы и рейтинг, а детектор вывода сделки остался за скобками.

**Заявка приходила подрядчику пустой** (ERR-0074). Лид заводится при открытии чата, текст появляется в первом сообщении — связи между этими событиями не было, и карточка в кабинете оставалась без единого слова. Экран в моках показывает именно текст обращения.

**Детектора вывода сделки мимо платформы не существовало** (ERR-0075). Сделан так, как написано в §18.2: не блокировка, а системное сообщение в самом чате — видят обе стороны, остаётся в истории, не чаще раза в сутки. **Ссылка в первом сообщении подрядчика теперь уходит на модерацию** — правило из того же абзаца §19.4 про фишинг. Сообщение доставляется, модератор узнаёт.

**Срок разбора жалобы не был ничем обеспечен** (ERR-0076): 24 часа записаны в документе, а в метриках были только «открытые». Обещание без счётчика — это намерение.

**Что осталось невыполненным и почему.** Автофильтр мата в отзывах (§15) требует словаря, которого нет: выдуманный список даст ложные срабатывания на живых отзывах — нужен от владельца. Чёрный список по телефону и документу (§18.2) больше, чем блокировка анкеты: заблокированный сегодня заводит новый аккаунт на другой номер, и это отдельная работа. Лимиты файлов, антивирус и авто-перевод из §19.4 упираются в S3 и внешние службы, которых нет.

Критерии этапа проверяли две вещи: отзыв по завершённой сделке и порог в три отзыва. Обе работали с первого раза. Проход по описанию и по документам, на которые оно ссылается, нашёл пять дыр.

**У экрана «Сделки» кабинета не было пути.** Подрядчик видел заявки — без сумм и сроков брони (ERR-0073). Заявка и сделка похожи настолько, что одно кажется другим.

## 2026-09-03 · Этап 8: кабинет подрядчика, отзывы, модерация

Шестнадцать путей: лиды, отзывы, ответы на них, аналитика воронки, верификация, жалобы и вся админка.

**Право на отзыв держит база, а не обработчик.** Один отзыв на сделку — уникальный индекс по `deal_id`; один отзыв гостя на подрядчика — по паре «токен + подрядчик». Проверка в коде означала бы два отзыва при двух одновременных отправках, и это ровно тот случай, когда «почти никогда» случается на первой же тысяче пользователей.

**Рейтинг с затуханием и порогом.** Свежий отзыв весит больше: мастер с пятёрками трёхлетней давности не должен вечно стоять выше того, кто хорошо работает сейчас. До трёх отзывов число не показывается — один отзыв от знакомого это 5,0 и первое место. Фильтр по рейтингу подчиняется тому же правилу: иначе выдача отсеивалась бы по цифре, которой на экране нет.

**Три ошибки по дороге.** Создание лида было вынесено в декоратор приложения — и оказалось невидимым для соседних модулей: у Fastify декоратор расширяет один контекст, а не приложение (ERR-0065). Миграция правилась после накатывания в третий раз за сессию, и в третий раз пришлось чистить базу руками (ERR-0066). Гостевой путь отзывов не попал в белый список путей, доступных по токену, и отвечал 401 на законный запрос (ERR-0067).

**Три теста пришлось переписать.** Они проверяли, что заглушки на месте: «нереализованный путь отвечает 501», «у каждого метода есть заглушка». Заглушек не осталось — из 132 операций последняя, вход через OAuth, отвечает своим кодом `oauth_not_configured`. Тест, требующий не доделывать работу, — плохой тест: проверки переписаны на то, что важно всегда («ни один путь контракта не отвечает 404», «реализованный путь не получает заглушку поверх обработчика»).

**Контракт v0.14:** выручка в аналитике стала `Money` — голое число не говорит ни о валюте, ни о единицах (R-11); прирост может быть `null`, потому что «+100 %» от нуля это выдумка; у лида дата и город допускают пустоту.

**Итог:** 359 → 387 тестов. Реализованы все 132 операции контракта.

## 2026-09-03 · Четвёртый проход по этапу 7: сквозное требование

Три прохода шли по спискам: состав этапа, раздел 5, матрица §18.6. Четвёртый пошёл по §13.4 — «устойчивость», раздел без списка путей и без критериев.

**Ограничения частоты не было нигде.** §13.4 требует 10 запросов в секунду на токен, раздел 6 плана — то же для гостевых токенов. Не реализовано ни то, ни другое (ERR-0064). Отдельные пределы существовали — коды из SMS, кадры в альбоме, взносы, — и по ним казалось, что ограничения есть. Отсюда правило: сквозные требования проверяются отдельным проходом, потому что в составе этапов их нет по построению.

Ключ — хеш токена, а не адрес: за одним адресом сидит целый свадебный чат с общим Wi-Fi, и сосед не должен получать отказ из-за чужой активности. Без Redis ограничителя нет вовсе, и об этом сказано в логе: счётчик в памяти процесса за балансировщиком означал бы лимит, умноженный на число процессов, — то есть ложь.

**Список чатов теперь по свежести переписки.** Порядок по дате создания означал, что новое сообщение в старом чате никуда его не двигает; на экране мока чаты стоят по времени последней реплики.

**Что проверено и оказалось в порядке.** Доступ гостя к чату дня X: в матрице роль есть, но гостевого экрана чата в моках нет и пути в контракте тоже — значит, это не дыра, а граница MVP. Идемпотентность RSVP и голоса за меню: обе операции — обновление, повтор ничего не ломает.

**Расхождение в документах для владельца:** §13.4 говорит «10 запросов в секунду на токен», раздел 6 — «10 в минуту» для гостевых. Взято 10/с, настройка вынесена наружу.

**Итог:** 355 → 359 тестов. Этап 7 закрыт.

## 2026-09-03 · Третий проход по этапу 7: забытый получатель

Прошлый проход шёл по разделу 5 — списку фоновых задач. Этот пошёл по §18.6 — матрице уведомлений, на которую состав этапа ссылается прямо: «Push: … с тихими часами и лимитом 3 в день (План §18.6)». В матрице шесть строк и три столбца получателей, и проверять её надо по столбцам, а не по строкам.

**Подрядчик не получал ничего.** Вся рассылка шла по `wedding_members`, а подрядчик участником свадьбы не числится: у него своя сторона. В матрице ему стоит галочка в трёх строках из шести. Работал только чат — там получатели собирались отдельным запросом и подрядчик в него попал случайно. Сдвинутый тайминг до ведущего не доходил вовсе, хотя §13.2 требует этого прямым текстом, а §19.6 называет killer-фичей (ERR-0061).

**О смене статуса сделки не узнавал никто.** Включая истечение мягкой брони, где раздел 5 требует «push паре и подрядчику». Причина знакомая: состояние меняется в четырёх местах, и рассылку забыли во всех. Решение — рассылать по ЖУРНАЛУ переходов, а не из места перехода: `deal_events` уже пишется везде, отметка `notified_at` делает повтор пустым (ERR-0062). Это тот же ход, что и с чатами: там триггеры, здесь задача по журналу, а причина одна — путей несколько.

**Подрядчику пишем того же дела, а не «всем забронированным».** Первая версия фильтровала подрядчиков по `state in (booked, paid_deposit, done)` — и отсекла ровно тот случай, ради которого уведомление и нужно: на снятой броне сделка уже `candidate`. Нашлось тестом про истечение брони.

**Ответы гостей не доходили до пары вовсе** — строка «RSVP гостя → сводка 1/день» не была реализована. Сводка, а не уведомление на каждый ответ: полторы сотни гостей — полторы сотни звонков (ERR-0063).

## 2026-09-03 · Второй проход по этапу 7: пять дыр, из них одна — моя оценка

Вопрос владельца «уверен, что всё доделано?» пришёлся на то место, где я сам себе поверил на слово.

**Главная находка — не в коде, а в оценке.** Состав этапа говорит одной строкой: «здесь же — вся очередь BullMQ из раздела 5». За ней девять задач в отдельной таблице плана. Я сделал три, а остальные объявил заблокированными «каналами доставки». Проверка показала: три из шести никаких каналов не требуют — они шлют обычное уведомление в приложении. Не были сделаны напоминание за 12 часов до конца брони, зов в открывшийся чат дня X и еженедельный дайджест (ERR-0056). Отсюда правило: прежде чем назвать пункт заблокированным, надо назвать, ЧЕМ именно, и проверить, что это правда.

**В день свадьбы уведомления всё равно ждали утра.** План §18.6 говорит «лимит 3 в день ВНЕ дня X» — в код попала первая половина фразы (ERR-0057). Мимо ограничений пускался только флаг, который ставится руками у каждого вызова, а «сегодня свадьба» — свойство дня, а не сообщения.

**Уведомления копились вечно** — ERR-0041 в третий раз. Правило про «таблицу подметает тот же код, что её растит» уже было записано, но живёт оно в журнале, а не в коде, и новая таблица его не унаследовала (ERR-0058).

**Живое соединение переживало токен.** Сокет живёт часами, токен — пятнадцать минут: помощник, которого убрали из команды, читал бы чат до конца дня. Заодно канал не спрашивал согласия на ПДн, хотя обычные пути отвечают на это 403 (ERR-0059). Причина одна: проверки канала написаны отдельно от проверок обычного запроса — две копии правила разошлись сразу, при написании.

**«Печатает…» заливал общий канал**: событие публиковалось на каждое нажатие клавиши (ERR-0060). Третий случай одного класса после альбома и взносов.

**Что осталось честно заблокированным:** сводка кейтерингу, напоминания гостям по RSVP и цепочка «после свадьбы». У гостя нет аккаунта — уведомить его в приложении нечем, нужны почта и SMS.

## 2026-09-03 · Этап 7 закрыт: живой канал, очередь, Web Push

Владелец разрешил три зависимости — `@fastify/websocket`, `bullmq`, `web-push`. Всё, что упиралось в них, доделано.

**Живой канал идёт через Redis, а не через память процесса.** Соединения хранятся в процессе, но процессов за балансировщиком несколько. Хаб публикует событие в pub/sub и раздаёт его всем процессам, включая свой. Без этого сообщение доходило бы только тем, кто попал на тот же сервер — «иногда не приходит» хуже, чем «не приходит никогда»: такое не чинят, потому что не воспроизводят.

Токен канала стоит в строке запроса: браузерный WebSocket заголовки ставить не умеет. Значит, он попадает в лог — и маскируется там же, где гостевые (ERR-0050). Отказ приходит внутри соединения (`{type:'error', status, code}`) и закрывает его кодом 4000+status: молча оборвать рукопожатие значит сказать «сеть барахлит» вместо «токен устарел», и клиент будет переподключаться бесконечно.

**Обычный GET на путь канала отвечает 426, а не 404.** Это нашёл контрактный тест: путь в контракте есть, а 404 отправил бы клиента искать опечатку вместо заголовка Upgrade.

**Push помечается отправленным в той же выборке**, что и выбирается (`for update skip locked`). Иначе два прохода очереди берут одну строку и человек получает уведомление дважды. Подписка удаляется только на 404 и 410 — это «получателя больше нет»; отказ соединения временный, и выбрасывать подписку из-за него нельзя.

**Расписание живёт в очереди, а не в системном cron:** очередь одна и деплой один. Планировщик именованный — рестарт обновляет расписание, а не заводит вторую задачу; после десяти деплоев уборка иначе шла бы десять раз в час.

Из раздела 5 в расписании три задачи: рассылка созревших push, уборка просроченного, страховка на истечение брони. Остальные (сводка кейтерингу, напоминания гостям, дайджест) упираются в каналы доставки — почту и SMS, которых пока нет; писать их значило бы делать заглушку, которая притворяется работающей.

**Ключи VAPID** генерируются `pnpm gen:vapid` и живут только в `.env` и переменных окружения хостинга. В репозиторий приватный ключ не попадает никогда.

**Итог:** 324 → 338 тестов, контракт v0.13 (104 пути). Критерий этапа проверен настоящим WebSocket против поднятого сервера: сообщение доходит второму соединению меньше чем за секунду.

## 2026-09-03 · Этап 7: чаты, уведомления, день X — без трёх зависимостей

Девять путей готовы: список чатов, история с курсором, отправка, чат с подрядчиком, уведомления и отметка прочтения, подписка на push, сдвиг тайминга, план Б.

**Чаты заводит база.** Свадьба создаётся в одном месте, но дата меняется в двух, а сделка становится `booked` в трёх. Триггеры на `weddings` и `deals` вместо вызовов в обработчиках — по той же причине, по какой счётчики мест уехали в триггеры на этапе 5 (ERR-0040): один путь однажды забудут.

**Чат дня X существует с начала и до срока закрыт** — 423, а не 403. «Откроется 13 июня в 09:00» и «нет доступа» — разные сообщения для человека. Появись чат только в срок, в списке до этого была бы пустота вместо строки из моков.

**Тиль отвечает честно.** Заглушка без модели говорит «пока без ИИ, вопрос сохранится». Молчание выглядело бы как поломка, «думаю…» — как обман.

**Перепроверка нашла три дыры.** Лимит push переносил всё лишнее на один и тот же завтрашний день (ERR-0053) — ошибка не проявляется, пока новостей ровно три. Чат дня X у свадьбы без даты был открыт настежь: пустой срок попал в ветку «ограничения нет» (ERR-0054). Любая строка в поле `tz` роняла `Intl`, а с ним каждое уведомление этому человеку (ERR-0055).

Заодно нулевой сдвиг тайминга отвечал 409, которого контракт у этого пути не обещает — та же ошибка, что ERR-0051, поймана до отправки. Теперь 422 по общему соглашению.

**Три зависимости не поставил и жду решения.** `@fastify/websocket` (доставка второму соединению — критерий этапа), `bullmq` (расписание задач раздела 5), `web-push` + ключи VAPID. Ставить зависимость без спроса нельзя, а без них этап работает так: чат — поллингом (§13.4 называет это штатным запасным путём), отложенные задачи считаются на чтении, как истечение брони, push отвечает 501 со своим кодом.

## 2026-09-03 · Решение владельца: ссылку-приглашение выдаёт только пара

Вопрос был вынесен после третьего прохода: помощник мог выдать гостю ссылку, а значит обменять её сам и действовать от имени гостя. Владелец выбрал вариант «б».

Ссылка — не строка списка гостей, а удостоверение. Список ведёт вся команда: помощник добавляет, правит, удаляет, отмечает RSVP. Выдача ссылки закрыта всем, кроме пары: для неё это неизбежно (она и есть отправитель), для помощника — права, которых работа со списком не требует.

Реализация — одно правило в матрице доступа, поставленное ВЫШЕ общего правила по гостям: побеждает первое подошедшее. Отдельной проверки в обработчике нет, иначе следующий гостевой путь снова открылся бы по недосмотру.

**Контракт v0.11:** у `POST …/invite-link` в описании явно сказано «только couple». **Матрица в BACKEND-PLAN ч. 6** получила отдельную строку и правило под номером 2.

## 2026-09-03 · Третий проход по этапам 5 и 6: три дыры вне обработчиков

Вопрос владельца — «уверен, что всё закрыл?». Честный ответ был «нет»: каждый предыдущий проход находил новое. Этот пошёл не по коду обработчиков, а по тому, что вокруг них.

**Гостевые токены писались в лог.** Токен стоит в адресе — так задумано, ссылку пересылают в мессенджере. Но адрес попадает в лог каждого запроса, а лог уезжает к хостеру и в сборщик ошибок. Строка `POST /gifts/{token}/{giftId}/reserve` — это и рабочий ключ от чужой страницы, и готовый ответ на «кто что подарил» (ERR-0050). Закрыто маскировкой в сериализаторе логгера.

**429 обещал то, чего не делал.** Контракт описывает единственный ответ «слишком часто — см. Retry-After», а пределы альбома и взносов отвечали без заголовка. Причина простая: класс, который единственный ставит заголовок, лежал в модуле входа по SMS, и оттуда его не нашли — ERR-0022 повторился дважды подряд. Класс переехал в `errors.ts`, рядом появился `quotaExceeded()` для постоянных пределов, а в контракте — отдельный ответ `QuotaExceeded` (ERR-0051).

**Повтор считали новым запросом.** Проверка «сколько взносов уже сделано» стояла перед проверкой ключа идемпотентности: гость, повторивший на плохой связи свой последний разрешённый взнос, получал 429 вместо своего ответа (ERR-0052). Идемпотентность отказывала ровно там, где нужнее всего.

**Что осталось и требует решения владельца.** Помощник (роль `helper`) может выдать гостю ссылку-приглашение — а значит, обменять её сам и действовать от имени гостя: зарезервировать подарок, снять чужой резерв, загрузить кадр в альбом. Это то же рассуждение, что и в ERR-0047, только адресат другой. Молча сузить права помощника я не стал: «помощник ведёт список гостей» — принятое решение этапа 2, и запрет на выдачу ссылок меняет продукт. Вопрос вынесен в `tasks/todo.md`.

Отдельно: ориентир «банкет на гостя» показывается каждому гостю по замыслу (§10.10), и помощник видит его на общих основаниях. Умножив на число гостей, он получает бюджет площадки — при том что бюджет ему закрыт. Считаю это следствием самой публикации ориентира, а не отдельной дырой, но владельцу стоит знать.

**Итог:** 278 → 285 тестов, контракт v0.10.

## 2026-09-03 · Этап 6: подарки, складчина, фонды — и две дыры в анонимности

Девять путей вишлиста готовы: подарки, резервы, складчина, денежные фонды, «просим не дарить». Двойной резерв закрыт первичным ключом по `gift_id` — вторая строка физически невозможна, а не «проверяется флагом». Складчину и переполнение держит `CHECK funded <= price`; сумму ведёт триггер, потому что строки взносов исчезают и мимо кода.

**Анонимность оказалась двухшаговой.** Критерий этапа — «в ответе паре нет подстроки `guest_token`» — выполнялся с первого прогона: резерв собирается через `exists(...)`, колонка не читается вовсе. Но ссылку-приглашение выдаёт пара, и перевыпуск отдавал ТОТ ЖЕ токен: обменяв ссылку сама, пара открывала гостевую страницу и видела, кто что зарезервировал. Гость об этом не узнавал (ERR-0047). Отсюда правило: обещание «X не увидит» проверяется не по одному ответу, а по двум шагам подряд, доступным X.

Перевыпуск теперь меняет токен. Это потребовало второго решения: **токен — это личность**, и резервы прежнего токена освобождаются триггером. Тот же триггер закрыл ERR-0046 — удалённый гость держал подарок занятым навсегда, потому что связь «токен → гость» не выражена внешним ключом и каскад её не видит.

**Идемпотентность приняли за защиту от потока.** Ключ придумывает клиент, поэтому взнос по рублю с новым ключом растит таблицу без предела (ERR-0048) — ровно ERR-0042, только в деньгах. Добавлен счёт взносов на гостя.

**Живой HTTP нашёл то, чего не видели 278 тестов.** Клиент, который ставит `content-type: application/json` на все запросы, получал 400 на `POST` без тела — `app.inject` этот заголовок не подставляет (ERR-0049). Свой разбор JSON: пустое тело — отсутствие тела, битое — 422 в общем формате.

**Отклонённые варианты.** Глобальная уникальность `idempotency_key` (как в плане таблиц) — отвергнута: гость, выбравший ключ «1», закрыл бы его всем остальным гостям всех свадеб. Уникальность сделана в пределах гостя. Верхняя граница у фонда — не введена: цель фонда это ориентир, а не касса, и отказывать гостю, который внёс больше, не за что; у подарка граница есть, потому что подарок один.

**Ждёт владельца.** Маркетплейс «Купить в приложении» и выплата фондов паре не сделаны намеренно — обе упираются в платежи. Путей в контракте для них нет: заглушка, которая притворяется работающей, здесь означала бы списание денег в никуда.

**Итог:** 266 → 278 тестов, контракт v0.9, живой HTTP-прогон 18/18.

## 2026-09-03 · Бэкенд, этап 5: гости, RSVP, рассадка, тайминг, логистика, меню, альбом

Двадцать два пути. Гость работает без аккаунта — по персональному токену, который паре не отдаётся никогда.

Один голос за блюдо — первичный ключ по гостю: повтор становится сменой выбора.

**Состав стола вычисляется из назначений.** Хранимый второй список расходится с назначениями, и человек оказывается за двумя столами сразу — это уже случалось во фронте (ERR-0016).

**Задачи из шаблона не удаляются.** Чек-лист перестанет быть чек-листом, если из него можно вычеркнуть «забронировать площадку». Отметить — можно.

**Автоплан дня только предлагает.** Контракт обещает предпросмотр; переписывать чужой тайминг без спроса нельзя. Конфликты времени возвращаются списком.

**Перепроверка нашла три дыры.**

1. *Удаление гостя не возвращало место в автобус.* Счётчик увеличивал обработчик, а строки исчезают и мимо него — каскадом. Автобус выглядел полным при пустом сиденье (ERR-0040). Счётчики переехали в триггеры: они срабатывают при любом пути изменения.
2. *Журнал рассылок рос без предела* (ERR-0041).
3. *Гость мог завалить альбом кадрами без счёта* — каждый кадр это файл в хранилище и работа модератора (ERR-0042).

**Проверено на живой базе и живым HTTP:** одноразовая ссылка гаснет после обмена, токен гостя в ответах паре отсутствует, второй гость в полный автобус получает 409, два нажатия голосования дают один голос, две рассылки за полминуты — одна, кадр виден гостю только после одобрения.

## 2026-09-03 · Вторая перепроверка этапа 4: четыре дыры

Первая перепроверка шла по критериям «Готово, когда» и нашла две дыры. Проход по составу этапа построчно нашёл ещё четыре.

**Один подрядчик не мог занять два слота одной свадьбы.** Фотограф, который снимает ещё и видео, — обычная история. Вторая бронь упиралась в первичный ключ `vendor_busy_dates` и получала «дата занята». Занята она была этой же парой. Ограничение писалось под вопрос «две пары на одну дату» и отвечало на него верно; вопрос «одна пара дважды» никто не задал, потому что в моке фронта у каждого слота свой подрядчик (ERR-0037).

Починка потянула вторую половину: отмена одного из двух слотов освобождала дату, хотя второй слот подрядчика ещё держит. Теперь занятость снимается, только если её никто не держит, а ссылка переписывается на оставшуюся сделку.

**Сервер требовал заголовок, которого контракт не обещал.** Обёртку идемпотентности навесили на всё, что меняет данные, — «на всякий случай». Но `Idempotency-Key` объявлен только у `book`, `pay`, `PATCH /deals` и `reschedule`. Клиент, написанный строго по контракту, получал 400 на оформлении договора (ERR-0038). Требовать больше обещанного — такая же поломка, как отдавать меньше.

**Сделку без цены можно было оплачивать бесконечно.** Проверка переплаты выглядела рабочей, но начиналась с `price > 0`: при `price = null` она просто не срабатывала (ERR-0039).

**Прошли сразу шесть проверок:** перевод в `booked` через `PATCH` захватывает дату и отмена её освобождает; чужая занятая дата даёт 409; бронь в свадьбе без даты никого не занимает; `candidate` и `contacted` не входят в «потрачено»; каждый переход попадает в журнал сделки с примечанием.

## 2026-09-03 · Бэкенд, этап 4: слоты, сделки, деньги, документы

Самый нагруженный этап плана. Пятнадцать путей, машина состояний, деньги и три гонки.

**Гонки сняты ограничениями, а не кодом.** Две пары на одну дату одного подрядчика упираются в первичный ключ `vendor_busy_dates (vendor_id, date)`: захват даты идёт в той же транзакции, что и перевод сделки в бронь, вторая получает 409. Повторная оплата упирается в первичный ключ `idempotency_keys`.

**А вот третью гонку ограничение не ловило.** Уникальность на `slots.deal_id` выглядела защитой «один слот — одна сделка», но два РАЗНЫХ идентификатора сделки её не нарушают: два одновременных «Забронировать» оба видели пустой слот, оба отвечали 200, и бюджет считал обе брони. Захват слота переписан условием в самом `UPDATE`. Первый прогон теста прошёл случайно — окно узкое; провалился на втором (ERR-0035).

**Мягкая бронь — срок, а не состояние.** Отдельное состояние «hold» пришлось бы синхронизировать с таймером, и рассинхрон был бы виден паре как «бронь висит, хотя срок вышел». Здесь `negotiating_until` и тот же `UPDATE`, что будет в фоновой задаче этапа 7, выполняемый перед чтением: до появления расписания это единственный способ не показывать протухшую бронь.

**Переходы только вперёд.** «Разбронировать обратно в переговоры» означало бы, что дата уже освобождена, а сделка выглядит живой. Отмена — отдельный и явный выход, из неё пути назад нет: заводится новая сделка.

**Бюджет считается на лету и нигде не хранится.** Ровно эта ошибка уже случалась во фронте: три экрана показывали три разных «потрачено» (ERR-0012). Строки бюджета и их доли взяты из данных фронта генератором — доля, а не сумма, потому что лимиты мока заданы под свадьбу за 1,5 млн.

**Оплата без эквайринга.** План §3.2 выносит платежи за MVP: запись в `payments` фиксирует факт, деньги ходят между парой и подрядчиком напрямую. Поэтому этап 4 НЕ упирается в платёжного провайдера — ждать его не пришлось.

**Перенос даты — целиком или никак.** Если хоть кто-то из забронированной команды занят на новую дату, ответ 409 со списком имён. Частичный перенос хуже отказа: половина команды осталась на старой дате, и это выясняется в день свадьбы.

**Отмена свадьбы требует обоих партнёров.** Первый вызов создаёт запрос, второй исполняет; тот же человек дважды ничего не отменяет. Свадьба — общее решение, и один в ссоре не должен стирать полгода работы двоих.

**Перепроверка нашла две дыры:** гонку за слот (ERR-0035) и вечно растущую таблицу ключей идемпотентности (ERR-0036). Ещё девять адверсарных проверок прошли сразу — в том числе «помощник не видит ни цены сделки, ни договора», «кабинет своего подрядчика не отдаёт команду и бюджет», «чужой ключ идемпотентности не подменяет ответ», «после неудачи тот же ключ работает снова», «сумма по строкам бюджета сходится с общей».

**Заодно всплыло в тестах прошлых этапов:** каталог общий на всю базу, и за прогоны в нём накопились сотни анкет — «первая страница» перестала содержать нужную. Выборки изолированы по имени прогона. Это та же ERR-0023, только про другую таблицу.

**Проверено на живой базе и живым HTTP:** 12 пустых слотов у новой свадьбы, бронь, исчезновение из выдачи на занятую дату, бюджет 8 500 000 после брони и 0 после отмены, двойная оплата одним ключом с `idempotent-replay: true`, договор с версией и дисклеймером, 409 на переходе назад, перенос даты, отмена свадьбы.

**Итог:** 168 → 204 теста, 59 из 130 операций контракта больше не заглушки.

## 2026-09-03 · Доперепроверка этапа 3: сломанное листание и параметр-пустышка

## 2026-09-03 · Бэкенд, этап 3: каталог и анкета подрядчика

**Два критерия этапа были невыполнимы по контракту.** «Выдача не возвращает занятого на дату» — параметра `date` в контракте нет. «Видео 200 секунд отклоняется» — длительность передать негде, в `VendorUpsert` только массив строк `portfolioUrls`. План перечисляет фильтры «категория, город, свободен на дату, цена, рейтинг, видео», контракт знает три из шести. Дописано в контракт v0.5 до начала кода.

**Инварианты — в ключах и ограничениях.** `vendor_busy_dates` с первичным ключом по паре (подрядчик, дата) — это и есть защита от двух броней на один день: вторая вставка не проходит, а не «проверяется и вставляется». Длительность видео ограничена `CHECK` в БД, а не только схемой: файл может попасть в таблицу и другим путём — из админки, из скрипта, из миграции данных.

**Дата под сделкой не снимается кнопкой в календаре.** Подрядчик освобождает только то, что закрыл сам (`source = 'manual'`). Иначе он снимает занятость, поставленную бронью, и пара приезжает на свадьбу к тому, кто уже занят другим.

**Ротация новичков.** Без неё каталог зарастает: у кого есть отзывы, тот получает показы, получает ещё отзывы и вытесняет новых навсегда. Десятая часть первой страницы отдана анкетам без отзывов, вытесняется хвост выдачи, а не верх. Только первая страница: на страницах с курсором подмена даёт повторы и пропуски.

**Автопубликация с пост-модерацией.** `published_at` ставится сразу, `moderated_at` — модератором потом. Держать анкету в очереди значит терять подрядчика, который пришёл один раз и больше не вернётся.

**Перепроверка нашла четыре дыры.**

1. *Каталог был открыт всему интернету.* «Каталог» звучит как витрина, и я поставил его открытым по аналогии с `/geo/*`. Но в контракте у этих путей нет `security: []`, а в матрице раздела 6 у гостя стоит «—». Два источника говорили одно, я не посмотрел ни в один (ERR-0029).
2. *Анкета ушедшего подрядчика оставалась в выдаче.* Мягкое удаление добавили на этапе 1, каталог — на этапе 3, связь между ними никто не провёл (ERR-0030).
3. *Ссылка из анкеты подставлялась в чужую страницу как есть.* `javascript:` в галерее — это выполнение чужого кода в браузере пары (ERR-0031).
4. *Заявки консьержу копились без счёта.* Каждая — ручная работа живого человека (ERR-0032).

**Что осталось честно недоделанным.** `POST /media/upload-url` отвечает 501 с кодом `storage_not_configured`: нужны бакет и ключи объектного хранилища Timeweb. Выдавать ссылку в никуда нельзя — файл уйдёт в пустоту, а анкета будет ссылаться на несуществующее. Из-за этого же ограничение 180 с пока проверяется по числу от клиента: настоящая проверка файла возможна только после загрузки.

**Проверено на живой базе и живым HTTP:** каталог без токена — 401; анкета сохраняется и публикуется; видео 200 с и `javascript:` в портфолио — 422 с именем поля; занятая дата убирает из выдачи; избранное; повторная заявка консьержу — 409; загрузка файла — 501 со своей причиной.

**Итог:** 128 → 165 тестов, 42 из 130 операций контракта больше не заглушки.

## 2026-09-03 · Перепроверка этапов 1 и 2: четыре дыры, 111 → 128 тестов

**Как искал.** Не перечитывал написанное, а задавал вопросы «что будет, если». Что покажет экран устройств через неделю? Как пара найдёт свою свадьбу с нового телефона? Что видит помощник в ответе, который ему разрешён? Кто ставит заголовок с адресом? Каждый вопрос сначала стал падающим тестом, потом исправлением.

**Найдено четыре настоящих дефекта.**

1. *Каждое обновление токена заводило новую сессию.* Обмен refresh создавал новую строку и гасил старую. За неделю активного пользования экран «Сессии и устройства» показал бы сотни «входов» с одного телефона, а время входа сбрасывалось каждые 15 минут — по нему нельзя заметить чужое устройство, ради чего экран и нужен. Тесты этапа 1 проверяли, что старый refresh перестаёт работать; сколько при этом становится сессий, никто не спросил (ERR-0025).

2. *Матрица путей не ловит утечку через поля.* Помощнику открыт `GET /weddings/{id}` — так и задумано, — а в ответе лежал `budgetTotal`. То же с `GET /invites`: список ему виден, и в нём лежали КОДЫ. Приглашение с ролью `couple` в руках помощника — повышение прав в один клик. Хук по путям выглядел исчерпывающим, и именно поэтому про поля забыли (ERR-0026).

3. *Ограничитель по адресу обходился одним заголовком.* `trustProxy: true` поставили ради правильного адреса за балансировщиком — значит, `X-Forwarded-For` принимался от кого угодно (ERR-0027).

4. *Свою свадьбу нельзя было найти после переустановки.* У `/weddings` в контракте был только `POST`; идентификатор жил в localStorage, и с чистого устройства добраться до собственной свадьбы было неоткуда (ERR-0028).

**Отдельная история — ограничители отправки кода.** Их стало три, и каждый закрывает свою дыру: на номер (5 в час) — чтобы чужой телефон не заваливали сообщениями; на адрес (100 в час) — против перебора номеров с одной машины; общий потолок (500 в час) — единственное, что реально ограничивает счёт за SMS.

Первая версия лимита на адрес была 10 в час, и она бы отрезала от входа целого мобильного оператора: за одним адресом CGNAT сидят сотни абонентов. Это выяснилось не рассуждением, а тем, что все наборы тестов ходят с одного адреса и начали друг друга блокировать — та же ситуация в миниатюре. Порог поднят и вынесен в настройку, а точным ограничителем остался лимит на номер.

**Что ещё вылезло по ходу.** Линт поймал в моём же тесте литерал `9_007_199_254_740_993`, который в JavaScript округляется сам: проверка «слишком большая сумма отвергается» проверяла бы округлённое число. Тело запроса пришлось собирать строкой. Заодно на входе появился потолок суммы — `bigint` из PostgreSQL приходит строкой, и `Number()` за границей точного целого молча округляет, после чего «потрачено» перестаёт сходиться с суммой сделок.

**Гонка последней пары.** Проверка «остался ли ещё кто-то с ролью couple» и удаление были двумя запросами: два участника, удаляющие друг друга одновременно, оба увидели бы «остался» и оба удалили — свадьба стала бы ничьей. Стало одним `DELETE` с `NOT EXISTS` внутри. Тест шлёт оба запроса параллельно и требует, чтобы прошёл ровно один.

**Предполётный запрос браузера.** Матрица закрывает всё, для чего не написано правило, а метода `OPTIONS` в правилах нет. Если бы хук успевал сработать, фронт получал бы 403 на предполётный запрос и не смог бы обратиться ни к одному пути свадьбы. Плагин CORS отвечает раньше — но это теперь проверено тестом, а не предположением.

**Проверено на живой базе и живым HTTP:** сессия одна до и после ротации с тем же временем входа; свадьба находится через `GET /weddings`; экспорт содержит свадьбы; у помощника карточка без `budgetTotal` и список приглашений без кодов, у пары коды на месте; нереальная сумма — 422.

**Итог:** 111 → 128 тестов, четыре записи в `ERRORS.md`, контракт v0.4.

## 2026-09-03 · Бэкенд, этап 2: свадьба и команда

**Матрица доступа — один хук на все пути свадьбы, а не проверка внутри каждого обработчика.** Забытая проверка в одном обработчике из сорока — это утечка, которую не видно ни в тесте пути, ни на ревью. Список правил из раздела 6 плана применяется до обработчика и до заглушки 501, поэтому покрывает и пути, которых ещё нет. Главный критерий этапа — «helper получает 403 на бюджете» — выполняется сейчас, когда бюджета не существует: путь этапа 4 закрыт с этапа 2.

**Запрет по умолчанию.** Путь, для которого правило не написано, доступен только паре. Ошибка в эту сторону валит тест этапа с 403 и чинится за минуту; ошибка в другую сторону — помощник видит чужие деньги — не видна никогда.

**Чужая свадьба отвечает 404, а не 403.** 403 подтверждает, что такой идентификатор существует; перебором это превращается в список свадеб. По той же причине приглашение отвечает одинаково на «нет такого кода», «отозван», «истёк» и «уже использован» — ответы сравниваются тестом побайтово.

**Одноразовость ссылки держится условием в UPDATE, а не проверкой перед ним.** `where accepted_at is null` возвращает строку ровно одному запросу; два одновременных перехода по ссылке иначе добавили бы в команду двоих. Так же сделан реферальный код: «один раз на аккаунт» — это первичный ключ `referral_uses.invited_id`, а не `if (уже применял)`.

**Последнего участника с ролью «пара» убрать нельзя.** Свадьба без пары становится ничьей: её нельзя ни редактировать, ни удалить, ни вернуть себе. Проверка в коде, а не в БД — ограничением «хотя бы одна строка с такой ролью» PostgreSQL не выражается.

**Коды приглашений выросли с 4 знаков до 8.** Пример контракта `ДРУГ-7F3K` — это около 20 бит, миллион вариантов: скрипт перебирает за минуты, а ссылка даёт доступ к чужой свадьбе. Стало `ДРУГ-7F3K-QX9M`. Алфавит без 0 и O, 1 и I и L, 5 и S, 8 и B — код читают вслух и переписывают с экрана, и «ноль или буква О» стоит дороже четырёх лишних знаков. Приставка называет роль: человек понимает, кем его зовут, ещё до открытия ссылки.

**Свадьба создаётся не пустой.** 12 слотов мозаики, 12 системных задач, шаблон тайминга. Состав взят из данных фронта генератором, а не набран заново — вторая копия разошлась бы с первой. Важное отличие сида от мока: в моке свадьба показана «в разгаре», площадка забронирована и пять задач сделаны; новой паре достаётся тот же набор пустым. Срок задачи считается от даты свадьбы: `period: 9` в моке был строкой для группировки, здесь из него получается настоящая дата.

**Город берётся из справочника, а не строкой.** Иначе «Уфа» и «уфа» станут двумя разными городами и поиск подрядчиков развалится. Выдуманный город — 404 при создании.

**Что приехало раньше срока.** `categories` с сидом из 35 записей — это этап 3, но слот ссылается на категорию, а слоты создаются здесь. Вместе с ними заведены `slots`, `tasks`, `timeline_events`: данные создаются на этом этапе, обработчики придут на этапах 4 и 5.

**Найдено по ходу:** в алфавите кодов остался знак `8`, хотя комментарий обещал его отсутствие. Поймал тест, который перебирает 200 кодов и ищет спорные знаки. Реферальный код при занятом имени падал в полностью случайный — теперь имя сохраняется: `ТИЛИ-АЛИНА-7F3K`.

**Проверено на живой базе и живым HTTP:** создание свадьбы с мозаикой, приглашение → принятие → повтор 410, helper 403 на бюджете и правке при 200 на карточке, посторонний 404, последняя пара 409, рефералы. 89 → 111 тестов.

## 2026-09-02 · Бэкенд, этап 1: вход, согласие, профиль, гео

**Расхождение, найденное до первой строки кода.** Контракт описывал вход по `email` + `password`. План требует OTP по SMS. Экран `/auth` во фронте реализует телефон и четырёхзначный код, поля пароля в продукте нет вообще. Два источника из трёх сходятся — поправлен контракт (v0.3): `/auth/register` и `/auth/login` заменены на `POST /auth/otp` и `POST /auth/otp/verify`. Путей осталось 103.

**Регистрация и вход — одно действие.** Отдельная регистрация имеет смысл там, где есть пароль: его надо придумать и подтвердить. С кодом из SMS разделение только добавляет экран и вопрос «а я уже регистрировался?». Аккаунт заводится при первой успешной проверке кода, гонку двух одновременных подтверждений закрывает `UNIQUE (phone)` в базе, а не проверка «а есть ли уже такой» в коде.

**Ответ на запрос кода одинаков для нового и известного номера.** Иначе перебором выясняется, кто зарегистрирован в сервисе. То же и при неверном коде: «код неверный или устарел» вместо «такого номера нет».

**Четыре цифры защищены не длиной.** 10 000 вариантов подбираются мгновенно, поэтому защита в трёх ограничениях сразу: код живёт 5 минут, ввести можно 5 раз, запросить — 5 раз в час на номер. Все три живут в таблице `otp_codes`, а не в памяти процесса: счётчик в памяти обнуляется при перезапуске, а перебор — нет. Часовой лимит нужен ещё и от счёта за SMS: без него чужой номер заваливают сообщениями за наши деньги.

**Код хранится HMAC с серверным секретом, а не голым sha256.** Без секрета утечка таблицы вскрывается перебором десяти тысяч вариантов за секунду. Телефон входит в хеш — код от одного номера не подойдёт к другому.

**Refresh одноразовый, и повторное предъявление гасит всё.** При обмене старый гасится. Если погашенный предъявлен второй раз — либо его украли, либо украли новый; в обоих случаях владельца выводит отовсюду и заставляет войти заново. Это дешевле, чем оставить вора внутри. Событие пишется в `audit_log` как `auth.refresh_reuse`.

**Access не проверяется по базе, сессия — проверяется.** Токен живёт 15 минут и подписан; но каждый защищённый запрос всё равно смотрит, не отозвана ли сессия. Без этого «выход со всех устройств» ничего не даёт до истечения access — а это 15 минут чужого доступа после кражи телефона.

**Без согласия — 403, а не 401.** Человек вошёл, но не подписал. 401 отправил бы его на повторный вход по кругу: код он получит, а дальше опять 401. Согласие — единственный защищённый путь без проверки согласия, иначе дать его было бы невозможно.

**Версия документа проверяется сервером.** Клиент присылает ту редакцию, которую показал человеку; при расхождении — 409. Иначе в базе окажется подпись под текстом, которого пользователь не видел, и по 152-ФЗ это не согласие.

**Города — данные фронта, а не вторая копия.** Сид генерируется из `app/src/lib/cities.ts`: 119 записей, 43 крупных, 27 с координатами. Вторая копия разошлась бы с первой на первой же правке. Координаты для остальных не выдуманы: `/geo/nearest` выбирает только среди тех, у кого они есть — иначе человек поедет не в тот город.

**Поиск городов — вычисляемая колонка, а не забота обработчика.** `name_norm` в базе хранит `lower(replace(name, ё, е))`, на ней два индекса: префиксный и триграммный. Это два разных вопроса — «начинается с» и «содержит», — и один индекс на оба не работает. Сортировка: точный префикс → крупный → название, поэтому «сиб» отдаёт Сибай, а не Новосибирск.

**Неописанное поле теперь отвергается, а не выбрасывается молча.** Fastify по умолчанию вырезает лишние ключи. Для нас это хуже отказа: опечатка `quiteHours` вместо `quietHours` просто ничего не делает, и искать её приходится по факту «настройка не сохраняется». Поставлен `removeAdditional: false` — приходит 422 с именем поля.

**Что отложено и почему.** OAuth (`/auth/oauth/{provider}`) отвечает 501 с кодом `oauth_not_configured` — нужны приложения во ВКонтакте, Яндексе, Google и Telegram, их регистрирует владелец; на экране входа кнопок соцсетей сейчас нет. SMS-провайдер сменный: без учётной записи SMSAero код уходит в лог, но сценарий входа рабочий целиком. `NODE_ENV=production` без настоящего провайдера не стартует.
