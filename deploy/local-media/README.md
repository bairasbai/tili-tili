# Локальные фото портфолио

Состав для разработки на одном компьютере: приложение, PostgreSQL16, Redis,
приватный MinIO и настоящий ClamAV. Production-состав находится отдельно в
`../docker-compose.prod.yml`. Альбомы гостей и документы этот запуск не включает.

Нужны Node22, Docker с Linux/amd64 engine и Compose с `additional_contexts`.
Проверяемая конфигурация: Docker29.3.1/Compose5.1.1. Образы закреплены по digest
в `images.json`. При первом запуске нужны интернет, место для образов и сигнатур
ClamAV; проверка готовности антивируса может занять несколько минут.

Из корня репозитория:

```powershell
node deploy/local-media/cli.mjs start
node deploy/local-media/cli.mjs status
node deploy/local-media/cli.mjs logs
node deploy/local-media/cli.mjs restart
node deploy/local-media/cli.mjs stop
```

Сайт: `http://127.0.0.1:43010`. S3 опубликован только на `127.0.0.1:43011`.
База, Redis, ClamD и API не имеют отдельных host-портов. На Windows выбран
контекст `desktop-linux`, на Linux — `default`; удалённый Docker запрещён.
Порты можно задать при первом запуске через `--web-port` и `--s3-port`.
Далее они закреплены в локальной identity. `--project tili-local-media-имя`
создаёт независимый локальный состав; опечатку или пропущенное значение CLI
отклоняет. Не запускайте Compose напрямую: порядок bootstrap/reconciliation
обязателен. Production `.env` и существующие ключи не читаются.

Секреты генерируются внутри Docker. Восемь именованных volumes выбранного
проекта: `credentials`, `api_credentials`, `pg_credentials`, `s3_credentials`,
`pg`, `objects`, `redis`, `clamdb`. `stop` и `restart` сохраняют данные. Launcher
один раз читает и проверяет файлы root MinIO до запуска процесса. API получает
ключ отдельной роли S3, работает от uid1000 и непривилегированной роли БД.
Ключи и содержимое credential volumes не выводите
в журналы. Для переноса нужны согласованные резервные копии после `stop`;
это ещё не проверенная процедура восстановления на сервере.

## Почему перезапуск важен

У локального S3 не заявлен проверенный абсолютный предел завершения POST.
Поэтому launcher включает явный `MEDIA_LOCAL_UNBOUNDED_POST=1`: обязательство
удаления исходника хранится в SQL как `infinity`. Обычная фоновая уборка не
считает истечение времени доказательством завершения чужой записи.

`restart` под эксклюзивной блокировкой удаляет старые контейнеры приложения
и S3, сохраняя volumes. MinIO сначала запускается внутри сети состава на отдельном
неопубликованном порту. В этом режиме настройщик пересоздаёт только принадлежащую
составу учётную запись, выдаёт новый ключ и назначает роль. Роль разрешает читать,
писать и удалять объекты в `quarantine/` и `clean/` одного bucket и читать его регион.
Настройщик проверяет новый ключ, отказ старому ключу и отсутствие административного
доступа, после чего launcher удаляет внутренний контейнер и запускает S3 на
локальном порту сайта. Публикация требует отметки того же запуска и ключа.

До очистки снова проверяются private bucket, отсутствие bucket policy и versioning,
привязка volume/БД/bucket к одному UUID, отказ старому ключу и CORS. До завершения очистки API не
принимает запросы и не запускает фоновые задачи. Незавершённые загрузки
истекают, их удаление подтверждается DELETE и HEAD404 с проверкой версии
обязательства в БД. Для готового файла сохраняется только проверенный объект.
Его карантинный исходник и предыдущие попытки удаляются. Повтор старого
запроса после удаления исходника больше не выдаёт разрешение на запись;
проверенный файл остаётся доступен по своим обычным правилам. Исходные даты
загрузок не переписываются; штатный запас времени квоты после окончания
разрешения сохраняется.

Удаление фотографии сразу убирает её из портфолио. Очередь физической очистки
может потребовать `restart`; активный старый POST не считается завершённым
только по таймеру. Это не обещание стирания всех внутренних orphan chunks
с диска и не сертификация будущего облачного хранилища.

Если команда завершилась ошибкой, контейнер `<project>-operation-lock`
сохраняется. Новая команда изменения откажется работать. Не удаляйте lock
наугад: сначала установите завершение исходной команды и её дочерних процессов,
сверьте exact container ID, `io.tili.project`, `io.tili.operation`,
`io.tili.host-pid`, mounts, сеть и владельца данных. Сохраните журнал отказа.
Только после этой проверки оператор может удалить конкретный свой lock и
выполнить `restart`. Существующие данные без identity или с другим форматом
провайдера автоматически не принимаются и не сбрасываются.

## Проверки и источник провайдера

```powershell
node --test deploy/local-media/test/guards.test.mjs
```

Тесты проверяют аргументы, принадлежность volumes/mounts/сети и отказ доступа
S3 к общим секретам. Интеграционные media tests находятся в backend. Настоящая
загрузка и перезапуск проверяются отдельно: unit fixture их не заменяет.

MinIO: [Chainguard image](https://images.chainguard.dev/directory/image/minio/overview),
[исходники закреплённой версии](https://github.com/chainguard-forks/minio/tree/76c06ff1d2cc844050fdeb1d54bf8fa70db72278),
GNU AGPLv3. В образ копируется готовый binary без изменения исходников.
Настройщик роли использует отдельный образ с бинарником из [Chainguard MinIO Client](https://images.chainguard.dev/directory/image/minio-client/overview).
Этот MinIO использует серверный `MINIO_API_CORS_ALLOW_ORIGIN`; bucket-level
PutBucketCors возвращает501. Его private ACL отдаёт пустой Owner ID, поэтому
принадлежность данных устанавливается UUID marker и bucket tag, а доступ
дополнительно проверяется настоящими анонимными запросами. CloudServer9.5.2
отвергнут после реального multipart POST501, его приёмка не заявляется.

Перед переносом на сервер остаются отдельные гейты TLS/локации, реального
provider POST bound, резервного восстановления, устройств и эксплуатации
по `../../RUNBOOK.md` §9. Локальные результаты их не закрывают.
