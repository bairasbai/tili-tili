# WP00 · FR002: внешняя договорённость

Пользователь 2026-10-07 возобновил полный WP00–WP16 после публикации FR018 в PR49. Эта поставка продолжает FR002 из [общего ТЗ, FR-002](../spec.md); она не заменяет полный WP00 или остальные пакеты.

## Проверенное основание

База: merge459b820188ccd35d23a3afadf1eb1fe5c576f6e4, чистый checkout перед началом. Отметка квиза и возврат категории в поиск уже реализованы в PrebookedSlot.tsx и DELETE slots/prebooked. Создание external deal уже сохраняет имя/телефон/положительную цену и атомарно снимает отметку. OrderDraft/OrderTerms уже сохраняют бриф, работы и снимки; external deal не получает performer receipt. Эти существующие гарантии нужно проверить текущими сценариями, а не объявлять новой реализацией.

Подтверждённый пробел: сохранённый внешний контакт нельзя дописать или исправить; PATCH deals меняет только state/price/note. Карточка внешней сделки не объясняет, что сведения внесла пара, и переход к существующему редактору условий скрыт за общей «Сделкой». Разведка выполнялась чтением кода, без runtime; самостоятельное наличие этих гарантий ещё не означает приёмку.

## Результат и контракт

1. Внешняя карточка явно сообщает: договорённость внесена парой; это не подтверждение исполнителя. Отметка квиза сохраняет свой источник и прежние две CTA.
2. Пара получает понятный переход к существующему составу/условиям заказа. Новая параллельная модель условий не вводится.
3. Текущая пара может дописать или исправить имя/телефон того же external deal через PATCH `/deals/{dealId}/order/external-contact`. Полный payload: expectedVersion существующего заказа, name, phone:string|null. Пустой телефон нормализуется в null; неизвестное значение не превращается в ноль или фиктивный контакт. Исходное имя до120 символов, после trim не менее2; телефон до32, без недопустимых управляющих символов.
4. Read-only externalContact добавляется в существующий WeddingOrder только для реально внешней сделки. Каталожной сделке этот writer недоступен. Запись доступна только живой роли couple и живому external deal booked/paid_deposit; cancelled/done не открываются ради правки контакта.
5. Запись использует существующий порядок wedding/principal/membership/deal/slot/order locks и существующую версию заказа. После ожидания проверяются текущие права, сессия, согласие и срок JWT. Устаревшая версия возвращает409. Повтор того же Idempotency-Key/body не пишет второй раз, требует текущих прав и возвращает актуальную разрешённую проекцию. Чужой ключ/body не переиспользуется. После COMMIT ответ перечитывается в новой авторизованной транзакции с повторной проверкой JWT; отказ не откатывает уже подтверждённую запись и не выдаёт сохранённое тело лишившемуся доступа.
6. Имя и телефон меняются в существующей сделке; версия заказа возрастает. Audit фиксирует автора/изменённые поля/версию, без копирования телефона в diff. Новый deal, деньги, payments, vendor calendar/resource allocations, program receipts не создаются и не меняются.
7. Опубликованные снимки и receipts остаются неизменными. Изменившийся контакт делает прежний источник условий устаревшим по существующему fingerprint; новая запись не является принятием условий исполнителем.
8. UI использует существующую обработку version conflict, точного повтора после потерянного ответа, сброса при смене сделки/сессии и RU/EN. После подтверждённой записи карточка перечитывается.

## Границы

Исходное создание external deal сохраняет нынешнее требование положительной известной цены. Поддержку создания без цены FR002 прямо не требует; отдельное изменение финансового контракта здесь не делается. Контактный writer не заменяет отмену/замену подрядчика, не переносит даты, не снимает ресурсные barriers371–374, не превращает external program acknowledgment в performer terms acceptance. Схема БД не расширяется: используются существующие external_name/external_phone и deal_orders.version.

## Приёмка

Текущие HTTP/PG проверки: read projection, сохранение/перечитывание, null и валидация, stale/race, idempotency/replay, чужие роли/ID/каталожный deal, revoked session/membership/consent и JWT expiry после реального ожидания. Snapshot/financial/resource/history invariants сравниваются до/после. Фронт: явное происхождение, переход к условиям, версия/потерянный ответ/переключение роли/сессии, RU/EN. Затем fresh independent review, полный init.sh, actual built browser/native FR002 сценарий, документация, отдельный коммит/PR/CI/main. Полный WP и физические устройства не принимаются одной этой поставкой.
