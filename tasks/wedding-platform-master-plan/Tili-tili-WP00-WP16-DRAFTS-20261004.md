##### 3. Код: нормализация условий

Новые файлы, одинаковая небольшая реализация в двух существующих TypeScript-проектах:

- `Тили-тили/app/src/lib/externalTerms.ts`
- `Тили-тили/backend/src/deals/external-terms.ts`

Дублирование здесь намеренное: общего компилируемого пакета между app/backend в рамках этого чтения не подтверждено; новая инфраструктура ради одного поля не предлагается. Контракт и парные тесты должны фиксировать одинаковое поведение.

```ts
export const EXTERNAL_TERMS_MAX_LENGTH = 2000

export type ExternalTermsResult =
  | { ok: true; value: string | null }
  | { ok: false; reason: 'invalid' | 'too_long' }

/** Literal text entered by the couple; never a vendor acceptance. */
export function normalizeExternalTerms(input: unknown): ExternalTermsResult {
  if (input == null) return { ok: true, value: null }
  if (typeof input !== 'string') return { ok: false, reason: 'invalid' }
  // Count Unicode code points, matching JSON Schema maxLength / PG char_length.
  if ([...input].length > EXTERNAL_TERMS_MAX_LENGTH) {
    return { ok: false, reason: 'too_long' }
  }
  // Allow ordinary multiline text and tabs, but reject NUL/control characters.
  if (/[\u0000-\u0008\u000b\u000c\u000e-\u001f\u007f]/u.test(input)) {
    return { ok: false, reason: 'invalid' }
  }
  const value = input.trim()
  return { ok: true, value: value === '' ? null : value }
}
```

###### Legacy `+1`

Старый текст «Анна, +1» остаётся совместимым и может уйти как `{ name: 'Анна', plusOne: true }`. Preview подписывает вторую персону «Человек без указанного имени (+1)».

Для добавления имени вместо placeholder есть явное действие «Указать имя вместо +1»: оно переводит draft в именованный режим, добавляет одно пустое поле и снимает legacy-флаг. Пока имя не заполнено, строка не готова. Не отправлять `plusOne: true` одновременно с `members`: взаимодействие двух способов не требуется этому срезу и не должно выдумываться. «Убрать +1» явно оставляет только основного человека.

###### Счётчики и итог

- Preview: «К отправке: N приглашений · M персон»; это локальная оценка выбранных валидных строк, а не факт создания
- Named-строка: `1 + members.length`; legacy-only `+1`: две персоны по описанному контракту
- Лимит 300 относится к приглашениям/строкам, не к сумме персон
- После ответа: «Создано приглашений: N» берётся из `res.created.length`
- «Создано персон: M» берётся из суммы валидных `partySize` в `res.created`; если хотя бы один размер отсутствует/некорректен — «Число персон уточняется после обновления списка», без подстановки preview, `plusOne` или `1`
- При пустом `created` известный итог персон — 0, поскольку сервер вернул пустой массив
- `skipped.index` относится к отправленному массиву; до запроса сохраняется соответствие `submittedIndex → draft.id → sourceIndex`
- `invalid` показывается как «Строка не принята сервером: проверьте поля», а не обязательно как ошибка телефона
- При ошибке запроса сохраняются исходный текст, правки и состав семьи; прошлое сообщение об успехе убирается
- После частичного ответа созданные строки удаляются из retry-draft, пропущенные сервером и неотправленные локальные ошибки остаются для исправления
- Локальная пометка дубликата предварительная. Сохраняем проверку primary name/phone текущего экрана; не придумываем новую дедупликацию member-имён

```ts
  guestNameKey,
  NAME_MAX,
  normalizeRuPhone,
  parseGuestList,
} from './guestsImport'

export const IMPORT_ROWS_MAX = 300
export const IMPORT_MEMBERS_MAX = 9
export const IMPORT_PHONE_MAX = 32

export type ImportMemberDraft = { id: string; name: string }
export type ImportInvitationDraft = {
  id: string
  sourceIndex: number
  raw: string
  name: string
  phone: string
  mode: 'named' | 'legacy-plus-one'
  members: ImportMemberDraft[]
  nextMemberId: number
}
export type ImportIssue = {
  field: 'name' | 'phone' | 'members' | 'mode'
  memberId?: string
  code: 'name-length' | 'phone' | 'too-many-members' | 'mixed-modes'
}
export type ExistingImportGuest = { name: string; phone?: string | null }
export type ImportPreviewRow = ImportInvitationDraft & {
  issues: ImportIssue[]
  duplicate: boolean
  persons: number
}

export function createImportDraft(text: string): ImportInvitationDraft[] {
  return parseGuestList(text).map(row => ({
    id: `import-${row.index}`,
    sourceIndex: row.index,
    raw: row.raw,
    name: row.name,
    phone: row.phone ?? row.invalidPhone ?? '',
    mode: row.plusOne ? 'legacy-plus-one' : 'named',
    members: [],
    nextMemberId: 0,
  }))
}

function validName(value: string): boolean {
  const name = value.trim()
  return guestNameKey(name).length >= 2 && name.length <= NAME_MAX
}

export function validateImportDraft(row: ImportInvitationDraft): ImportIssue[] {
  const issues: ImportIssue[] = []
  if (!validName(row.name)) issues.push({ field: 'name', code: 'name-length' })
  const phone = row.phone.trim()
  if (phone && (phone.length > IMPORT_PHONE_MAX || !normalizeRuPhone(phone))) {
    issues.push({ field: 'phone', code: 'phone' })
  }
  if (row.members.length > IMPORT_MEMBERS_MAX) {
    issues.push({ field: 'members', code: 'too-many-members' })
  }
  if (row.mode === 'legacy-plus-one' && row.members.length > 0) {
    issues.push({ field: 'mode', code: 'mixed-modes' })
  }
  for (const member of row.members) {
    if (!validName(member.name)) {
      issues.push({ field: 'members', memberId: member.id, code: 'name-length' })
    }
  }
  return issues
}

export function appendImportMember(row: ImportInvitationDraft): ImportInvitationDraft {
  if (row.mode !== 'named' || row.members.length >= IMPORT_MEMBERS_MAX) return row
  return {
    ...row,
    members: [...row.members, { id: `${row.id}-member-${row.nextMemberId}`, name: '' }],
    nextMemberId: row.nextMemberId + 1,
  }
}

export function nameLegacyCompanion(row: ImportInvitationDraft): ImportInvitationDraft {
  if (row.mode !== 'legacy-plus-one') return row
  return appendImportMember({ ...row, mode: 'named', members: [] })
}

export function buildImportPreview(
  rows: ImportInvitationDraft[],
  existing: ExistingImportGuest[] | undefined,
): ImportPreviewRow[] {
  // undefined означает, что существующий список ещё неизвестен.
  // Дубликаты внутри текущей вставки всё равно обнаруживаются.
  const names = new Set((existing ?? []).map(g => guestNameKey(g.name)))
  const phones = new Set((existing ?? []).flatMap(g => {
    const phone = g.phone ? normalizeRuPhone(g.phone) : null
    return phone ? [phone] : []
  }))
  return rows.map(row => {
    const issues = validateImportDraft(row)
    const phone = row.phone.trim() ? normalizeRuPhone(row.phone) : null
    const duplicate = issues.length === 0 && (
      names.has(guestNameKey(row.name)) || (!!phone && phones.has(phone))
    )
    if (issues.length === 0 && !duplicate) {
      names.add(guestNameKey(row.name))
      if (phone) phones.add(phone)
    }
    return {
      ...row,
      issues,
      duplicate,
      persons: row.mode === 'legacy-plus-one' ? 2 : 1 + row.members.length,
    }
  })
}

export function importPayload(row: ImportInvitationDraft): GuestImportRow {
  if (validateImportDraft(row).length > 0) throw new Error('invalid-import-draft')
  const phone = row.phone.trim()
  return {
    name: row.name.trim(),
    ...(phone ? { phone } : {}),
    ...(row.mode === 'legacy-plus-one' ? { plusOne: true } : {}),
    ...(row.mode === 'named' && row.members.length > 0
      ? { members: row.members.map(member => ({ name: member.name.trim() })) }
      : {}),
  }
}

export function prepareImport(preview: ImportPreviewRow[]) {
  const selected = preview.filter(row => row.issues.length === 0 && !row.duplicate)
  return {
    rows: selected.map(importPayload),
    rowIds: selected.map(row => row.id),
    invitations: selected.length,
    persons: selected.reduce((sum, row) => sum + row.persons, 0),
  }
}

// Response.created — одна primary-строка на созданное приглашение.
// Необязательный partySize проверяем, никакого ?? 1.
export function createdImportPersons(
  created: ReadonlyArray<{ readonly partySize?: number }>,
): number | null {
  let total = 0
  for (const row of created) {
    const size = row.partySize
    if (typeof size !== 'number' || !Number.isInteger(size) || size < 1 || size > 10) {
      return null
    }
    total += size
  }
  return total
}

export function retainUncreatedDrafts(
  all: ImportInvitationDraft[],
  submittedIds: string[],
  skipped: ReadonlyArray<{ index: number }>,
): ImportInvitationDraft[] {
  const submitted = new Set(submittedIds)
  const skippedIds = new Set(skipped.map(item => {
    if (!Number.isInteger(item.index) || item.index < 0 || item.index >= submittedIds.length) {
      throw new Error('invalid-import-response-index')
    }
    return submittedIds[item.index]!
  }))
  return all.filter(row => !submitted.has(row.id) || skippedIds.has(row.id))
}
```

```tsx
          inputMode="tel"
          maxLength={IMPORT_PHONE_MAX}
          onChange={event => onChange({ ...row, phone: event.target.value })}
          aria-invalid={row.issues.some(issue => issue.field === 'phone')}
        />
      </label>
      {row.mode === 'legacy-plus-one' ? (
        <div>
          <p>{t('Человек без указанного имени (+1)')}</p>
          <button type="button" onClick={() => onChange(nameLegacyCompanion(row))}>
            {t('Указать имя вместо +1')}
          </button>
          <button type="button" onClick={() => onChange({ ...row, mode: 'named' })}>
            {t('Убрать +1')}
          </button>
        </div>
      ) : (
        <div className="space-y-2">
          {row.members.map((member, index) => (
            <div key={member.id}>
              <label>
                {t('Человек семьи')} {index + 2}
                <input
                  value={member.name}
                  maxLength={NAME_MAX}
                  aria-invalid={row.issues.some(issue => issue.memberId === member.id)}
                  onChange={event => onChange({
                    ...row,
                    members: row.members.map(item => item.id === member.id
                      ? { ...item, name: event.target.value }
                      : item),
                  })}
                />
              </label>
              <button type="button" onClick={() => onChange({
                ...row,
                members: row.members.filter(item => item.id !== member.id),
              })}>
                {t('Удалить человека')} {index + 2}
              </button>
            </div>
          ))}
          <button
            type="button"
            disabled={row.members.length >= IMPORT_MEMBERS_MAX}
            onClick={() => onChange(appendImportMember(row))}
          >
            {t('Добавить человека в семью')}
          </button>
        </div>
      )}
      {/* Рядом с конкретными полями вывести ошибки через t(),
          связав их через aria-describedby и стабильные row/member id. */}
      <p>{t('Исходная строка:')} {row.raw}</p>
    </fieldset>
  )
}
```

При вводе использовать `setDrafts(previous => previous.map(...))`, чтобы правка одной строки не теряла соседнюю. Для member-строк стабильные id из `nextMemberId`, а не array index; удаление второго человека не должно переносить фокус/значение третьего.

##### 8. Фрагмент D: отправка и честный результат

Интеграционный эскиз для изолированной панели. `prepared`, `drafts`, `weddingId`, `onImported` берутся из её текущего состояния/props; `ImportResult` сохраняет полноценный `skipped.index`.

```tsx
const pendingRef = useRef(false)
const [busy, setBusy] = useState(false)
const [result, setResult] = useState<{
  invitations: number
  persons: number | null
  skipped: { index: number; name: string; reason: 'duplicate' | 'invalid' }[]
} | null>(null)

async function submitImport() {
  if (pendingRef.current) return
  if (!weddingId) {
    setError(t('Сначала создайте свадьбу — гости живут в ней'))
    return
  }
  if (prepared.rows.length === 0 || prepared.rows.length > IMPORT_ROWS_MAX) return

  // Снимок только текущего утверждённого предпросмотра.
  const submitted = prepared
  const submittedDrafts = drafts
  pendingRef.current = true
  setBusy(true)
  setError(null)
  setResult(null)
  try {
    const response = await importGuests(weddingId, submitted.rows)
    if (!response || !Array.isArray(response.created) || !Array.isArray(response.skipped)) {
      throw new Error(t('Сервер не вернул итог импорта. Обновите список перед повтором.'))
    }
    // Проверить индексы прежде, чем удалять любые локальные строки.
    const remaining = retainUncreatedDrafts(submittedDrafts, submitted.rowIds, response.skipped)
    setResult({
      invitations: response.created.length,
      persons: createdImportPersons(response.created),
      skipped: response.skipped,
    })
    setDrafts(remaining)
    onImported()
  } catch (error) {
    setError(explainError(error))
    // Draft сохраняется. При потере ответа сервер мог уже выполнить импорт:
    // сначала обновить список, затем повторять после проверки дубликатов.
    onImported()
  } finally {
    pendingRef.current = false
    setBusy(false)
  }
}
```

Обязательные детали интеграции:

- Панель монтируется как `<GuestImportPanel key={weddingId ?? 'no-wedding'} ... />`; никакого переноса draft из одной свадьбы в другую
- Пока запрос идёт, запретить submit, редактирование, возврат к исходному тексту и переключение режимов; `pendingRef` закрывает повтор до следующего render
- При внешнем размонтировании/смене свадьбы поздний ответ не должен создавать итог в панели другой свадьбы. Callback `onImported` привязан к исходному запросу/свадьбе; при сборке проверить stale callback поведение существующего `useApi`
- Успех сервера с невалидными/непонятными индексами не трактовать как «никого не добавлено»; показать неопределённость, обновить список, сохранить draft
- `created.length + skipped.length` должен соответствовать количеству отправленных строк. В будущей реализации добавить явную проверку response partition; при несовпадении сохранить draft и показать неизвестный итог, а не удалять строки по предположению
- При partial response показать результат и оставить пропуски для правки. После reload повторная локальная дедупликация использует уже обновлённые данные
- `skipped` показывать с номером исходной строки через сохранённый `submitted.rowIds`, а не через положение в исходной вставке напрямую
- В `Wedding.tsx` не держать одновременно старый и новый `bulkResult`/`preview`; два конкурирующих состояния создадут ложный итог

##### 2. Точное поведение подэтапа

- Прежнее условие незавершённости `!task.done` сохраняется; `done: true` исключается до ограничения тремя строками
- Известный срок — только реальная календарная дата `YYYY-MM-DD`, годы 0001–9999. Проверяются длина месяца и високосный год. Никакие часы, UTC, часовой пояс свадьбы/пользователя и текущий день не добавляются
- Известные даты идут по возрастанию. Старые незавершённые сроки также остаются первыми; подписи «просрочено», «сегодня», «на этой неделе» этот подэтап не вычисляет
- При одинаковой известной дате сохраняется порядок входного ответа. `null`/`undefined` означают missing. Остальные невалидные значения, в том числе пустая строка, пробелы, невозможная дата и timestamp вместо date, означают invalid
- Missing и invalid вместе идут после всех известных сроков, сохраняя взаимный порядок входного ответа. Невалидный срок не становится 1970 годом, сегодняшней датой или искусственным приоритетом
- Сортируется новый массив описателей. Входной массив, записи, серверный sort, порядок полного чек-листа и сохранённые даты не меняются
- Имя ответственного берётся только из `task.assignee.name`; trim нужен лишь для определения/показа непустого имени. Если имени нет, строка имени не выводится. Из отсутствующего имени нельзя делать вывод «никто не назначен» или угадывать имя по ID
- Общая подсказка объясняет правило порядка; каждая строка отдельно объясняет известный/отсутствующий/невалидный срок. Для missing допустимо сохранить прежнюю справочную подпись period; period не участвует в сортировке и не превращается в конкретную дату
- Клик по любой строке и по «Чек-лист →» сохраняет `/wedding/checklist`. Нет новых кнопок завершения/скрытия, PATCH, ссылок с task ID, новых API, запросов members или уведомлений
- Строки и объяснение показываются только при `ready(tq)`. Ошибка/загрузка/403 и пустой/полностью закрытый список сохраняют существующее различение состояний

Это правило объясняет именно календарный порядок. Оно не утверждает, что задача важнее по последствиям, дороже, назначена текущему пользователю или требует выполнения в ближайшие семь дней.

##### 4. Чистый selector

Полный предлагаемый файл `Тили-тили/app/src/lib/homeTaskPriority.ts`:

```ts
import type { components } from './api/schema'

type Task = components['schemas']['Task']

export type TaskDueInfo =
  | { state: 'known'; date: string }
  | { state: 'missing' | 'invalid'; date: null }

/** Calendar dates only: no clocks, Date parsing, timezone or silent repair. */
export function classifyTaskDue(value: Task['due']): TaskDueInfo {
  if (value == null) return { state: 'missing', date: null }
  if (!/^\d{4}-\d{2}-\d{2}$/.test(value)) return { state: 'invalid', date: null }
  const year = Number(value.slice(0, 4))
  const month = Number(value.slice(5, 7))
  const day = Number(value.slice(8, 10))
  if (year < 1 || month < 1 || month > 12) return { state: 'invalid', date: null }
  const leap = year % 4 === 0 && (year % 100 !== 0 || year % 400 === 0)
  const monthDays = [31, leap ? 29 : 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31]
  if (day < 1 || day > monthDays[month - 1]!) return { state: 'invalid', date: null }
  return { state: 'known', date: value }
}

/** First three open tasks; ties and all unknown dates retain response order. */
export function selectHomeTaskPreview(tasks: readonly Task[]) {
  return tasks
    .map((task, sourceIndex) => ({ task, sourceIndex, due: classifyTaskDue(task.due) }))
    .filter(({ task }) => !task.done)
    .sort((a, b) => {
      if (a.due.state === 'known' && b.due.state === 'known') {
        if (a.due.date < b.due.date) return -1
        if (a.due.date > b.due.date) return 1
      } else if (a.due.state === 'known') {
        return -1
      } else if (b.due.state === 'known') {
        return 1
      }
      return a.sourceIndex - b.sourceIndex
    })
    .slice(0, 3)
}
```

Календарная проверка нужна только для честного отображения/сортировки пришедшего значения. Она не изменяет серверную валидацию, не задаёт допустимый бизнес-диапазон для редактора и не исправляет сохранённые данные. Даты сравниваются как уже проверенные фиксированные десятисимвольные строки, без localeCompare и runtime locale.

## Очерёдность продолжения

Подготовка четырёх текстовых срезов не меняет зависимости реализации и не означает запуск четырёх WP параллельно. После восстановления разрешённого coding-процесса:

1. Установить актуальный main и состав незавершённой работы. Проверить итог CI и применимость сохранённых результатов
2. Закрыть подтверждённый остаток FR-018, начиная с причины PWA 403/404, затем отдельные части и полную приёмку WP00. PR #42 повторно не переносить
3. WP01 вести по готовности решений о провайдерах/хранении; WP03 после WP00 не требует ожидания WP01. WP02 опирается на WP00, его файлы — на WP01; WP07 требует WP00/WP01
4. Продолжить WP04 после WP02/WP03, WP05 после WP03/WP04, WP06 после WP05 и файловой готовности WP01
5. WP08 — после проверенных команд WP00–07; WP09 — после WP02–07 и основы 017/квиза; WP10 — после WP01/WP03/WP04; WP12 — после 018-A/B, WP00/WP07; WP13 — после WP12
6. WP14 — после WP02/WP04/WP06; WP15 — после WP01/WP04/WP06/WP07. WP11 зависит от решений владельца и провайдера; прямые зависимости от WP в плане не указаны
7. WP16 завершает приёмку требуемого состава последним

Каждая логическая поставка — отдельный проверяемый объём. Крупный WP допустимо делить на самостоятельные части; его полный статус остаётся открытым до всей приёмки. Ветку, commit, PR, push, merge и выпуск выполнять только в разрешённом процессе, не в рамках подготовки этого файла.
