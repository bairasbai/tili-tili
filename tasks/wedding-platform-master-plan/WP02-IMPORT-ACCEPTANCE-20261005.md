## Реализованный сценарий; приёмка по доказательствам

1. Вставка строк → редактирование основного человека и остальных персон → предпросмотр всего приглашения. Дубли проверяются среди всех имён, включая имя legacy-спутника, а также по телефону; отдельно обозначены повтор в семье, в принятой части текущего импорта и уже существующая персона. Отвергнутая/невалидная семья не резервирует имена, поэтому следующая допустимая строка не теряется.
2. Явная отправка содержит только валидные недублирующиеся приглашения. Лимит — 300 приглашений и 10 персон в приглашении: основной человек + 9 дополнительных. RU/EN используют действующие правила plural, а не одну форму для всех чисел.
3. Полный ответ сопоставляется с исходными ID строк, не с индексом после фильтрации. Подтверждённые строки исчезают; ошибки и серверные пропуски сохраняются для исправления. Числа создания берутся из ответа, не из предпросмотра.
4. Неизвестный итог (сеть, timeout, 5xx, неверный/неполный success body) сохраняет неизменяемую попытку. Изменение/удаление имён и сброс заблокированы. Только «Повторить тот же импорт» отправляет исходное тело. Обновившийся список, где уже появились записи, не меняет тело повторной попытки. Автоматического повтора нет. Закрыть панель можно без потери попытки в пределах её текущего времени жизни.
5. Первичный HTTP4xx является отказом текущего запроса и сохраняет редактирование. HTTP4xx при повторе не доказывает откат предыдущей неизвестной транзакции, поэтому исходная попытка остаётся зафиксированной. Ошибка callback обновления списка не превращает подтверждённый POST в новую отправку.
6. Прежние границы свадьбы/аккаунта/сессии и подавление устаревших ответов сохранены. Продление токена в той же сессии и закрытие/открытие не теряют ввод. Исходящие уже отправленные команды не объявляются отменёнными.
