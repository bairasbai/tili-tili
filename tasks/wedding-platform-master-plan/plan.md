# Технический план реализации

Связанные документы: [ТЗ](spec.md), [baseline](baseline.md), [задачи](tasks.md), [действующий roadmap](../product-improvements-roadmap.md).

## 1. Архитектурный подход

Сохранить текущие React/TypeScript, Fastify, PostgreSQL, Redis, PWA и контрактную генерацию. Не вводить микросервисы ради разделения файлов. Сначала закончить существующие функции и сформировать предметные модули внутри текущего приложения.

Для каждого этапа: проверить актуальные инварианты `CLAUDE.md`, основную продуктовую спецификацию и бизнес-логику; составить feature-level spec/plan/tasks по существующему процессу. Этот пакет задаёт общий охват и границы. Точные столбцы, DTO и URL утверждаются в действующих источниках правды перед кодом, а не копируются в новый контракт.

Намеренных исключений из инвариантов проект не предлагает. Контрольные точки: R-MAP/R-BTN, i18n, null вместо потери значения, серверная настройка, отсутствие мёртвых кнопок, настоящие состояния данных, ограничения БД, секреты вне Git. Денежные значения берутся из действующего Money-контракта; устаревшую формулировку о «целых рублях» не использовать для округления уже существующих копеек.

## 2. Интеграция уже написанного — до расширений

1. Зафиксировать новые SHA всех веток и статусы открытых PR. Не затрагивать незакоммиченную работу другой сессии.
2. Отдельной правкой в рабочей ветке исправить ожидания consent в двух новых наборах тестов; проверить соответствие актуальному контракту, версии согласия и требованиям age/consent. Не менять production-код ради старого фикстурного ожидания.
3. Прогнать сценарии 019 на настоящих PostgreSQL/Redis. Разобрать все ошибки после успешной подготовки пользователя; не считать первичную причину единственной возможной.
4. Создать интеграционную ветку от актуального main. По истории выбрать перенос PR #1 → PR #3 → продолжения без повторного применения общих коммитов. Затем совместить PR #2 либо выбрать иной эквивалентный порядок с тем же конечным набором изменений. Не смешивать в одной поставке независимый рефакторинг.
5. Разрешить смысловые конфликты бронирования, квиза, шаблонов, подсказок, тайминга и контрактов. Generated-файлы пересоздать штатными генераторами. Проверить уникальность/порядок миграций; не применять советы из старого описания PR о конфликтующих номерах без проверки текущих файлов.
6. На одноразовой базе проверить установку с нуля и обновление с базы main с данными. Применённые в реальной среде миграции не переписывать: исправления делать последующей миграцией. Для удаляющих преобразований использовать backup/restore и forward-fix; опасный down не выполнять над пользовательскими данными.
7. Завершить 019: интерфейс запросов/ответов, принятие, истечение, перенос/отмена, стирание и выгрузка. Проверить общий путь bookVendor и снимки условий.
8. Прогнать общий gate и браузерные сценарии на точном SHA интеграции. Слияние и deployment выполняются отдельным авторизованным действием; этот документ ничего не сливает.

## 5. Данные и миграции

Ниже — изменения модели, подлежащие внесению в основную бизнес-логику; это не альтернативная физическая схема.

### Семья и персона

- Семья/приглашение — единица коммуникации, персона — единица участия и вместимости. Участие персоны привязано к мероприятию.
- Старый guest становится основной персоной. `plusOne=true` создаёт отдельную безымянную персону с происхождением «миграция», не выдуманное имя или согласие на обработку дополнительных сведений.
- Для наследуемой рассадки/рейса можно сохранить существующее фактическое размещение двух мест; блюдо, аллергия, имя и индивидуальный ответ спутника остаются «нужно уточнить».
- До переключения сверить число людей, мест и порций, список исключений, связи подарков/отелей. Не менять вместимость молча для прохождения миграции.
- Гостевые ссылки либо сохраняются через безопасное сопоставление с прежней областью доступа, либо заменяются с явно подготовленным процессом повторной выдачи. Ссылка семьи не получает доступ к другим семьям.

### Мероприятия и тайминг

- Существующей свадьбе назначить основное мероприятие, сохранить даты/пояс; не дробить автоматически по названию блока.
- Существующие ID событий сохранить; новые ID генерировать только при добавлении. Добавить version/revision на согласованном уровне и журнал изменений.
- Операция принимает ожидаемую версию. Устаревшее редактирование возвращает конфликт и текущий снимок; UI предлагает перечитать/сопоставить изменения.
- Время хранить с однозначной интерпретацией, соблюдать действующий формат API. Локальную дату дня определять в часовом поясе мероприятия; проверить переход суток и летнее время для поддерживаемых регионов.
- Зависимости не допускают циклов. Превышение длительности, пересечение ресурса и нарушение fixed-блока показывать до записи.

### Деньги, смета и покупки

- Использовать текущие целочисленные минимальные единицы и код валюты, проверять переполнение и отрицательные значения по смыслу операции. Float для денег не вводить.
- Компонент цены имеет состояние известности, источник, единицу, количество, ставку и включение в итог. Способ округления документировать в основном контракте.
- Не смешивать прогноз, согласованную сумму и фактическую отметку оплаты. Сценарный расчёт не меняет сделку.
- Покупка/сделка/ручной расход получают явную связь, исключающую двойной учёт. Миграция ручных строк не должна выдумывать оплаченность.
- Согласованная редакция предложения и договора неизменяема; новое условие — новая версия с отдельным подтверждением.
- Залог разделять на обязательство выдать, выдано, возвращено и удержано. Отрицательные «расходы» не использовать как неявный универсальный возврат.

### Ресурсы и документы

- Ресурс принадлежит подрядчику/компании; назначение связано с заказом и временным интервалом. Исключающие ограничения либо сериализованный доступ держат конфликт под нагрузкой.
- Персональные внешние календари хранить с закрытым токеном доступа, минимальным импортом данных и источником записи. Версия импорта не перезаписывает ручное изменение без правила разрешения конфликта.
- Документ, файл и согласование — разные сущности/состояния. Хранить hash файла, версию, авторство, области доступа, историю отзыва и замены согласно политике.

### Миграционная процедура каждого этапа

Expand → backfill → сверка → совместимое чтение → переключение → отложенный contract/cleanup. Длительные операции выполнять порциями с checkpoint и возможностью безопасного повтора. Двоичную запись использовать только при чётком владельце истины и проверке расхождений. На реальной базе не выполнять разрушительный rollback ради галочки up/down/up.

## 6. Согласованность и безопасность

- Повторная проверка роли внутри критической транзакции: роль могла быть снята после первоначального запроса.
- Предсказуемый порядок блокировок по текущему ядру брони и финансовым модулям. Обязательно протестировать accept против ответа, удаления пакета, отмены свадьбы и удаления аккаунта.
- Idempotency-Key scoped по пользователю/свадьбе/операции, payload fingerprint, устойчивый результат повторной попытки; разные тела под одним ключом получают конфликт. Не записывать неуспех как навсегда завершённую успешную команду.
- Событие изменения и исходящее уведомление фиксируются в одной транзакции через outbox или эквивалентный существующий механизм. Отправка после commit; повторный worker не создаёт дубль, изменение/отмена делает устаревшую отправку недействительной.
- Производные сводки используют единые сервисы, не локальные копии расчётов бюджета/гостей. Кэш включает версию/область доступа и инвалидируется по событию.
- Гостевые токены случайные, ограничены областью, отзываемы и имеют срок по политике; не логировать полные bearer-ссылки. Не включать приватные страницы в публичную индексацию и аналитику с токенами.
- Секреты интеграций — существующий secret/env-механизм; не Git, не клиент и не текст ошибки. В журнале маскировать телефоны, токены, платёжные документы и чувствительные примечания.
- Отключённый/удалённый участник теряет доступ к API, websocket, файлам и запланированным отправкам. Экспорт и удаление охватывают новые сущности и вторичные хранилища.
- Тиль получает только авторизованный контекст. Модель не выбирает tenant/role; сервер валидирует предложенную команду, версию и права заново при подтверждении. Документы и сообщения — данные, а не инструкции исполнителю.

## 7. Внешние интеграции и отказоустойчивость

### Файлы

Реализовать выдачу ограниченного upload URL, временную область, завершение загрузки и проверку объекта перед публикацией. Проверять разрешённый тип по содержимому, размер, квоту, вредоносное содержимое по принятому процессу; очищать метаданные там, где они могут раскрывать координаты. Файл не становится публичным по факту загрузки. Скачивание документов — после авторизации с короткой ссылкой. Удалять незавершённые загрузки по политике. Окончательный список типов/квот согласовать с действующими ограничениями, не обещать безлимитное видео.

### Уведомления

Настроить существующий SMS-адаптер и VAPID, затем добавить требуемые гостевые каналы. Для каждого канала хранить capabilities: наличие delivery receipt, read receipt, лимитов и стоимости. Сетевой 200 провайдера не является доставкой человеку. Таймаут, backoff с jitter, ограниченные повторы, очередь проблемных отправок, дедупликация и операторская диагностика обязательны. Ручная альтернатива доступна при отказе интеграции.

### Подписка

Выбрать провайдера перед платным выпуском. Проверять подпись webhook по официальному контракту выбранного провайдера, replay, идентификатор события, валюту и сумму заказа; состояние сверять сервером. Возврат/chargeback и задержанный callback обрабатывать идемпотентно. Не выдавать права по возврату браузера с checkout.

### Календари, карты, погода

Первый календарный этап может использовать ICS import/export с указанием последней синхронизации. OAuth и двусторонняя синхронизация — отдельный адаптер с отзывом доступа. Внешний календарь не источник истины для подтверждённой брони. Погода/ETA имеют timestamp, источник, ошибку и fallback; ручные значения подписываются как ручные. Внешние URL не загружать произвольно сервером: защита SSRF и ограничения исходящих запросов при появлении такого функционала.

| NFR-007 | Предлагаемая цель стенда: p95 чтения ключевых списков ≤800 мс, записи без внешнего провайдера ≤1500 мс при 50 активных сессиях; 5xx от приложения = 0 за 15-минутный контрольный прогон. Указать железо, объём БД, профиль запросов и отдельно гонки; не распространять результат на неизвестный production |
| NFR-008 | Наблюдаемость: correlation ID, доля ошибок/конфликтов, очередь/возраст уведомлений, отказ интеграций, резервные копии; тревоги не содержат PII |
| NFR-009 | Предлагаемые цели пилота RPO ≤24 ч и RTO ≤4 ч; подтвердить восстановлением в отдельную среду с файлами и БД. Не принимать только наличие дампа |
| NFR-010 | Права и данные: полный цикл экспорт/стирание/архив с файлами, фоновыми заданиями и отключёнными пользователями; сроки хранения утверждены перед сбором новых категорий данных |
| NFR-011 | Проверки выпуска: текущие генераторы, типы, lint, сборки, все интеграционные тесты с PostgreSQL/Redis и браузерные сценарии; реестр skipped пуст для обязательных gates |
| NFR-012 | Совместимость: актуальные iOS Safari/PWA и Android Chrome на физических устройствах, desktop Chrome; версии и результаты фиксируются в отчёте, поведение push не выводится из headless-теста |

## 9. Сквозная приёмка и выпуск

Использовать SC-001–SC-018 из spec. Минимальный набор fixture-свадеб: без даты; короткая подготовка; внешние подрядчики; семейные приглашения с детьми; два дня; разные часовые пояса; отменённая; состоявшаяся; ограниченный координатор; компания с сотрудниками. Это синтетические данные, не копия production.

Каждый этап: контракт/миграции → серверные проверки и гонки → UI/error states → интегрированный browser flow → документация. Полный regression проводить на итоговом SHA, повторять после изменения прикладного кода, не после одной правки prose без необходимости.

Пилот: как предлагаемая выборка — 3 пары, 5 подрядчиков разных профессий, 1 координатор и 10 гостей, включая пользователей без установки приложения. Числа — план набора, не существующая аудитория. Каждый проходит релевантный сценарий; фиксируются завершённость, препятствия, время и обращения за помощью. Любая потеря/утечка данных, двойная бронь или ложная оплата блокирует расширение пилота. Проблемы UX получают приоритет и владельца; не подменять качественное исследование процентом готовности.

Feature flags: серверные, с отдельным fallback для чтения старых данных. После выключения записи документы и подтверждённые договорённости остаются доступны по правилам. План отката проверять до выкладки: предыдущая версия должна читать расширенную схему; разрушительная миграция требует отдельного окна и восстановления.

Release report: SHA, набор включённых WP, версии схемы/контракта, ссылки CI/browser/device evidence, миграционные сверки, известные ограничения, внешние конфигурации без секретов, rollback и наблюдение после запуска.

## 10. Решения перед соответствующим выпуском

| Вопрос | Предлагаемое умолчание для проектирования | Когда зафиксировать окончательно |
|---|---|---|
| Хранение чеков/сканов/фото | Приватное объектное хранилище, временная область, квоты; существующий DB receipts учитывать при миграции | WP01/WP07 до включения загрузки |
| Каналы гостям и расходы | Ссылка/встроенная информация + доступный настроенный канал; платный fallback выключен без лимита | WP10 |
| Тарифы пары/подрядчика | Конфигурируемые продукты и права, никаких выдуманных цен в UI | WP11 до приёма денег |
| Сроки хранения и доступ поддержки | Минимальные данные, доступ по основанию, сохранение согласно утверждённой политике | WP01/WP07/WP15 |
| Возврат залога/оплаты | Ручной учёт с источником; не обещать фактический банковский возврат | WP12/WP13 |
| Новые роли/доступ к деньгам | Существующие права без расширения по умолчанию | WP06/WP09/WP14 |

Эти решения не препятствуют публикации плана. Они не считаются ответами владельца только потому, что предлагаются в документе.
