# Спека: Хвосты ревью старого кода — схема, вход, лимиты, рейтинг, контракт

**Папка:** tasks/фичи/005-хвосты-ревью · **Заведена:** 2026-09-11 · **Статус:** сделана 2026-09-12 (итог — `tasks.md`)
(вопросы В1–В8 и ответы — `plan.md` §«Решения»)

## Зачем

Ревью всего старого кода (149 находок) и два раунда ревью фиксов закрыли всё, что закрывается кодом без смены схемы и
без решений о продукте. Осталось то, где честное решение — миграция (стоп-условие) или выбор владельца: чат своего
подрядчика живёт на слоте, а не на сделке; автобус считает записи, а не людей; отзыв гостя привязан к ссылке, а не к
гостю; удалённый аккаунт при повторном входе получает SMS и 401; чужой номер можно заблокировать пятью запросами;
три гостя одной свадьбы дают подрядчику «5,0». Каждая из этих дыр сейчас прикрыта обходом в обработчике — обход
работает, но правило живёт не там, где должно (CLAUDE.md §5 п. 11: инварианты — в базе).

## Границы

**Входит:** семь миграций (четыре из ревью, три прежних хвоста); восстановление или отказ при повторном входе
удалённого; лимиты входа по номеру и адресу; порог показа рейтинга; контракт v0.29.0 с полями, которых не хватало
экранам; продуктовые мелочи по выбору владельца; мёртвый генератор шаблонов.

**Не входит:** внешние службы (SMS, Redis, S3, VAPID, платежи — `RELEASE-BLOCKERS.md` №1–6); стенд; Turnstile без ключа.

## Истории

### US1 — Схема держит правила сама (P1) 🎯 MVP

**Как** владелец, **я хочу**, чтобы чат своего подрядчика, места в автобусе, отзыв гостя и пакет сделки держались
ограничениями базы, **чтобы** ни один новый путь в коде не мог их обойти.

Сценарии приёмки:
1. Дано: пара убрала своего подрядчика А любой кнопкой и позвала Б — тогда у Б новый чат, у пары в списке два чата
   (А — закрытый, Б — живой), Б не видит ни одной реплики А, и это гарантирует уникальный индекс по сделке.
2. Дано: автобус на 20 мест, 19 гостей «с +1» — тогда счётчик `taken` показывает 38, двадцатый «с +1» получает
   «мест нет», и это считает триггер, а не обработчик.
3. Дано: гость оставил отзыв, пара перевыпустила ему ссылку — тогда отзыв остаётся тем же и второй не заводится,
   потому что ключ — гость, а не токен.
4. Дано: бронь по пакету — тогда сделка помнит пакет, и кабинет показывает, что именно продано.

### US2 — Повторный вход удалённого (P1)

**Как** человек, удаливший аккаунт и передумавший в течение 30 дней, **я хочу** войти тем же номером и получить
свои данные обратно (либо услышать отказ до траты SMS), **чтобы** не получать код и 401 следом.

### US3 — Чужой номер нельзя заблокировать (P1)

**Как** пара, **я хочу**, чтобы посторонний не мог пятью запросами кода закрыть мне вход на час, **чтобы** вход
работал, даже если кто-то знает мой номер.

### US4 — Рейтинг не накручивается тремя гостями (P2)

**Как** пара, выбирающая подрядчика, **я хочу**, чтобы число в каталоге появлялось только после отзывов пар,
**чтобы** «5,0» не было результатом трёх приглашённых гостей одной свадьбы.

### US5 — Экраны получают то, чего им не хватало (P2)

Гость видит свою бронь отеля и считает «свадьба прошла» по её поясу; пара видит комментарий гостя из RSVP;
системная запись в чате помечена сервером, а не угадывается по тексту; сдвиг тайминга честно называет, кому ушло.

## Требования

- **FR-001** Миграции — по одной на изменение, каждая обратима (`down`), каждая с тестом на живой базе; `npm run
  migrate up` проходит на пустой базе (проверка — на стенде, №22).
- **FR-002** `chats.deal_id` для `kind='external'`, уникальный индекс по сделке; заполнение существующих строк
  текущей сделкой слота; старый индекс по слоту снимается; обработчики ищут чат по сделке.
- **FR-003** Триггер `bus_seat_counter` считает `1 + plus_one` и пересчитывает при смене `plus_one`; `CHECK taken
  BETWEEN 0 AND seats` остаётся; обходная проверка в обработчике снимается.
- **FR-004** `reviews.guest_id` (FK → guests, ON DELETE SET NULL), уникальный индекс `(guest_id, vendor_id)`,
  заполнение по `guests.rsvp_token`; ключ `guest_token` остаётся для совместимости чтения, но не участвует в
  уникальности; перенос токена при перевыпуске становится лишним и снимается.
- **FR-005** `deals.package_id` (FK → vendor_packages, ON DELETE SET NULL); бронь сохраняет пакет; кабинет и
  карточка сделки показывают название пакета.
- **FR-006** Прежние хвосты: `CHECK` на `complaints.resolution` по цели; `CHECK (file_url LIKE 'https://%')` на
  `vendor_verifications`; частичный уникальный индекс «одна `pending`-заявка на подрядчика».
- **FR-007** Повторный вход удалённого — по решению владельца: восстановление (`deleted_at = null`, запись
  `user.restored` в аудит, согласие спрашивается заново, если было отозвано) или 409 `account_deleted` в `POST
  /auth/otp` до отправки SMS.
- **FR-008** Лимиты входа: по паре «номер + адрес» — 3 кода в час; по номеру — 10 в час и 30 в сутки; по адресу —
  как сейчас; пять неверных попыток гасят код, но следующий код доступен через 60 с; ключ ограничителя на гостевых
  путях — по адресу с повышенным лимитом (токен гостя не подписан).
- **FR-009** Порог показа рейтинга — по решению владельца: три отзыва пар (гостевые входят в среднее после порога)
  либо как есть.
- **FR-010** Контракт v0.29.0: `myHotelId` в `GET /join/{t}/hotels`; `tz` в `GET /join/{t}/team` и
  `WeddingPublic`; `comment` гостя в `Guest` для пары; `Message.system: boolean`; `guestsAffected` вместо
  `notifiedGuests` в ответе сдвига (старое поле остаётся до следующей версии); `blocked` в анкете подрядчика;
  `GET /users/me/push-subscriptions`; тело 202 у рассылок; генераторы в том же коммите.
- **FR-011** Продуктовые мелочи — по выбору владельца (см. `plan.md` §«Решения», вопрос 6).
- **FR-012** `gen-templates.mjs` удаляется (стоп-условие — после «да»), `templates.generated.ts` переименовывается
  в `templates.ts` и правится руками; тест `stage2` держит соответствие категорий справочнику.
- **FR-013** Каждое изменение — с регрессионным тестом, красным без него; карты и словарь — в той же итерации.

## Критерии успеха

- **SC-001** Ни одного обхода «инвариант в обработчике» из списка FR-002…FR-006 не остаётся: правило проверяется
  базой, тест ломает его напрямую SQL и получает отказ.
- **SC-002** Прежний сценарий «А → Б в одном слоте» проходит через все двери отмены без единого чужого сообщения.
- **SC-003** Посторонний с чужим номером и одним адресом не может закрыть жертве вход дольше чем на минуту.
- **SC-004** `init.sh` exit 0; полные наборы зелёные; контракт v0.29.0 без расхождений с обработчиками (`audit14`).

## Сущности

Чат (`deal_id`), маршрут (`taken` по персонам), отзыв (`guest_id`), сделка (`package_id`), пользователь
(`deleted_at`, восстановление), код входа (счётчики по номеру и адресу), рейтинг (порог), контракт v0.29.0.

## Допущения

- **A1** Миграции не откатывают данные: заполнение существующих строк — частью `up`, обратимость — снятие колонок и
  индексов без потери прежних полей.
- **A2** Восстановление удалённого — только пока строка не стёрта (30 дней); после стирания вход заводит новый
  аккаунт, как сейчас.
- **A3** Turnstile/капча — отдельное решение с ключом; в этой фиче — только серверные лимиты.
- **A4** Стенд для миграций на пустой базе (№22) — по-прежнему за владельцем; локально миграции накатываются на
  живую базу `tili`.
