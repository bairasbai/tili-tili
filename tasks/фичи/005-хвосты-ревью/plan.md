## Фазы (порядок исполнения после одобрения)

### Фаза 1 — миграции (В1) · ~1 день агентской работы

Каждая миграция — свой файл `1759200000000_…cjs` и далее, `up`/`down`, прогон `npm run migrate up` на локальной
базе, тест на живой базе, который нарушает правило прямым SQL и ждёт отказ.

1. **`chats.deal_id`** (FR-002). `up`: колонка `deal_id uuid references deals on delete cascade`, заполнение
   `update chats c set deal_id = s.deal_id from slots s where c.slot_id = s.id and c.kind='external'` (чаты убранных
   подрядчиков без текущей сделки — по последней сделке слота через `deal_events`), уникальный индекс
   `(deal_id) where kind='external'`, старый `(wedding_id, slot_id)` снимается. Код: `externalChatId(dealId)`;
   `POST …/external` заводит новый чат на новую сделку; список чатов пары показывает закрытый чат прежнего
   подрядчика с пометкой «подрядчик убран». Фильтр по дате из ERR-0219 снимается. **Рекомендация:** делать —
   это единственное место, где ПДн третьего лица держатся на дате, а не на ключе.
2. **`bus_seat_counter` по персонам** (FR-003): триггер на `bus_bookings` (insert/delete) прибавляет
   `1 + plus_one` гостя; второй триггер на `guests` при смене `plus_one` пересчитывает маршрут гостя; `up`
   пересчитывает `taken` для всех маршрутов. Обходная проверка персон в `POST /join/{t}/shuttle` остаётся как
   ранняя 409 (дешевле отката по `CHECK`). **Рекомендация:** делать — экран пары показывает `taken`, и сейчас он
   врёт ровно на число «+1».
3. **`reviews.guest_id`** (FR-004): колонка, заполнение `from guests g where g.rsvp_token = r.guest_token`,
   уникальный индекс `(guest_id, vendor_id) where guest_id is not null`, старый индекс по токену снимается;
   `CHECK reviews_key_matches_source` расширяется: гостевой отзыв требует `guest_id`. Перенос токена при
   перевыпуске (ERR-0234) снимается. **Рекомендация:** делать.
4. **`deals.package_id`** (FR-005): колонка + FK `on delete set null`; бронь пишет; `toDeal` отдаёт `packageName`
   (контракт). **Рекомендация:** делать, но приоритет ниже — без него ничего не ломается.
5. **`CHECK complaints_resolution_by_target`** (прежний хвост): `block/downrank` только для `vendor`, `hide` —
   для `review`. 6. **`CHECK vendor_verifications_file_url_https`**. 7. **`unique (vendor_id) where status='pending'`**
   на заявках. **Рекомендация:** делать все три — код уже ведёт себя так, база лишь закрепляет.

### Фаза 2 — вход и лимиты (В2, В3) · ~0,5 дня

- **Повторный вход удалённого** (FR-007). Вариант А — восстановление: в `verify` `update users set deleted_at =
  null, consent_withdrawn_at = …` только если `deleted_at > now() - 30 days`; запись `user.restored` в `audit_log`;
  если согласие было отозвано — следующий запрос получает 403 `consent_required`, экран показывает согласие заново.
  Вариант Б — отказ: `POST /auth/otp` отвечает 409 `account_deleted` до SMS с текстом «аккаунт удаляется, данные
  сотрутся <дата>»; восстановить нельзя. **Рекомендация: А.** Практика (Telegram, Apple, Google) — окно на
  передумать с восстановлением одним входом; комментарий в коде говорит то же: «человек передумывает чаще, чем
  кажется». Б проще, но превращает «удалить» в необратимое сразу, вопреки обещанию «30 дней».
- **Лимиты входа** (FR-008): выдачи уже лежат в `otp_codes` (номер, адрес, `created_at`) — счёт по `(phone, ip)` берётся из неё без новой таблицы; верхние
  потолки по номеру (10/час, 30/сутки); `Retry-After` во всех 429; на клиенте таймер уже читает заголовок.
  Неверные попытки: код гаснет после пяти, новый код — через 60 с, как сейчас; это не вектор блокировки, если
  выдача кода не ограничена одним адресом. **Рекомендация:** серверные лимиты сейчас, Turnstile — когда будет
  ключ (В3 говорит, нужен ли вообще).

### Фаза 3 — рейтинг (В4) · ~2 часа

## Открытые технические вопросы — решены 2026-09-12

- `chats.deal_id`: чат слота → текущая или последняя своя сделка (`order by (state <> 'cancelled') desc, created_at desc`);
  прежним сделкам слота заводятся свои чаты, реплики переезжают по окнам `[created_at; следующая created_at)` одним
  set-based `UPDATE` (коррелированный вариант шёл минутами — ERR-0246); 86 чатов без сделки (без сообщений) удалены.
- `taken` пересчитан одним `UPDATE … coalesce((select sum(persons) …), 0)`; персоны хранятся в `bus_bookings.persons`
  (каскадное удаление гостя иначе вычитало бы единицу вместо двух); 4 переполненных тестовых маршрута → CHECK `NOT VALID`.
- Порог по парам: 332 анкеты с числом → 287; фикстуры `audit3`/`audit29` получили `couple_reviews_count`, чтобы курсор по
  рейтингу по-прежнему проверялся на несклеенных ключах.
