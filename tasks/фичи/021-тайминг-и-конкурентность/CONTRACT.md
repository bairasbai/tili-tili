# 021 · T002 — контракт идентичности и версии тайминга

Дата: 2026-09-28.

## 1. Aggregate

Одна версия относится ко **всему расписанию свадьбы**, потому что текущая операция редактирования — полная замена/reorder списка.

Новая колонка:

`weddings.timeline_version integer not null default 1`

Инвариант: `timeline_version > 0`.

## 2. Постоянный event ID

- существующий `timeline_events.id` остаётся primary key;
- если PUT содержит известный `id` этой свадьбы — обновляется та же строка;
- новый блок без `id` получает новый `uuidv7`;
- блок, отсутствующий в полном payload, удаляется;
- ID другой свадьбы или уже удалённый ID нельзя «подхватить» — операция должна завершаться конфликтом без раскрытия чужой свадьбы;
- reorder меняет `sort`, но не `id`.

## 3. Что меняет timeline_version

Версия увеличивается только после реального committed mutation:

- успешный полный PUT тайминга;
- Day-X shift, если сдвинут хотя бы один блок;
- перенос даты свадьбы, если дата реально изменилась и вместе с ней переносится/инициализируется тайминг.

Preview `/timeline/autogen` версию не меняет.

## 4. Optimistic concurrency — T005

JSON body существующего `GET/PUT /timeline` сохраняется массивом, чтобы 021 не ломала body-contract без необходимости.

Версия передаётся стандартным HTTP-механизмом:

- GET/успешный PUT возвращают `ETag: "timeline-<version>"`;
- редактирующий клиент сохраняет этот ETag;
- PUT обязан отправить `If-Match` с последним полученным ETag;
- compare-and-swap выполняется под блокировкой строки свадьбы;
- несовпадение → HTTP 409, code `timeline_version_conflict`; сервер ничего не меняет, клиент перечитывает расписание и явно показывает конфликт.

Day-X shift и reschedule являются intent/delta-операциями над актуальным состоянием, поэтому сами не требуют старого snapshot от клиента, но **обязаны увеличивать версию**. Благодаря этому открытый до них full-editor затем получит 409.
