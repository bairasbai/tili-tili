# 021 · T001 — инвентаризация текущего тайминга

Дата проверки: 2026-09-28. База: `main@a9f17aea32351e32b996c3b6246cee629b9ad98b`.

## Фактическая модель до 021

- `timeline_events` существует с этапа 2: UUID `id`, `wedding_id`, название, локация, `starts_at`, `ends_at`, `who`, `icon`, `sort`.
- Этап 5 добавил `outdoor`.
- Фича 009 добавила `for_guests`.
- UUID уже является primary key, то есть новая таблица событий для 021 не нужна.

## Backend

### Чтение

`GET /weddings/{weddingId}/timeline` читает `timeline_events` по свадьбе и возвращает массив, отсортированный по `sort, starts_at`.

### Полная запись

`PUT /weddings/{weddingId}/timeline` принимает весь массив состояния экрана. До 021 обработчик:

1. удаляет **все** `timeline_events` свадьбы;
2. вставляет каждый элемент заново;
3. для каждой вставки создаёт новый `uuidv7()`.

Следствие: поле `id` присутствует и в БД, и в ответе API, но **не является постоянной идентичностью события**. Любое сохранение меняет ID даже у неизменённого блока.

### Автоплан

`POST /weddings/{weddingId}/timeline/autogen` — только preview. Он не пишет БД. Сейчас он проверяет соседние временные пересечения и подставляет исполнителей из забронированной команды.

### День X

`POST /weddings/{weddingId}/timeline/shift` сдвигает будущие события, пишет `timeline_shifts`, уведомляет команду/гостей и защищён idempotency key. Aggregate-version расписания до 021 отсутствует.

### Перенос даты свадьбы

`rescheduleWedding(...)` уже блокирует строку `weddings FOR UPDATE` и переносит время `timeline_events` вместе с датой. Однако отдельной версии тайминга до 021 нет.

## Frontend

- `TimelineDraft` уже содержит `id?: string`.
- Экран `Wedding.tsx` сохраняет список целиком.
- На клиенте есть защита от локального stale state между PUT и refetch (`sent/accepted`), но это не защищает от второго устройства/вкладки.
- Backend до 021 игнорирует присланный `id`, поэтому клиент физически не может сохранить идентичность блока.

## Подтверждённые дефекты, которые закрывает 021

1. **Нестабильный ID** — любой PUT меняет UUID всех блоков.
2. **Lost update** — два клиента могут последовательно сохранить полный список, и более поздний PUT молча затрёт более свежий.
3. **Сдвиг/перенос даты не видим для stale editor** — после Day-X shift или reschedule старый открытый экран может записать старые времена обратно.
4. `who` сейчас свободный текст, зависимости отсутствуют, fixed/flexible семантики нет, travel/buffer как сущностей нет.

## Что не строим заново

021 расширяет существующие `timeline_events`, `/timeline`, `/timeline/shift` и существующий экран. Параллельную систему расписания не создаём.
