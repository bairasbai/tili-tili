# План WP03

1. Зафиксировать baseline полного main и воспроизвести потерю ID/устаревшую запись до исправления.
2. Основная модель: постоянные timeline_events, версия программы, автор/время; изменения в единственном контракте. Не заводить вторую модель тайминга.
3. Сохранение: блокировка контекста свадьбы, проверка исходной версии и принадлежности всех ID до изменений; upsert существующих и создание новых; удаление только отсутствующих в снимке.
4. Учесть все существующие способы изменения timeline_events, включая создание свадьбы, перенос даты, сдвиг дня X и план Б. Они тоже инвалидируют версию/ознакомление.
5. Добавить зависимости, fixed и область сдвига, duration/buffer/travel и разрешённые назначения. Preview и confirm проверяют права и версию заново.
6. UI сохраняет исходную версию, подтверждённый сервером список и черновик при отказе. Конфликт не повторяется автоматически поверх чужих данных. Использовать существующие API, i18n и дизайн-токены.
7. Ознакомление подрядчиков: текущая версия и разрешённая программа, отзыв доступа, новое ожидание после изменения.
8. Offline: чтение снимка с давностью и очистка после отзыва прав; отсутствие сети не подтверждает запись.
9. Миграционный drill с прежними данными, targeted/полный gate, browser flow двух сессий и мобильные ширины; карты экранов/кнопок и REPORT.
10. Только после полной приёмки WP03: отдельный feature-коммит, push и интеграция main. Незавершённый код не выдавать за завершённый пакет.

## Протокол T003

- Чтение текущего массива сохраняется для существующих читателей; сервер отдаёт ETag исходной версии. Редактор получает согласованный снимок с версией, автором/временем и блоками.
- PUT требует исходный If-Match. Отсутствие версии не разрешает legacy-обход: 428; устаревшая версия — 409 timeline_conflict без мутаций или рассылки.
- Проверка версии и запись выполняются в одной транзакции под замком свадьбы. Каждый путь изменения timeline_events меняет серверную версию, включая перенос даты и сдвиг.
- Миграция не придумывает автора/время исторических изменений: неизвестная метка остаётся null; после реального изменения появляется фактическая метка.
- Версия — монотонный серверный счётчик изменений, не количество пользовательских сохранений. Автор устанавливается из аутентифицированного контекста, не из присланного тела.
- Клиент хранит версию конкретного снимка, а не общий «последний ETag свадьбы»: чужое фоновое чтение не может разрешить запись старого списка.
- ETag и X-Timeline-Updated-At/By привязаны к одному согласованному чтению. Snapshot API клиента возвращает также заголовки; экран переводит подписи RU/EN, сопоставляет ID с именем из members и не подменяет неизвестную историю.
- После ожидания замка повторяются проверки живого аккаунта/сессии, текущей роли и состояния свадьбы. Отрицательный witness отзыва членства в этот момент записан до исправления.

## Модель T005

- Поля блока: durationMinutes (nullable, можно задать до времени старта), fixed, travelMinutes и bufferMinutes. Место остаётся существующим location. Все минуты — явный ввод, без обещания расчёта маршрута. Инженерный предел отдельного интервала: 10080 минут; сохраняется точная длительность существующих корректных startsAt/endsAt, без округления исторических данных.
- При известном старте длительность и endsAt согласованы. Явная длительность вычисляет endsAt; противоречивые start/end/duration отклоняются. Без старта endsAt отсутствует, длительность может быть задана отдельно. Fixed означает явную метку старта; автоматический shift не меняет этот блок.
- Зависимости — список постоянных ID. Самоссылка, цикл, чужой/неизвестный ID и ID удалённого из предлагаемого полного списка блока отклоняются до записи. DB FK ограничены одной свадьбой, constraint-trigger защищает граф от циклов и через SQL.
- Ответственный и участники — ссылки вида {kind: member|guest|deal, id}. Это включает команду, реальных гостей/персон и забронированного своего/каталожного подрядчика без требования аккаунта. Один ответственный, участники без дублей; финансовые поля в ссылки не входят.
- Удаление персоны/членства/сделки очищает назначения через FK; soft deletion аккаунта и отмена сделки тоже снимают назначения. Изменение relations инвалидирует версию программы, чтобы прежний список не восстановил отозванные ссылки. Проверяется под тем же wedding lock и FK.
- Planning-references возвращаются только в полном team API; гостевой /join/day не получает внутренние ID назначений и граф. Existing who остаётся отдельным legacy-текстом, не основанием для прав/назначений.
- Полная запись по-прежнему требует ETag. Все UI-пути (добавление, удаление, галочка, автоплан, редактор блока) сохраняют planning metadata. T006 добавит scoped preview/confirm и проверку зависимостей/временных конфликтов при сдвиге; T005 не считается полной приёмкой FR-039.

## T006: Источник Времени И Расчёт

- Первая дата использует template_start/template_day_offset, записанные непосредственно при создании постоянного блока; sort/имя/текущий format больше не источники времени. Для исторического/custom origin без доказательств остаётся NULL; explicit unknown duration не получает выдуманное окончание.
- Pure previewTimelineShift принимает server-resolved day/event scope и полный авторизованный снимок. Проверяет future/fixed/day, зависимости, участников/ресурсы, manual travel/buffer и неизвестные интервалы; возвращает последствия без мутаций. Это промежуточный модуль, не реализация HTTP preview/confirm.
- Реальная модель мероприятий/tenant-safe связь и версия/context lock реализованы промежуточным этапом (REPORT-EVENT-MODEL.md): одно main для истории, реальные date/tz/location, eventId в GET/PUT/autogen/черновиках, event API с If-Match и access recheck. UI управления/индивидуальные приглашения WP04 этим не закрыты.
- Canonical vendor resource reader, actual day/event scope, idempotent versioned HTTP confirm и /dayx Dialog теперь подключены (REPORT-SHIFT-HTTP.md). Legacy shift больше не альтернативная команда. Server recheck включает actual clock, user/session/version и digest; ledger/notifications/receipt атомарны. Координатор исправляет конфликт обычным редактором и получает новый preview, override отсутствует.
- T006 всё ещё требует human-readable effects, полных интервалов и связи с event invitees/transfers; существующий wedding RSVP/explicit guest refs не заменяет персональные приглашения WP04. T007–T011 и весь исходный scope остаются обязательными.
- Проверенные результаты и остающееся: REPORT-SHIFT-CORE.md. Весь исходный scope WP00–WP16 неизменён.

## T008: Основной DayX

- Известный active interval: start <= now < end; показывать все параллельные,
  не выбирать последний sort. Next — ближайший будущий instant. Отсутствующий
  end/пояс не восстанавливать по соседям/браузеру/главному мероприятию.
- Для eventId требовать одинаковый ETag timeline/events перед отображением
  локальных часов и имени. Несовпадение означает неизвестный контекст, явное
  перечитывание не меняет captured preview/version сдвига.
- Старый offline не LIVE и не получает текущий context; полноценный snapshot
  с version/access cleanup остаётся T009. Evidence — REPORT-DAYX.md, не весь T008.

## T006–T008: Читаемые Captured Последствия

- Имена блоков/мероприятий/назначений, известные интервалы и guest names читать
  сервером в авторизованном снимке, включать в digest, не подставлять из
  обновляемого родительского списка. Preview field scope не заменяет свой
  timezone каждого отображённого блока.
- Сравнение конфликта: AFTER moved против captured unchanged. Не выводить
  неизвестные имена из телефонов или unknown end из соседей. Минимальные
  projections, без финансов/контактов; старый incomplete response не confirm.
- Manual travel/buffer timestamps — плановые начала блока, не фактический
  рейс/прибытие. Event invitations/реальные transfers ещё обязательны.
- Контракт 0.57.0 генерируется штатно; verification/history — REPORT-EFFECTS.md.

## T007: Версия Разрешённого Снимка

- Зарегистрированному владельцу анкеты выдавать только назначенные блоки его
  committed deals; hidden IDs/private fields не включать в projection/digest.
- GET read-only; captured version/content/user/session proof, explicit ack под
  wedding lock с live access/expiry recheck. Natural uniqueness/history+audit
  atomic, новая редакция или владелец не наследуют прежнее ознакомление.
- Legacy update ack не считать новым programme ack. API0.58.0 генерировать
  штатно; migration history/rollback и full tests — REPORT-PROGRAM-ACK-HTTP.md.
- После server foundation actual UI/RU/EN/browser, обратная видимость команде,
  разрешённые external/delegated actors и offline lifecycle остаются обязательны.
