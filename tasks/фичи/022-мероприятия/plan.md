## Следующая Поставка: Состав Приглашённых
FR-027/030/035: дополнительные мероприятия имеют явный набор персон, не семейный boolean и не автоматическое приглашение всем. Основная программа остаётся переходно доступной прежним гостям; RSVP/токены/семейная идентичность не перезаписываются. Решение о едином сроке события записано в spec; дедлайн и отдельные ответы остаются следующей поставкой, не активируются без полного сценария.

1. Добавочная `guest_event_invitations`: составные FK свадьба/мероприятие и свадьба/персона, запрет main-строк, блокировка свадьбы и существующий revision trigger. Down отказывается от populated roster. Удаление персоны чистит только её приглашения; удаление мероприятия с приглашёнными получает event_in_use.
2. GET/PUT `/weddings/{weddingId}/events/{eventId}/invitations`: только couple (персональные данные), общий ETag; PUT полного набора с If-Match, отказ дублей/чужих персон/event, атомарность. Свежие lockGuestReadAccess/lockSeatingAccess и финальная проверка JWT.
3. `/rsvp/{guestToken}` читает одним закреплённым снимком wedding/party/персон, проверяет токен снова после ожидания. `events[]` только main и явно приглашённые дополнительные события; guestIds только люди своей семьи. Нет полного roster/контактов/бюджета/чужих ответов. Legacy ответ не становится ответом на новое событие.
4. `/wedding/events/:eventId/invitations`: snapshot имени события/доступных персон/selected IDs, checkbox-персоны, captured version/draft, конфликт/неясный исход блокирует повтор до явного свежего снимка. Guest Invite показывает разрешённые события/персон; старый RSVP явно «Ответ на основную программу».
5. Permanent tests + actual migration/SQL/role/privacy/race verification, full init.sh fresh PG/Redis, actual production Chromium, карты/report/publication. Core master originals не менять. Нарушений CLAUDE §5 не планируется.

## После Состава: Отдельный RSVP И Deadline
Следующая реализация сохраняет legacy main ответы как main-only, без автоприсвоения
yes дополнительным событиям. Новый ответ и право писать проверяются по person/event
приглашению в той же транзакции. Снятие приглашения/смена срока/отзыв ссылки во
время ожидания не разрешают запись по старой проверке. Каждый основной логистический
побочный эффект старого RSVP (место/семейный номер) должен остаться main-only;
дополнительный ответ не удаляет основной трансфер/бронирование и не меняет main yes.

Утверждённый срок = nullable calendar date общего мероприятия, не per-party.
Граница закрытия = начало следующего календарного дня по IANA-поясу события,
а не UTC-23:59:59 и не фиксированные24часа после начала дня. При отсутствии
срока ответ открыт; отсутствие зоны не выдаётся за московскую зону. Проверять
DST/разные UTC offsets, край конца дня, изменение зоны/дедлайна и реальный
lock wait, а не только mocked clock. После срока сохраняется отдельное обращение
организатору без изменения принятого ответа; правка пары имеет provenance.
UI пары/гостя должен показать реальные ответы/сроки/закрытие/обращение и сохранить
черновик при отказе; отдельный контракт/migration/UI/report/full/browser/publication.
