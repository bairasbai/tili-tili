## Реализация

Контракт OpenAPI 0.70.0, 6 операций, коммит `0da3e23`. Миграция
`backend/migrations/1763700000000_event_rsvp_deadlines.cjs`:
`wedding_events.rsvp_deadline` под двумя CHECK (срок только у дополнительного
события с известным поясом; срок ≤ дата мероприятия), `event_guest_participation.source`
+ `organizer_correction` (пишет только couple), новая `event_rsvp_requests`
(составной FK на `guests(wedding_id,id,party_id)`, частичный уникальный индекс
одной ожидающей просьбы, неизменяемость триггером, без `BEFORE DELETE`-стража).
Единая `rsvpWindow` в `backend/src/wedding/rsvp-events.ts`: нет срока → `none`,
иначе закрытие — начало следующих суток по IANA-поясу через
`fromLocal`/`localDayBounds` (`backend/src/notify/quiet.ts`); неизвестная/невалидная
зона — 422 без подстановки Москвы. Все пишущие пути — одна транзакция: замок
свадьбы → повторная проверка токена/семьи/сессии/роли → приглашение в
ростере → мероприятие (не main, существует) → срок по текущим данным →
версия → запись → аудит.

Фронт: `app/src/lib/api/eventRsvp.ts` (типизированные обёртки с рантайм-проверкой
формы), гостевой блок «Ваши мероприятия» на `app/src/pages/Invite.tsx` — один
список (решение D5): основное мероприятие — информационная карточка со ссылкой-якорем
«Ответ на основную программу ↓», дополнительные — карточки `AdditionalEventsList`/
`GuestEventRsvpCard` со сроком, переключателем «Приду»/«Не приду» по каждому
человеку до срока и формой просьбы организатору после. Новый экран пары
`app/src/pages/EventRsvp.tsx` (`/wedding/events/:eventId/rsvp`), вход — ссылка
«Ответы» в строке мероприятия на `app/src/pages/WeddingEvents.tsx`: срок,
список приглашённых с источником ответа, правка ответа парой, решения по
просьбам. Полная карта экранов/кнопок — `Тили-тили_Карта_экранов.md`,
`Тили-тили_Карта_кнопок.md` (журнал T012).

## Независимое Ревью (Opus) И Фиксы

Для обоих P1-находок есть тест, который падал до фикса и проходил после.

- **P1-1.** Каскадное удаление гостя/члена семьи/+1 (legacy `POST /rsvp/token`
  с `plusOne:false`) или дополнительного мероприятия с живой просьбой падало
  500: прежний `BEFORE DELETE`-страж на `event_rsvp_requests` не отличал
  легитимный `ON DELETE CASCADE` от прямого удаления строки, которого в коде
  нет нигде. Страж снят, неизменяемость по `UPDATE` осталась; удаление
  события с существующими просьбами по-прежнему получает `409 event_in_use`
  на уровне API мероприятий, не каскадом БД.
- **P1-2.** Решение по просьбе гостя (`decideRequest`) строило профиль
  персоны join'ом по действующему ростеру мероприятия — если пара снимала
  приглашение между просьбой и решением, join ничего не находил, вся функция
  404-илась и откатывалась в одной транзакции, и просьба навсегда оставалась
  `pending`. Профиль теперь строится по «гость этой свадьбы», приглашение
  проверяется только там, где от него зависит сам результат записи.
- **P2 (401-оракул).** `PUT …/rsvp/{guestId}` с чужим `guestId` отдавал 401
  вместо 404 — единственное место, где код ответа отличал «есть, но чужое» от
  «нет вовсе». Выровнено на 404, как у остальных чужих ресурсов этого API.
- **P2 (срок в CHECK).** Срок ≤ дата мероприятия перенесён из обработчика
  `PATCH` в CHECK базы — прямая правка в обход API тоже защищена.
- **P2 (усиление тестов).** Реальная запись-с-откатом, настоящие ожидания
  блокировки через `pg_blocking_pids`, переворот часового пояса, полная
  изоляция ответов по отелю/столу/меню/основной программе от ответов на
  дополнительные мероприятия.
- **P3 (чтение гостя).** `GET` по гостевому токену берёт `for share`, не
  безусловный `for update` — иначе `GET /rsvp/{token}/events` держал
  эксклюзивный замок семьи до конца транзакции, и два члена семьи не могли
  одновременно открыть список мероприятий.
- **P3 (DST на полуночи).** `fromLocal` получил второй проход коррекции
  смещения: переход летнего/зимнего времени ровно на местной полуночи
  (пример — America/Santiago) приземлял однопроходный результат уже по ту
  сторону перехода и уводил момент на величину скачка.
- **P3 (down-тест).** Тест отката миграции всегда выполняет настоящий
  `ROLLBACK`, не оставляет БД в откаченном состоянии.
- **P3 (согласованность party).** Составной FK `guests(wedding_id,id,party_id)`,
  индекс под обратный FK `event_rsvp_request_party`, решённая просьба не
  возвращается в `pending` триггером.

Полный разбор и правило на будущее по каждому пункту — `ERRORS.md`
(LOCAL-030-32…35).
