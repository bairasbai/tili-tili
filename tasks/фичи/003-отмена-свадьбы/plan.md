# План: Отмена свадьбы и архив

**Спека:** ./spec.md

## Ворота инвариантов

Проверено против `CLAUDE.md` §5 и R-01…R-15.

| Инвариант | Что нарушаем | Зачем | Почему нельзя иначе |
|---|---|---|---|
| — | нарушений нет | | |

Пояснения:
- **Стоп-условие «массовые операции с данными».** Уборка архива — плановое удаление по Плану §19.1 и контракту
  («архив на 12 месяцев»), включённое владельцем 2026-09-07 выбором этой фичи; срок — переменная окружения,
  удаляются только отменённые свадьбы старше срока; каждая — строкой журнала.
- **§5.12.** Идентификатор свадьбы на устройстве — свойство устройства (кэш), источник правды — `GET /weddings`.
- **§5.5.** «Отменить» и «Подтвердить» — запрос; «Начать новую» — переход.
- **R-15.** Экран 45 «Отмена свадьбы / удаление аккаунта» — в §20.1, живёт на `/settings`; состояние «отменена» —
  состояние того же экрана, нового маршрута нет.

## Контракт

1. `POST /weddings/{weddingId}/cancel`: ответ `200` → `CancelResult { state: confirmation_required|cancelled,
   requestedBy?: string, cancelledDeals?: integer }`; `403` (`Forbidden` — не пара), `404` (`NotFound`);
   описание: «Отменяются сделки `booked` и `paid_deposit`; `done` остаются; даты подрядчиков освобождаются;
   проект в архиве `WEDDING_ARCHIVE_DAYS` дней (по умолчанию 365), затем удаляется уборкой со всем содержимым».
2. Версия — та же 0.27.0, что у фичи 002 (одна итерация генераторов на обе).

## Хранение

- Отмена: `state = any($2)` → `['booked', 'paid_deposit']` вместо `COMMITTED` (в `COMMITTED` есть `done`);
  **освобождение дат и слотов — только по отменённым сделкам** (сверка C01): `delete from vendor_busy_dates where
  source = 'deal' and deal_id = any($ids)` и `update slots set deal_id = null where deal_id = any($ids)` вместо условий по
  `wedding_id`; события `deal_events` — как сейчас.
- Уборка (`cleanup()`, раз в час), в транзакции: выбрать `id` отменённых свадеб с `archived_at < now() - make_interval(days => $1)`
  **`limit 100`** (партия — как у `eraseDeletedUsers`); для них — `delete from vendor_busy_dates where source = 'deal' and deal_id in
  (select id from deals where wedding_id = any($ids))` (сверка C04: `deal_id` у занятости — `SET NULL`, без этого дата
  подрядчика оставалась бы занятой навсегда); `audit_log` на каждую (`actor_id` null — колонка это допускает, миграция
  `1757100000000_auth_and_geo.cjs:87`; `action = 'wedding.purged'`, `entity = 'wedding'`, `entity_id`, `diff = { cancelledAt, archivedAt }`);
  затем `delete from weddings where id = any($ids)` — каскад снимает участников, гостей, сделки, слоты, чаты, задачи;
  отзывы (`reviews.wedding_id`/`deal_id` — `SET NULL`) остаются (A8); в лог — число за проход.
- Конфиг: `weddingArchiveDays` из `WEDDING_ARCHIVE_DAYS` через `envNumber` (пустое — «не задано» → 365); **нижняя граница 30 и
  целое**: `Math.max(30, Math.round(n))`, иначе `0`/отрицательное/дробное стёрло бы всё или уронило бы `make_interval` и
  весь `cleanup()` (сверка C02); мусор в переменной — предупреждение в лог и значение по умолчанию.
- Фронт: при запуске, если вошёл и `tt_wedding_id` есть, — `GET /weddings` через новую обёртку `listMyWeddings()` в
  `lib/api/wedding.ts` (`findMyWedding()` переписывается поверх неё — сверка C05); идентификатора нет в ответе →
  заменить на свою (роль `couple`) или первую, либо `null`; сеть недоступна — оставить как есть. Пока приложение
  открыто, отмена партнёром с другого устройства доходит при следующем запуске (SC-002).

## Решения

| Решение | Почему | Что отклонили и почему |
|---|---|---|
| проверка помнимой свадьбы при каждом запуске | отмена с другого устройства иначе не доходит до телефона: 404 на всех экранах без выхода | ловить 404 у `GET /weddings/{id}` в каждом экране — десять мест и десять способов ошибиться |
| состояние «отменена» — на `/settings`, без нового маршрута | экран 45 плана; после сброса идентификатора остальное приложение само в состоянии «свадьбы нет» | отдельный маршрут — экран вне списка §20.1 |
| `done` не отменяется | контракт обещает «booked и paid_deposit»; выполненная услуга — не бронь, отменять нечего | оставить как есть — контракт врал бы, подрядчик получал «Сделка отменена» по уже сделанной работе |
| уборка — только отменённых | План §18.5 п. 4: состоявшийся проект хранится бессрочно; §19.1 про 12 месяцев — про отменённые | убирать все архивы — стирать состоявшиеся свадьбы вместе с альбомом |
| срок — переменная окружения | владелец меняет число без кода (`RELEASE-BLOCKERS` №10 — его решение) | константа — правка кода на каждое решение |
| причина отмены не собирается | тела у пути нет; добавить — расширение контракта и продукта | спрашивать причину экраном и никуда не отправлять — «только экран» |

## Открытые технические вопросы

- **Уведомление подрядчикам** идёт из `announceDealEvents` раз в минуту и только при Redis (№2). Синхронное
  уведомление из обработчика дало бы дубль с рассылкой; оставлено как есть, владельцу — №2.
- **Отзыв запроса на отмену** — ERR-0101, отложено владельцем; экран показывает срок 72 часа.
