# 032 · Приватный файловый сервис: фотографии портфолио

Программа: WP01/T005; основа для будущих файлов WP02/WP06/WP07/WP15. Это первый законченный инкремент общего сервиса, а не закрытие всего T005/WP01 или WP00–WP16. Источники: master-plan/plan.md §7, существующий /media/upload-url, План приложения §12.4 (5 фото до10МиБ), текущие правила прав/хранения/отзыва.

## Поставки

032-A содержит только основу: явная конфигурация, приватный S3 transport, ClamD protocol и растровая нормализация. Маршруты не подключены; /media/upload-url сохраняет501. Она не закрывает пользовательский сценарий, T005/WP01 или WP00–WP16. В032-B обязательны все M01–M12, DB99/API/UI/erase/GC и их общая приёмка до включения загрузки.

## Результат032-B

Владелец компании с действующим согласием на права портфолио выбирает JPEG/PNG/WebP, видит реальное состояние загрузки/проверки, добавляет проверенную фотографию и удаляет её. Публикация определяется действующим состоянием анкеты. Без настроенного приватного S3 и сканера новые загрузки честно недоступны; старые внешние ссылки продолжают работать. Видео, гостевой альбом и сканы документов этим инкрементом не включаются.

## Требования

- M01. Допуск — текущий владелец vendor, живая сессия, актуальное согласие и media_rights_at. Resource-manager не получает эти права. Права и JWT проверяются повторно после внешних ожиданий, при конечной операции — под существующим company/principal префиксом. Caller не назначает владельца, storage key, ACL или произвольный URL загрузки.
- M02. POST /media/upload-url принимает vendor_photo, заявленные MIME/байты и Idempotency-Key. Короткий presigned POST ограничивает конкретный случайный quarantine key, тип, точный размер и срок. Клиент получает uploadId/method/fields/expiresAt; fileUrl до проверки недоступен. vendor_video/album_photo/document_scan остаются явно не включёнными.
- M03. Не более5 фотографий; до10МиБ входных байтов. Активные прежние фото и pending/processing reservations считаются под тем же vendor-lock, что PUT /vendor/profile и finalize. Две попытки не обходят лимит; byte limits и identity проверяет сервер, а не MIME браузера. Повтор ключа с иными параметрами —409.
- M04. Объект остаётся в приватном quarantine. Complete получает реальные ограниченные байты из фиксированного операторского S3 endpoint, проверяет точный размер, сигнатуру/заявленный формат, одиночное растровое изображение/размеры/число пикселей, сканирует ClamAV и полностью декодирует/перекодирует Sharp без EXIF. SVG, анимация, повреждённый, подменённый и вредоносный файл не публикуются. Ограничена одновременная обработка и время внешних операций.
- M05. Finalize использует уникальный nonce/lease. Публикуется отдельный immutable clean key; повторная запись по старому POST не меняет готовый объект. Опоздавший worker не публикует объект после нового lease/удаления/истечения/отзыва. Повтор успешного complete возвращает тот же результат.
- M06. Ошибка ответа/COMMIT не удаляет потенциально уже готовый объект. Candidate заранее учитывается в durable cleanup; GC проверяет отсутствие active/current-lease ссылки. Не делать deleteObject в catch как компенсацию неизвестного COMMIT.
- M07. Сохраняется стабильная связь media asset с vendor_media. PUT /vendor/profile не удаляет/пересоздаёт managed ID, если эта фотография остаётся; чужие/удалённые managed URL не принимаются. Прежние внешние ссылки не загружаются сервером и сохраняют прежние правила.
- M08. Доставка clean-объекта через собственный endpoint: owner получает приватный preview после авторизации, остальные — только действующее опубликованное/одобренное/неблокированное портфолио. Raw quarantine, scanner protocol, bucket keys и signed upload grants не попадают в каталог/экспорт. Приватные ответы no-store; MIME/nosniff/CSP не позволяют исполнить содержимое.
- M09. Удаление выводит фото из портфолио атомарно; first-photo обновляется или становится null. Для managed объекта явно возвращается queued deletion, физическое удаление идёт durable worker; при отказе провайдера не объявляется законченным. Старые внешние URL не скачиваются/не удаляются удалённо.
- M10. Каскад eraseUser/удаления vendor сохраняет cleanup keys до удаления metadata. Outbox переживает аккаунт и содержит только необходимые для удаления ключи/сроки/попытки, без JWT, подписанных URL или содержимого. Ограниченные повторы/backoff, явный failed state для оператора. Незавершённые объекты удаляются после окончания upload capability с запасом; active clean объект GC не удаляет.
- M11. Owner export включает свои текущие состояния/даты/размеры/готовую media-ссылку, без secret/object keys/presigned grants. Удаление/отзыв проверяются через реальные DB-пути и гонки, а не только mock.
- M12. UI RU/EN, существующие темы/AsyncState; input, upload, scan, ready, failure, retry и delete показывают реальные состояния. Owner/session generation ограждает поздние результаты и blob URLs; нет применения старой операции к новой учётной записи. Повтор complete после потери ответа не создаёт второе фото.

## Границы включения

Оператор должен предоставить отдельный приватный S3 bucket/политику/CORS и ClamAV. Реальные credentials не запрашиваются в чате и не используются в этой задаче; local synthetic HTTP/TCP fixtures проверяют реальные SDK/protocol boundaries, не считаются приёмкой облака или настоящего antivirus engine. Физические устройства/восстановление БД+S3/реальные provider outage — дальнейшие WP01/WP16 gates. Ни один из них не отмечается PASS по наличию библиотеки.

Собственная логика определяет права/квоты/состояния/публикацию.
