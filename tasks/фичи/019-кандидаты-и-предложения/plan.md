## Ворота инвариантов

Проверено против `CLAUDE.md` §5 и R-01…R-15.

| Инвариант | Что нарушаем | Зачем | Почему нельзя иначе |
|---|---|---|---|
| — | нарушений нет | | |

Как соблюдается то, что здесь легко нарушить:
- **§5.1 R-MAP/R-BTN.** Карты экранов и кнопок обновляются в конце КАЖДОЙ фазы с экранами (T-задачи «карты» в фазах 3, 4,
  5), а не одной задачей в полировке: остановка на MVP не оставит карты позади.
- **§5.11 (инварианты — в базе).** «Не больше трёх кандидатов» — `unique (slot_id, position)` + `check (position between
  1 and 3)`; «один открытый запрос на подрядчика и место» и «одно действующее предложение на запрос» — частичные уникальные
  индексы; согласованность статусов (закрыт ↔ причина ↔ время, принято ↔ сделка) — CHECK; «один исполнитель на место» —
  существующий `slots_deal_unique`.
- **§5.13 / R-178.** Счётчики и занятость — только из ответа; неизвестное — «—»; цена пакета без суммы — «по запросу»
  одной подписью на всех экранах (сейчас их четыре: `app/src/pages/VendorApp.tsx:568`, `Admin.tsx:1476`, `Search.tsx:648`,
  `Discover.tsx:192`).
- **§5.15 / R-174.** Экран не обещает «подрядчик ответит»: «запрос отправлен» и срок, который назвал подрядчик.
- **R-40 / FR-014.** Помощнику и координатору — только факт «ответ получен» (`status`), без цены, названия, состава,
  текста и снимка пакета: цена может стоять в любом из них. Предложения не зеркалятся в чат — координатор читает чаты
  с подрядчиками (`backend/src/chats/access.ts:24-31`).
- **R-311.** Ссылки на `users` — `on delete set null`; на `vendors` — `cascade`: ответы подрядчика — его данные и уходят
  с ним при стирании (152-ФЗ), сделка пары остаётся с ценой и именем (`eraseUser` пишет `external_name`). Тест стирания
  через уборку и через вход (R-311), поиск следов — и в `jsonb`.
- **R-312.** Ключ идемпотентности — на попытку, для запроса, предложения и принятия: живёт до успеха, повтор той же
  попытки после обрыва идёт тем же ключом (как `app/src/pages/PaymentSchedule.tsx:84-89`). База держит не всё: новое
  предложение законно заменяет прежнее (FR-010), и повтор с новым ключом дал бы второе предложение и второе уведомление.
- **R-317.** Порядок замков всех записей 019: свадьба `FOR SHARE` → пользователь `FOR SHARE` → слот `FOR UPDATE` →
  запрос `FOR UPDATE` → предложение → подрядчик `FOR SHARE OF u` → пакет `FOR KEY SHARE`. Ответ подрядчика берёт тот же
  порядок начиная с запроса (свадьбу он не пишет): запрос `FOR UPDATE` → пакет `FOR KEY SHARE`.

## Контракт

Версия 0.46.0 (`backend/test/audit55.test.ts:462`). Каждая правка YAML — в той же задаче с `gen-contract`, `gen-schemas`,
`openapi-typescript` и копией `app/src/lib/api/schema.ts` (инвариант 9). Коды отказа названы у своей операции (audit55
G-c1); операции с `withIdempotency` объявляют `Idempotency-Key` и 400 (G-a). «Анкета недоступна» — один код во всех
операциях 019: 409 `vendor_unavailable` (прежний `…/book` отвечает 404 и не меняется).

| Операция | Кто `[В1]` | Коды |
|---|---|---|
| `GET /weddings/{weddingId}/slots/{slotId}/shortlist` — кандидаты места: карточка, пакеты, занятость `free|held|busy|null`, запрос и предложение (паре — целиком, остальным — `status`) | пара, помощник, координатор | 403, 404 |
| `PUT /weddings/{weddingId}/shortlist/{vendorId}` — в кандидаты места категории подрядчика; места нет — сервер его заводит | пара, помощник | 409 `shortlist_full` (в `details` — нынешние три), `vendor_unavailable`; 403, 404 |
| `DELETE /weddings/{weddingId}/slots/{slotId}/shortlist/{vendorId}` — убрать; открытый запрос закрывается `removed` | пара; помощник — только без открытого запроса | 409 `request_open` (помощнику); 403, 404 |
| `POST /weddings/{weddingId}/slots/{slotId}/offer-requests` — запрос одному–трём кандидатам; итог по каждому (`sent`, `busy`, `already_open`, `unavailable`, `category_changed`) `[В2][В4]` | пара | 201 с итогами; 409 `not_shortlisted`, если не ушло ни одного; 429 `offer_requests_limit` (10 в сутки на свадьбу); 422; 400 ключ; 403, 404 |
| `POST /weddings/{weddingId}/offers/{offerId}/accept` — бронь по предложению, ответ — `Slot` | пара | 409 `offer_expired`, `offer_stale_date`, `offer_superseded`, `request_closed`, `offer_declined`, `slot_taken`, `date_taken`, `vendor_unavailable`; 400 ключ; 403, 404 |
| `GET /vendor/offer-requests` — запросы подрядчику (дата или «не выбрана», гости, город, пожелания, ориентир, если передан, статус) | подрядчик | 403 |
| `POST /vendor/offer-requests/{requestId}/offers` — предложение или отказ `[В5]` | подрядчик | 409 `request_closed`, `vendor_unavailable`; 422; 400 ключ; 403, 404 |
| `PUT /vendor/profile` — `packages[]` по схеме `VendorPackageInput` (с необязательным `id`) | подрядчик | 422 `unknown_package` (чужой `id`) |

Две схемы пакета, а не одна: в ответе `id` обязателен и `price` бывает `null` («по запросу»); на вводе `id` необязателен,
а `price` отсутствует, а не `null` (R-281). `VendorDetail.packages[]` переходит на `VendorPackage`.

## Хранение

Миграция `1761500000000_shortlist_offers` (после `1761400000000`; `pgm.sql`; откат с данными — только с
`tili.allow_data_loss=yes`, как у 018).

```
slot_shortlist   (slot_id → slots cascade, vendor_id → vendors cascade, position smallint check 1..3,
                  added_by → users set null, created_at; pk (slot_id, vendor_id), unique (slot_id, position))
offer_requests   (id, slot_id → slots cascade, vendor_id → vendors cascade,
                  status open|closed, close_reason null|removed|booked_other|booked|wedding_cancelled,
                  closed_at; check ((status = 'open') = (close_reason is null and closed_at is null)),
                  wedding_date date null (снимок), guests int null, city text null, wishes text ≤ 2000,
                  budget_hint bigint null + currency RUB [В2], created_by → users set null, created_at;
                  unique (slot_id, vendor_id) where status = 'open'; index (created_at) для предела 10 в сутки)
offers           (id, request_id → offer_requests cascade, kind offer|decline, package_id → vendor_packages set null,
                  package_snapshot jsonb null, title text, price bigint null + currency RUB, includes jsonb,
                  message text ≤ 2000, valid_until date null, superseded_at, accepted_at, deal_id → deals set null,
                  created_by → users set null, created_at;
                  check (kind = 'decline' and price is null and valid_until is null and accepted_at is null)
                     or (kind = 'offer' and price > 0 and valid_until is not null);
                  check (accepted_at is null or superseded_at is null);
                  check ((accepted_at is null) = (deal_id is null));
                  unique (request_id) where superseded_at is null)
```

Снимок пакета в предложении: правка анкеты после ответа предложение не меняет (US2-4, FR-010); `package_id` — только
чтобы бронь назвала живой пакет. `deal_id` у принятого — чтобы сделка называла пакет и состав из предложения, когда
пакета в анкете уже нет или предложение было своим описанием (FR-012).

## Жизненный цикл запроса — все пути

| Путь | Что с запросом | Кому сообщается |
|---|---|---|
| Пара убирает кандидата | `closed`, `removed` | подрядчику — «пара отозвала запрос» |
| Бронь места любой дверью (`…/book`, `…/external`, `…/accept`) | остальные открытые запросы места — `closed`, `booked_other`; принятый — `booked` | остальным — «пара выбрала другого исполнителя», без имени и цены `[В3]` |
| Отмена свадьбы | все открытые — `closed`, `wedding_cancelled` | подрядчикам — «пара отменила свадьбу» |
| Уборка архива и стирание пары | удаляются каскадом вместе со свадьбой — отменённая свадьба уже закрыла их выше | — |
| Стирание подрядчика | удаляются каскадом (его данные) | — |
| Перенос свадьбы | не закрывается; предложения на прежнюю дату — «на прежнюю дату», принять нельзя | — (подрядчик видит новую дату в запросе) |
| Анкету скрыли | не закрывается; ответить нельзя (409 `vendor_unavailable`), принять нельзя | — |

Закрытие по брони — в ядре `bookVendor`, одно место для трёх дверей (R-237).

## Решения

| Решение | Почему | Что отклонили и почему |
|---|---|---|
| Сущность — «шорт-лист» (`slot_shortlist`), на экране — «Кандидаты»; прежнее состояние сделки `candidate` на экранах получает другую подпись | слово занято (`backend/src/deals/state.ts:11,54-61`, `app/src/pages/Wedding.tsx:122`, `Tools.tsx:40`, `VendorExtras.tsx:40`); кандидатов нельзя сделать сделками — `slots.deal_id` уникален | сделки в состоянии `candidate` — одна сделка на место |
| Одно ядро брони `bookVendor` для трёх дверей; слот и пакет уже под замками (ERR-0317, `1472c9e`) | принятие предложения и две прежние брони — одно правило (R-237); закрытие запросов места — там же | принимать предложение своим кодом — третья копия правила |
| Добавление в кандидаты — по подрядчику (`PUT …/shortlist/{vendorId}`), место категории заводит сервер | вход — анкета и выдача, слот ищется по категории; `POST …/slots` доступен только паре, и помощник при В1=Б получил бы 403 у 23 категорий из 35 вне шаблона | клиент заводит место сам — отказ помощнику |
| Кандидат — только подрядчик категории места (FR-001); сменил категорию позже — остаётся с пометкой, новый запрос не уходит | сравнение пакетов одной категории | прежняя «Добавить в свадьбу» категорию не сверяет и не меняется |
| Сохранение пакетов по `id`; мастер переносит `id` из ответа `PUT` в черновик и вводит состав | мастер пересоздаёт пакеты на каждом «Далее» и стирает состав (`R/vendor.ts:287-296`, `app/src/pages/VendorApp.tsx:419,436-446`); пакет, добавленный в той же сессии, без `id` удалялся бы на следующем шаге | пути на каждый пакет — больше контракта ради того же |
| Занятость `free|held|busy|null` считает сервер: `held` — переговоры другой пары (запрос уходит), `busy` — бронь на дату (запрос не уходит, `busy`), своя свадьба — `free`, без даты — `null` | анкета различает три состояния (`app/src/pages/Search.tsx:380-381,696`), сравнение — одно и считает свою бронь занятостью (`app/src/pages/Smart.tsx:120,144`) | булево — два экрана отвечали бы по-разному |
| Запрос нескольким — частичный успех, итог по каждому; 409, только если не ушло ни одного | один занятый не должен отменять запрос остальным | всё или ничего — лишний круг для пары |
| Предел: не больше 10 новых запросов в сутки на свадьбу (429) | цикл «убрать — добавить — запросить» обходит «три на место» | без предела — утверждение спеки о защите было бы неправдой |
| Уведомления запросов и предложений — вид `deal`, `critical: false` (тихие часы и лимит действуют); заголовок и текст — постоянные строки, экран переводит оба | прочие `deal` в проекте критичные (`backend/src/jobs/index.ts:416,559`), а запрос — не срочное событие; FR-017 требует EN, сервер пишет по-русски | новый вид — миграция CHECK и настройки; перевод на сервере по `users.lang` — новый механизм |
| Срок предложения — дата в поясе свадьбы, по умолчанию сегодня + 7 `[В5]`; тесты считают «сегодня» так же (R-310) | «истёк» сравнивается с «сегодня» свадьбы, как сроки графика 018-A | метка времени — пояса пары и подрядчика расходятся |
| Снимок даты свадьбы в запросе; принять можно, только если он равен нынешней дате (без даты и потом с датой — тоже «на прежнюю дату») | FR-011; сверка под `weddings FOR SHARE`, как у брони | переписывать запросы при переносе — подрядчик отвечал на другие условия |
| Цена брони = цена предложения в момент принятия (SC-005); дальше `PATCH /deals` как сейчас | переговоры после брони — существующая возможность | запрещать правку — ломать 018-A и прежнюю бронь |
| `/compare` — только отмеченные кандидаты места; без места — выбор избранного галочками, не «первые три» | входы без места есть на главной, «Мы», избранном и в выдаче (`app/src/pages/Home.tsx:255`, `Us.tsx:178`, `Extras.tsx:48`, `Search.tsx:250`) | оставить «первые три» — ровно то, что спека называет проблемой |
| Новый экран кабинета «Запросы предложений» — вход с главной кабинета | подрядчик иначе не найдёт запрос; экран вне 67 экранов MVP — запись в JOURNAL и вопрос владельцу по §20.1 (R-15), план не правится молча | запросы среди лидов — лид на свадьбу, запрос на место |

## Ответы владельца — что меняется

- **В1** (сейчас Б). А: помощнику 403 на `PUT`/`DELETE` шорт-листа, экраны прячут кнопки, T010 ждёт 403. В: новое правило
  матрицы для запросов, но поле ориентира бюджета тогда у помощника — против «без бюджета» (Бизнес-логика §2, R-40):
  ориентир остаётся только паре.
- **В2** (сейчас Б). А: без `budget_hint` — audit52 16 таблиц, поле уходит из формы и выгрузки. В: нужен лимит категории
  018-B (ждёт слияния и В4 по 018) и соответствие «категория места → статья бюджета», которого нет.
- **В3** (сейчас А). Б: подрядчик узнаёт только из статуса «закрыт» в кабинете, уведомления нет. В: флаг в теле `accept`
  и галочка на экране; для `…/book` и `…/external` — сообщать по умолчанию.
- **В4** (сейчас А). Б: нужна операция чтения запросов места вне шорт-листа, `not_shortlisted` уходит, предел открытых
  запросов на место — свой.
- **В5** (сейчас А). Б: поле срока уходит из формы. В: CHECK `valid_until` снимается, `offer_expired` уходит, нужна
  операция «подрядчик отзывает предложение» — контракт, колонка, уведомление, кнопка, тесты.
