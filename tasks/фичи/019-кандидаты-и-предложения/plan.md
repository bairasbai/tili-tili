# План: кандидаты, запросы предложений и сравнение

**Спека:** ./spec.md · **Вопросы:** ./questions.md · **Задачи:** ./tasks.md
**Статус:** черновик на вариантах по умолчанию В1–В5 (ответов владельца ещё нет). Каждое место, которое зависит от
ответа, помечено `[В1]`…`[В5]`; другой ответ меняет только помеченное.

Факты о текущем коде — разведка 2026-09-26 (ссылки `путь:строка` ниже; `R` — `backend/src/routes`, `M` — `backend/migrations`).

## Затрагивается

| Слой | Что |
|---|---|
| БД | три таблицы: `slot_shortlist` (кандидаты), `offer_requests` (запросы), `offers` (предложения и отказы); уникальности под FR-001/FR-016; две денежные колонки с CHECK RUB (audit52 → 17 таблиц) |
| Бэк | ядро брони выносится в одну функцию для `…/book` и принятия предложения, слот запирается `FOR UPDATE` до вставки сделки; `PUT /vendor/profile` сохраняет пакеты по `id`; маршруты кандидатов, запросов, предложений; кабинет подрядчика — запросы; закрытие запросов при брони места, удалении кандидата, отмене свадьбы; уведомления |
| Контракт | 0.46.0: схемы `VendorPackage` (с `id`), `ShortlistEntry`, `OfferRequest`, `Offer`; 7 операций (ниже) |
| Фронт | экран места `/wedding/slot/:id` — блок кандидатов; анкета `/vendor/:id` — «В кандидаты» и «Запросить предложение»; `/compare` — выбранные кандидаты, пакеты, предложения; кабинет подрядчика — список запросов и форма ответа; мастер анкеты — `id` и состав пакетов; экран уведомлений — заголовок через `t()` |

## Ворота инвариантов

Проверено против `CLAUDE.md` §5 и R-01…R-15.

| Инвариант | Что нарушаем | Зачем | Почему нельзя иначе |
|---|---|---|---|
| — | нарушений нет | | |

Как соблюдается то, что здесь легко нарушить:
- **§5.11 (инварианты — в базе).** «Не больше трёх кандидатов» — `unique (slot_id, position)` + `check (position between 1 and 3)`;
  «один открытый запрос на подрядчика и место» и «одно действующее предложение на запрос» — частичные уникальные индексы;
  «один исполнитель на место» — существующий `slots_deal_unique`. Код под замком только выбирает свободную позицию.
- **§5.13 / R-178.** Счётчики кандидатов и «свободен на дату» — только из ответа; неизвестное — «—»; цена пакета без суммы —
  «по запросу», не 0 (R-281).
- **§5.15 / R-174.** Экран не обещает «подрядчик ответит»: только «запрос отправлен» и срок, который назвал подрядчик.
- **R-40 / FR-014.** Суммы предложений и бюджетный ориентир режутся из ответов для всех, кроме пары и автора
  предложения. В чат предложения не зеркалятся: координатор читает чаты с подрядчиками (`backend/src/chats/access.ts:24-31`).
- **R-311.** Новые ссылки на `users` — `on delete set null`; на `vendors` — `cascade` (стёртый подрядчик уходит из кандидатов);
  тест стирания для каждой.
- **R-312.** Защиту от дублей держит база (уникальности выше), а ключ идемпотентности — на попытку: клиент берёт новый ключ
  на каждый вызов (`app/src/lib/api/client.ts:363`), и два партнёра одновременно — это два ключа.

## Контракт

Версия 0.46.0 (`backend/test/audit55.test.ts:462`). Генераторы `gen-contract`, `gen-schemas`, `openapi-typescript` и копия
`app/src/lib/api/schema.ts` — в той же задаче, что правка YAML (инвариант 9). Каждый код отказа назван у своей операции
(audit55 G-c1), операции с `withIdempotency` объявляют `Idempotency-Key` и 400 (G-a).

| Операция | Кто `[В1]` | Коды |
|---|---|---|
| `GET /weddings/{weddingId}/slots/{slotId}/shortlist` — кандидаты места с карточкой, пакетами, занятостью на дату, запросом и предложением | пара, помощник, координатор; суммы предложений — только паре | 404 |
| `PUT /weddings/{weddingId}/slots/{slotId}/shortlist/{vendorId}` — в кандидаты | пара, помощник | 409 `shortlist_full` (в `details` — нынешние три), 422 `vendor_unavailable`, `category_mismatch` |
| `DELETE /weddings/{weddingId}/slots/{slotId}/shortlist/{vendorId}` — убрать; открытый запрос отзывается | пара, помощник | 404 |
| `POST /weddings/{weddingId}/slots/{slotId}/offer-requests` — запрос одному или нескольким кандидатам `[В2][В4]` | пара | 409 `not_shortlisted`, `request_open`, `vendor_busy`; 422; 400 ключ |
| `POST /weddings/{weddingId}/offers/{offerId}/accept` — бронь по предложению | пара | 409 `offer_expired`, `offer_stale_date`, `offer_superseded`, `slot_taken`, `date_taken`, `vendor_unavailable`; 400 ключ |
| `GET /vendor/offer-requests` — запросы подрядчику | подрядчик | — |
| `POST /vendor/offer-requests/{requestId}/offers` — предложение или отказ `[В5]` | подрядчик | 409 `request_closed`; 422; 400 ключ |

`VendorUpsert.packages[]` получает необязательный `id`; `VendorDetail.packages[]` и новые схемы ссылаются на одну схему
`VendorPackage` (правило R-314: одна схема, а не копии).

## Хранение

Миграция `1761500000000_shortlist_offers` (после `1761400000000`; `pgm.sql`, откат с данными — только с
`tili.allow_data_loss=yes`, как у 018).

```
slot_shortlist   (slot_id → slots cascade, vendor_id → vendors cascade, position smallint check 1..3,
                  added_by → users set null, created_at; pk (slot_id, vendor_id), unique (slot_id, position))
offer_requests   (id, slot_id → slots cascade, vendor_id → vendors cascade, status open|withdrawn|closed,
                  close_reason null|removed|booked_other|booked|wedding_cancelled, wedding_date date null (снимок),
                  guests int null, city text null, wishes text ≤ 2000, budget_hint bigint null + currency RUB [В2],
                  created_by → users set null, created_at, closed_at;
                  unique (slot_id, vendor_id) where status = 'open')
offers           (id, request_id → offer_requests cascade, kind offer|decline, package_id → vendor_packages set null,
                  package_snapshot jsonb null, title text, price bigint null + currency RUB, includes jsonb,
                  message text ≤ 2000, valid_until date null, superseded_at, accepted_at, deal_id → deals set null,
                  created_by → users set null, created_at;
                  check (kind = 'decline' and price is null) or (kind = 'offer' and price > 0 and valid_until is not null);
                  unique (request_id) where superseded_at is null)
```

Предложение хранит снимок пакета (`package_snapshot`: название, состав, цена на момент ответа): правка анкеты после ответа
предложение не меняет (US2-4, FR-010). Ссылка `package_id` — только чтобы бронь назвала пакет, пока он жив.

## Решения

| Решение | Почему | Что отклонили и почему |
|---|---|---|
| Сущность — «шорт-лист» (`slot_shortlist`), на экране — «кандидаты» | слово `candidate` занято состоянием сделки и плитки (`backend/src/deals/state.ts:11,54-61`); кандидатов нельзя сделать сделками — `slots.deal_id` уникален, `deals.slot_id` обязателен | сделки в состоянии `candidate` — одна сделка на место |
| Одно ядро брони для `…/book` и `…/accept`; слот `FOR UPDATE` сразу после свадьбы и пользователя | бронь вставляет сделку (замок KEY SHARE на слоте от внешнего ключа) до захвата слота — две брони ждут друг друга, 40P01 уходит 500; [Вероятно] это и есть известное 200/500 audit4 (`R/slots.ts:223,264-279`) | принимать предложение своим кодом — две двери одного правила (R-237) |
| Пакет в ядре брони — `for key share` до вставки сделки | параллельное сохранение анкеты удаляет пакет, вставка падает 23503 → 500 (`R/slots.ts:252-256`) | ловить 23503 после — замок дешевле и честнее |
| Пакеты анкеты сохраняются по `id`: обновить присланные, вставить новые, удалить отсутствующие | мастер пересоздаёт пакеты на каждом «Далее» и стирает состав (`R/vendor.ts:287-296`, `app/src/pages/VendorApp.tsx:419,436-446`) | отдельные пути на пакет — больше кода и контракта ради того же |
| Кандидат — только подрядчик категории места (FR-001) | сравнение пакетов одной категории; вход — анкета, слот ищется по категории (`app/src/pages/Search.tsx:432`) | правило брони «категорию не сверяем» остаётся для прежней кнопки «Добавить в свадьбу» |
| Запросы — отдельная сущность, не лиды | лид — на свадьбу (`unique (vendor, wedding)`), запрос — на место | расширить лиды — сломать их уникальность |
| Уведомления — вид `deal`, заголовки — постоянные строки, экран переводит `t(title)` | новый вид — миграция CHECK и правка настроек; FR-017 требует EN, а сервер пишет по-русски | переводить на сервере по `users.lang` — нового механизма ради четырёх строк |
| «Свободен на дату» считается сервером в ответе шорт-листа: занятость и холды, своя свадьба — не занятость, без даты — `null` | экран сравнения смотрит только `busyDates` и считает свою свадьбу занятостью (`app/src/pages/Smart.tsx:120,144`) | по запросу на подрядчика с клиента — N запросов и ограничитель |
| Срок предложения — дата в поясе свадьбы; по умолчанию сегодня + 7 `[В5]` | «истёк» сравнивается с «сегодня» свадьбы, как сроки графика 018-A | метка времени — пояс подрядчика и пары расходятся |
| Перенос свадьбы: предложение на прежнюю дату — «на прежнюю дату», принять нельзя (FR-011); запрос не закрывается | снимок даты в запросе сравнивается с датой свадьбы под `weddings FOR SHARE` | переписывать запросы при переносе — подрядчик ответил на другие условия |
| Цена брони = цена предложения в момент принятия (SC-005); позже пара может менять цену `PATCH /deals` — это событие журнала сделки | переговоры после брони — существующая возможность (`R/deals.ts:210-241`) | запрещать правку — ломать 018-A и старую бронь |
| Бронь места любым путём закрывает остальные открытые запросы этого места и сообщает их подрядчикам без имени и цены `[В3]` | иначе подрядчики держат дату и пишут паре (FR-013) | закрывать только при принятии предложения — бронь из каталога оставила бы запросы висеть |

## Риски, которые закрывает план

1. Взаимоблокировка двух броней одного места (audit4) — ядро брони с замком слота; регрессионный тест с одновременными бронями.
2. Потеря пакетов и их состава при каждом шаге мастера — FR-006; тесты `stage3` и `audit49l` меняют ожидание
   «заменяются целиком» на «сохраняются по id, удалённый не воскресает».
3. Пути под слотом закрыты матрицей всем (`backend/src/wedding/access.ts:43` не называет GET/PUT) — новые правила выше неё.
4. Стирание аккаунта — тест для каждой новой ссылки (R-311, `backend/test/stage9.test.ts:90-113`).
5. Отмена свадьбы закрывает открытые запросы (`R/weddingLifecycle.ts:152-171` сейчас отменяет только брони).
