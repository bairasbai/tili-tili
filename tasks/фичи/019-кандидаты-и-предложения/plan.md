## Ворота инвариантов

Проверено против `CLAUDE.md` §5 и R-01…R-15.

| Инвариант | Что нарушаем | Зачем | Почему нельзя иначе |
|---|---|---|---|
| — | нарушений нет | | |

Как соблюдается то, что здесь легко нарушить:
- **§5.1 R-MAP/R-BTN.** Карты экранов и кнопок обновляются в конце КАЖДОЙ фазы, которая меняет экран (фаза 2 — мастер
  анкеты; фазы 3, 4, 5), а не одной задачей в полировке: остановка на любой фазе не оставит карты позади.
- **§5.11 (инварианты — в базе).** «Не больше трёх кандидатов» — `unique (slot_id, position)` + `check (position between
  1 and 3)`; «один открытый запрос на подрядчика и место» и «одно действующее предложение на запрос» — частичные уникальные
  индексы; согласованность статусов (закрыт ↔ причина ↔ время, принято ↔ сделка) — CHECK; «один исполнитель на место» —
  существующий `slots_deal_unique`.
- **§5.13 / R-178 / R-281.** Счётчики и занятость — только из ответа; неизвестное — «—»; пакет без цены —
  «цена не названа» (R-281): так пишет мастер (`app/src/pages/VendorApp.tsx:568`), а анкета показывает пустоту
  (`app/src/pages/Search.tsx:648`) — правится там же, где анкета получает «В кандидаты».
- **§5.15 / R-174.** Экран не обещает «подрядчик ответит»: «запрос отправлен» и срок, который назвал подрядчик.
- **R-40 / FR-014.** Помощнику и координатору — только факт «ответ получен» (`status`), без цены, названия, состава,
  текста и снимка пакета: цена может стоять в любом из них. Предложения не зеркалятся в чат — координатор читает чаты
  с подрядчиками (`backend/src/chats/access.ts:24-31`).
- **R-311 / R-221.** Ссылки на `users` — `on delete set null`. `slot_shortlist.vendor_id` и
  `offer_requests.vendor_id` — `on delete set null`, чтобы обещанная позиция «анкета недоступна» пережила стирание
  без id и имени. До удаления vendor открытые запросы закрываются `vendor_erased`, непринятые предложения удаляются;
  принятые условия уже скопированы в неизменяемые колонки сделки. `performer_erased_at` делает сделку без
  `vendor_id`/`external_name` явным валидным состоянием; имя и телефон не подменяются меткой. `offers.deal_id` — `on delete cascade`, а не
  `set null`: `set null` рядом с CHECK «принято ↔ сделка» откатывал бы уборку архива (ERR-0209). Тест стирания — через
  уборку и вход, со свадьбой и принятым предложением; поиск id, имени, телефона и непринятых текстов — включая JSON.
- **R-322.** Tombstone адресуется собственным `slot_shortlist.id`, а не nullable `vendor_id`: поэтому DELETE принимает
  `entryId` и позволяет паре освободить одну из трёх позиций даже после полного стирания подрядчика.
- **R-323.** Замена одного кандидата другим — одна серверная операция под замком слота. Клиентская цепочка
  `PUT → DELETE → PUT` не допускается: при гонке или отказе она оставляла бы две записи. Устаревший/чужой `replaceEntryId` возвращает 409 со свежей
  тройкой и ничего не меняет (ERR-0323).
- **R-312.** Ключ идемпотентности — на попытку, для запроса, предложения и принятия: живёт до успеха, повтор той же
  попытки после обрыва идёт тем же ключом. Новое намерение законно заменяет предложение (FR-010), но не чаще пяти
  версий за скользящие 24 часа на запрос: замок запроса, 429 `offer_revisions_limit` + `Retry-After`; уведомление —
  только после успешной новой версии.
- **R-317 / R-315 / R-271.** Порядок замков записей 019: свадьба → пользователь `FOR SHARE` → слот `FOR UPDATE` →
  запрос `FOR UPDATE` → подрядчик `FOR SHARE OF u` → пакет `FOR KEY SHARE` → обновление старого предложения. Запрос —
  единственный mutex версий и будущего accept; активный offer до vendor/package читается без `FOR UPDATE`, иначе `PUT /vendor/profile`
  может замкнуть цикл offer → vendor против vendor → package delete → FK `offers.package_id SET NULL` (ERR-0326). Свадьба — `FOR SHARE`, кроме
  двух записей, которым нужна её эксклюзивность: добавление в кандидаты (ищет место категории — уникальности
  «свадьба + категория» нет, как у `POST …/slots`, `R/slots.ts:154-178`) и запрос предложения (считает предел в сутки —
  R-271, замок строки-владельца); они берут свадьбу `FOR UPDATE` первой, никогда не повышая `FOR SHARE` (R-315). Ответ
  подрядчика свадьбу не пишет: запрос `FOR UPDATE` → vendor/user `FOR SHARE` → пакет `FOR KEY SHARE` → offer update/insert.

## Контракт

Текущая версия 0.49.0; операции US1 добавлены в T013, а атомарная замена закрыла ERR-0323 при интеграции T017; T023 добавил batch-запрос и кабинет, T033 — принятие. Каждая правка YAML — в той же задаче с `gen-contract`, `gen-schemas`,
`openapi-typescript` и копией `app/src/lib/api/schema.ts` (инвариант 9). Коды отказа названы у своей операции (audit55
G-c1); операции с `withIdempotency` объявляют `Idempotency-Key` и 400 (G-a). «Анкета недоступна» — один код во всех
операциях 019: 409 `vendor_unavailable` (прежний `…/book` отвечает 404 и не меняется).

| Операция | Кто | Коды |
|---|---|---|
| `GET /weddings/{weddingId}/slots/{slotId}/shortlist` — кандидаты места: карточка, пакеты, занятость `free|held|busy|null`, запрос и предложение (паре — целиком, остальным — `status`) | пара, помощник, координатор | 403, 404 |
| `PUT /weddings/{weddingId}/shortlist/{vendorId}` — в кандидаты места категории подрядчика; места нет — паре сервер его заводит, помощнику — отказ; необязательный `replaceEntryId` атомарно заменяет выбранную запись в полной тройке | пара, помощник | 409 `shortlist_full` (в `details` — свежие три), `request_open`, `vendor_unavailable`, `slot_missing` (помощнику: место заводит пара); 422, 403, 404 |
| `DELETE /weddings/{weddingId}/slots/{slotId}/shortlist/{entryId}` — убрать по стабильному id записи (в том числе tombstone); открытый запрос закрывается `removed` | пара; помощник — только без открытого запроса | 409 `request_open` (помощнику); 403, 404 |
| `POST /weddings/{weddingId}/slots/{slotId}/offer-requests` — запрос одному–трём кандидатам; необязательный `budgetHint`; итог по каждому (`sent`, `not_shortlisted`, `busy`, `already_open`, `unavailable`, `category_changed`) | пара | 201 с итогами; 409 `no_request_sent` с итогами, если не ушло ни одного; 429 `offer_requests_limit` (10 за скользящие 24 часа на свадьбу); 422; 400 ключ; 403, 404 |
| `POST /weddings/{weddingId}/offers/{offerId}/accept` — бронь по предложению, ответ — `Slot` | пара | 409 `offer_expired`, `offer_stale_date`, `offer_superseded`, `request_closed`, `offer_declined`, `slot_taken`, `date_taken`, `vendor_unavailable`; 400 ключ; 403, 404 |
| `GET /vendor/offer-requests` — запросы подрядчику (дата или «не выбрана», гости, город, пожелания, ориентир, если передан, статус) | подрядчик | 403 |
| `POST /vendor/offer-requests/{requestId}/offers` — предложение или отказ; срок задаёт подрядчик, default +7 дней | подрядчик | 409 `request_closed`, `vendor_unavailable`; 429 `offer_revisions_limit` + `Retry-After`; 422; 400 ключ; 403, 404 |
| `PUT /vendor/profile` — `packages[]` по схеме `VendorPackageInput` (с необязательным `id`) | подрядчик | 422 `unknown_package` (чужой `id`) |

`shortlist_full` и `no_request_sent` возвращают route-specific схемы с массивом текущих кандидатов/итогов; общий
helper `errors.ts` произвольные `details` не добавляет. Ответ собирается явно, как `slot_exists`, и форма проверяется
контрактным тестом — иначе полезный массив молча потеряется.

T022 фиксирует форму будущего контракта T023. Запрос пары передаёт `{ entryIds, wishes?, budgetHint? }`, где
`entryIds` — 1–3 уникальных UUID собственных записей `slot_shortlist`, а `budgetHint` — положительный `Money` только
в RUB. Успех имеет ровно `{ results }`; `409 no_request_sent` — ровно
`{ error: { code, message, details: { results } } }`. Каждый итог адресуется исходным `entryId`, а `requestId`
присутствует только у `sent`. `GET /vendor/offer-requests` возвращает bare array, как существующий список лидов.

Успешный ответ подрядчика возвращает точный `Offer`:
`{ id, requestId, kind, packageId, title, price, includes, message, validUntil }`. Для `decline` поля пакета, названия,
цены и срока равны `null`, `includes` пуст; для `offer` обязательны название, положительная цена RUB и срок. В чтении
места пара получает запрос и действующее предложение целиком, помощник и координатор — только
`{ status: 'pending' | 'responded' }`. Это не новый маршрут: формы закрепляют уже запланированные операции.

Две схемы пакета, а не одна: в ответе `id` обязателен и `price` бывает `null` («по запросу»); на вводе `id` необязателен,
а `price` отсутствует, а не `null` (R-281). `VendorDetail.packages[]` переходит на `VendorPackage`.

## Хранение

Миграция `1761500000000_shortlist_offers` (после `1761400000000`; `pgm.sql`; откат с данными — только с
`tili.allow_data_loss=yes`, как у 018).

```
slot_shortlist   (id pk, slot_id → slots cascade, vendor_id nullable → vendors set null,
                  position smallint check 1..3, added_by → users set null, created_at;
                  unique (slot_id, vendor_id) where vendor_id is not null, unique (slot_id, position))
offer_requests   (id, slot_id → slots cascade, vendor_id nullable → vendors set null,
                  status open|closed, close_reason null|removed|booked_other|booked|wedding_cancelled|date_changed|vendor_erased,
                  closed_at; check ((status = 'open' and close_reason is null and closed_at is null)
                                 or (status = 'closed' and close_reason is not null and closed_at is not null)),
                  wedding_date date null (снимок), guests int null, city text null, wishes text ≤ 2000,
                  budget_hint bigint null + currency RUB, created_by → users set null, created_at;
                  unique (slot_id, vendor_id) where status = 'open' and vendor_id is not null;
                  index (slot_id, created_at) + join slots(wedding_id) для предела 10 в сутки)
offers           (id, request_id → offer_requests cascade, kind offer|decline, package_id → vendor_packages set null,
                  package_snapshot jsonb null, title text, price bigint null + currency RUB, includes jsonb,
                  message text ≤ 2000, valid_until date null, superseded_at, accepted_at, deal_id → deals cascade,
                  created_by → users set null, created_at;
                  check (kind = 'decline' and price is null and valid_until is null and accepted_at is null)
                     or (kind = 'offer' and price > 0 and valid_until is not null);
                  check (accepted_at is null or superseded_at is null);
                  check ((accepted_at is null) = (deal_id is null));
                  unique (request_id) where superseded_at is null;
                  index (request_id, created_at) для предела 5 версий за 24 часа)
deals            (+ package_title_snapshot text null,
                  + package_includes_snapshot jsonb null check array;
                  + performer_erased_at timestamptz null;
                  check (vendor_id is not null or external_name is not null or performer_erased_at is not null);
                  миграция заполняет снимок для существующих сделок с живым package_id)
```

Снимок пакета в предложении: правка анкеты после ответа предложение не меняет (US2-4, FR-010); `package_id` нужен
только для проверки и связи до брони. В момент любой брони название и состав копируются в `deals`: обычная бронь —
из живого пакета под `FOR KEY SHARE`, принятие — из неизменяемого предложения. Чтение сделки предпочитает снимок и
лишь для старой строки без снимка использует живой пакет. Поэтому удаление предложения или подрядчика не меняет
условия сделки пары и подрядчика (FR-006/FR-018).

## Жизненный цикл запроса — все пути

| Путь | Что с запросом | Кому сообщается |
|---|---|---|
| Пара убирает кандидата | `closed`, `removed` | подрядчику — «пара отозвала запрос» |
| Бронь места любой дверью (`…/book`, `…/external`, `…/accept`) | открытый запрос забронированного подрядчика (если был) — `closed`, `booked`; остальные открытые запросы места — `closed`, `booked_other` | остальным — «пара выбрала другого исполнителя», без имени и цены (В3-А) |
| Отмена свадьбы | все открытые — `closed`, `wedding_cancelled` | подрядчикам — «пара отменила свадьбу» |
| Уборка архива и стирание пары | удаляются каскадом вместе со свадьбой — отменённая свадьба уже закрыла их выше | — |
| Стирание подрядчика | открытый запрос — `closed/vendor_erased`; непринятые предложения удаляются; `vendor_id` в запросе и кандидате обнуляется, остаётся обезличенный tombstone; принятые условия уже в сделке | — |
| Перенос свадьбы или первая дата | все открытые запросы свадьбы — `closed`, `date_changed`; предложения — «на прежнюю дату», принять нельзя; пара запрашивает заново | подрядчикам — «пара перенесла дату — запрос закрыт» |
| Анкету скрыли | не закрывается; ответить нельзя (409 `vendor_unavailable`), принять нельзя | — |

Закрытие по брони — в ядре `bookVendor`, одно место для трёх дверей (R-237).

## Решения

| Решение | Почему | Что отклонили и почему |
|---|---|---|
| Сущность — «шорт-лист» (`slot_shortlist`), на экране — «Кандидаты»; прежнее состояние сделки `candidate` на экранах получает другую подпись | слово занято (`backend/src/deals/state.ts:11,54-61`, `app/src/pages/Wedding.tsx:122`, `Tools.tsx:40`, `VendorExtras.tsx:40`); кандидатов нельзя сделать сделками — `slots.deal_id` уникален | сделки в состоянии `candidate` — одна сделка на место |
| Одно ядро брони `bookVendor` для трёх дверей; слот и пакет уже под замками (ERR-0317, `1472c9e`) | принятие предложения и две прежние брони — одно правило (R-237); закрытие запросов места — там же | принимать предложение своим кодом — третья копия правила |
| Добавление в кандидаты — по подрядчику (`PUT …/shortlist/{vendorId}`); место категории паре заводит сервер, помощнику — отказ словами `slot_missing` | вход — анкета и выдача, слот ищется по категории; состав мест решает пара (фича 014, `backend/src/wedding/access.ts:93-94`) — помощник косвенно заводить места не должен | помощник заводит место через шорт-лист — расширение его прав мимо решения фичи 014 |
| Кандидат — только подрядчик категории места (FR-001); сменил категорию позже — остаётся с пометкой, новый запрос не уходит | сравнение пакетов одной категории | прежняя «Добавить в свадьбу» категорию не сверяет и не меняется |
| Сохранение пакетов по `id`; мастер переносит `id` из ответа `PUT` в черновик и вводит состав | мастер пересоздаёт пакеты на каждом «Далее» и стирает состав (`R/vendor.ts:287-296`, `app/src/pages/VendorApp.tsx:419,436-446`); пакет, добавленный в той же сессии, без `id` удалялся бы на следующем шаге | пути на каждый пакет — больше контракта ради того же |
| «Забронировать» кандидата на пустом месте — прежним путём анкеты: выбор пакета и цена из анкеты (или своя), `…/book` | запросы места закрыты прежней бронью (`booked_other`), их предложения принять нельзя; для цены из предложения — запросить заново | принимать предложение закрытого запроса — подрядчику уже сказали «выбрали другого» |
| Любая новая сделка хранит неизменяемый снимок названия и состава пакета; принятие копирует его из предложения | живой пакет меняется и удаляется, предложение удаляется при стирании подрядчика; условия сделки должны пережить оба события у пары и подрядчика | читать живой пакет или `offers.deal_id` при каждом GET — задним числом меняет или теряет договорённость |
| При стирании подрядчика кандидат и запрос остаются только обезличенными tombstone; непринятые предложения удаляются | спека обещает «анкета недоступна», но хранить id, имя и свободные тексты после стирания нельзя | `ON DELETE CASCADE` — молча теряет историю пары; хранить все ответы — лишние персональные данные |
| Занятость `free|held|busy|null` считает сервер: `held` — переговоры другой пары (запрос уходит), `busy` — бронь на дату (запрос не уходит, `busy`), своя свадьба — `free`, без даты — `null` | анкета различает три состояния (`app/src/pages/Search.tsx:380-381,696`), сравнение — одно и считает свою бронь занятостью (`app/src/pages/Smart.tsx:120,144`) | булево — два экрана отвечали бы по-разному |
| Запрос нескольким — частичный успех, итог по каждому; 409, только если не ушло ни одного | один занятый не должен отменять запрос остальным | всё или ничего — лишний круг для пары |
| Предел: не больше 10 новых запросов за скользящие 24 часа на свадьбу (429), под замком свадьбы | цикл «убрать — добавить — запросить» обходит «три на место»; скользящее окно не зависит от пояса (тесты — без R-310) | календарные сутки — зависимость от пояса и часа |

## Принятые ответы владельца — 2026-09-27

- **В1-Б:** кандидатов добавляют и убирают пара и помощник; помощник не создаёт место и не убирает кандидата с
  открытым запросом. Запросы и принятие — только пара; координатор только читает без сумм.
- **В2-Б:** `budget_hint` nullable, поле пустое по умолчанию; ничего из бюджета свадьбы не подставляется автоматически.
- **В3-А:** при успешной брони остальные подрядчики получают обезличенное уведомление «пара выбрала другого».
- **В4-А:** запрос только кандидату; действие с анкеты сначала добавляет его в кандидаты при наличии места.
- **В5-А:** срок задаёт подрядчик, default — сегодня свадьбы + 7 дней.
