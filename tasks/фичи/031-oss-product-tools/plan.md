# План реализации

1. Основа — проверенный одним fetch `origin/main` 3041d2c в отдельной sparse-копии. Прежняя PDF-ветка принадлежит старой локальной копии; переносить только полезный код/лицензии и адаптировать к текущему контракту. Прежние документы и незавершённые изменения других сессий не переносить.
2. PDF: единый локальный генератор pdfme, статический OFL-шрифт; явные текстовые модели для договора, программы, гостей и рассадки; кнопки в существующих экранах и текущий namespace/поколение/снимок/операция. Код генератора ленивый. Никаких изменений денежных величин/условий договора/серверных подписей.
3. Приглашение: новая отдельная таблица черновика/публикации с собственной bigint-версией; строгая версия JSON-формата с четырьмя типами Puck-блоков и ограниченными свойствами. If-Match обязателен. Существующий wedding access lock и повторная проверка JWT после ожидания. Чтение текущей командой, сохранение/публикация только парой. Гостевые проекции отдают только published; при его отсутствии сохраняется прежнее представление.
4. Фото: ограниченный inline raster, до трёх фото по 128 KiB decoded, итог ниже существующего 1 MiB body limit; MIME/magic и фактические dimensions проверяются сервером. Клиентская подготовка на canvas; запрет SVG/анимации/удалённых URL и произвольного вложенного дерева. Рендер собственными компонентами на прежних токенах; один рендер для preview/гостя. Отмена/конфликт не публикуют непроверенный черновик.
5. Тиль: ограниченный структурированный ответ модели сохраняет прежний текстовый fallback. Вопрос привязывается по messageId, контекст ограничивается им. Три неденежных action kinds; task id/revision берутся из проверенного контекста. Добавить DB revision задач и таблицу immutable-предложений с привязками и состояниями. Действие принимает только исходный получатель пары через POST accept с пустым телом; актуальный lock/auth/consent/JWT, собственность и ревизия под транзакцией; изменение задачи + сохранённый результат атомарны и повторяемы без второго исполнения.
6. assistant-ui использовать как локальный ExternalStoreRuntime/Tool UI для карточек над имеющимися серверными сообщениями. Сетевой транспорт/подгрузка/отправка остаются существующими. Не включать неподдержанные edit/regenerate/file-upload функции. Обновление результата выполняется по action/message id, в том числе в ранней странице истории; устаревшие обработчики блокируются.
7. DocETL: самостоятельный optional CLI в Юлдаше с двумя конфигурациями источников; CSV/JSON агрегаты, редактирование входных данных и явное включение модели. Секреты не добавлять, модель/провайдер — параметр оператора. Пробные проверки на synthetic/mock adapter и отдельно отмеченная непроверенность качества настоящего LLM. Не создавать новый сервер/бота или фонового агента.
8. Перед новым кодом подсистем — независимая приёмка плана. Каждая функция получает отдельный коммит после проверок. Контракт и generated types — штатными генераторами. Сначала типы и целевые функциональные проверки, затем свежий review, затем полный обязательный frontend/backend и браузер текущей версии.
9. Для backend зарезервировать только проверенный свободный 15432 и отдельный Redis после проверки владельца; runner допускает только disposable DB/codex_test и согласованные TEST_DATABASE_URL/DATABASE_URL. Не подключаться к системной 5432 или чужому кластеру. Все службы root-owned, скрытые, PID/time/cwd/ports регистрируются. Сохранить исходные FAILED и нужные данные по правилам проекта. По завершении остановить свои процессы и удалить свои копии после сохранения коммитов/патчей/доказательств.

Новые миграции получают уникальные timestamp-имена и не редактируют 95-ю миграцию незавершённой соседней ветки. Фактические поля/индексы и порядок блокировок уточняются по существующему коду до записи SQL. Новые ветки не сливаются в main и не публикуются этим поручением.

## Обязательные уточнения независимого ревью до кода

- Ревизия `tasks.revision` — bigint, начальное значение 1. Монотонный DB-trigger повышает её на **каждом UPDATE** строки задачи, включая обычные обработчики и служебный SQL; клиент не может задать или уменьшить ревизию. Удаление задачи делает старую карточку неприменимой. Обязателен сценарий A→B→A: изменение и возврат прежних полей не восстанавливают применимость старой карточки.
- Документ приглашения: не более 16 блоков, только Text/Photo/Program/Place; уникальный id 1–80 ASCII-букв/цифр/_/-, обязательная версия формата 1. Text: заголовок до 120, текст до 4000 символов; Photo: подпись до 240, не более 3 блоков; Program: до 24 пунктов, время HH:mm, подпись пункта до 240; Place: название до 240, адрес до 500. Произвольные root/props/вложенные блоки/HTML/CSS/URL запрещены как структура, пользовательский текст отображается буквально. Размер JSON UTF-8 ≤768 KiB.
- Фото: только PNG/JPEG/WebP; decoded вход ≤128 KiB на фото; ширина и высота 1–4096, площадь ≤8 000 000 пикселей, один кадр. Сервер полностью декодирует ограниченный raster и нормализует его в WebP без EXIF/метаданных; выход также ≤128 KiB. Для надёжного декодирования применяется закреплённый sharp, вместо собственноручного парсера изображения. Несовпадение MIME/magic, обрезанные/повреждённые данные, SVG/анимация, превышение любого предела дают отказ без изменения черновика.
- Тиль: максимум 3 предложения на ответ, title 1–200, taskId только существующий UUID checklist-задачи своей свадьбы, due только реально существующая ISO-дата YYYY-MM-DD. Параметры неизменяемы после сохранения. Только исходный получатель может принять pending-предложение; срок pending 24 часа по времени БД. Старый/чужой вопрос или устаревшая ревизия не порождают применимое действие. Внутри транзакции хранится tagged outcome; HTTP-успех и события выдаются только после commit.
- Обязательные regression cases: все численные границы и превышения; MIME/байты/dimensions/повреждённый файл; draft не виден в обеих guest projections; publish сохраняет ровно выбранную версию; два устройства/CAS; отзыв роли, сессии, согласия и истечение JWT во время ожидания; подмена чужих id/payload/recipient; A→B→A; parallel/restart repeat accept; принудительный поздний rollback не даёт ни действия, ни ложного HTTP success. Первичные FAILED/RED не заменяются успешными файлами.
