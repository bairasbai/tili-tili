## Контракт

Версия `0.26.0`. Генераторы в той же итерации (инвариант 9): в `backend` — `pnpm run gen`
(`gen-contract`, `gen-schemas`, `gen:types`); типы фронта — тем же установленным в `backend` пакетом:
`node node_modules/openapi-typescript/bin/cli.js ../Тили-тили_API_openapi.yaml -o ../app/src/lib/api/schema.ts`
(в `app` пакета нет, `npx` потянул бы зависимость из сети — стоп-условие).

1. `UserProfile` + `isStaff: boolean`, **`readOnly: true`** (как `id`, `phone`, `email`): `PATCH /users/me`
   берёт тело по той же схеме, и без `readOnly` контракт объявил бы признак настраиваемым — против
   SC-004. Единственное место, где клиент узнаёт о признаке, и только о своём.
2. **Новый** метод `GET` у пути `/admin/categories` → `AdminCategories { categories: AdminCategory[], synonyms: object<string,string> }`,
   `AdminCategory = Category + sort: integer`, `icon` — `nullable` (в базе так). Без чтения экран
   категорий правил бы словарь вслепую: `PUT` заменяет его целиком. Путей остаётся 117, операций — 153.
3. `PUT /admin/categories`: тело — `categories: AdminCategory[]` (не `Category[]`: нужен `sort`),
   `synonyms: { additionalProperties: { type: string } }` (сейчас `type: object` без свойств — генерится
   как `Record<string, never>`, и в него не положить ни одной пары); ограничения как у бэкенда
   (`maxItems: 100`, `id ≤ 40`, `title 1..100`, `icon ≤ 16`, `sort: integer`); ответ
   `CategoriesUpdated { categories: integer, synonyms: integer }`. Клиент не шлёт `icon: null` — поле
   опускается, сервер сохраняет прежний значок (`coalesce`).
4. `GET /admin/moderation/vendors` → `ModerationVendorPage { items: ModerationVendor[], nextCursor }`,
   `ModerationVendor = Vendor + createdAt + publishedAt` (`date-time`): бэкенд уже отдаёт `createdAt`,
   контракт молчал; `publishedAt` добавляется, потому что экран обещает дату публикации, а не создания.
5. `POST /admin/moderation/vendors/{vendorId}` → ответ `VendorDecision { vendorId, action }`; `reason`
   `maxLength: 1000`; описание: при `reject` причина обязательна (сервер отвечает `422`, поле `reason`).
6. `POST /admin/complaints/{complaintId}` → ответ `ComplaintDecision { complaintId, action }`; `note`
   `maxLength: 2000`; в описании — какие санкции к какой цели применимы; неприменимая — `422`.
7. `GET /admin/metrics` → `AdminMetrics { users, weddings, vendorsPublished, moderationQueue, complaintsOpen,
   complaintsOverdue, deals: integer; gmv: Money; cities: [{ city, vendors: integer, launchReady: boolean }] }`.
8. `GET /admin/weddings/{weddingId}`: `reason` `minLength: 5, maxLength: 500`; ответ выделен в схему `WeddingSupportCard`.
9. Новый компонент `responses.Validation` (`422`, схема `Error`): такого ответа в контракте нет ни у одной
   операции, хотя сервер отдаёт `422 validation_failed` на любой провал схемы. Всем операциям `/admin/*` —
   `401` (`Unauthorized`), `403` (`Forbidden`), `404` (`NotFound`, где есть путь-параметр), `422` (`Validation`).
   Описание `Category`: «через POST /admin/categories» → `PUT`.

## Хранение

Новых таблиц и ограничений нет. Что делает бэкенд поверх существующих колонок:

- очередь модерации: `published_at is not null and moderated_at is null and blocked_at is null`,
  в выборке — `published_at` для `publishedAt`;
- решение по анкете: `reject` без непустой `reason` → `422 validation_failed`, поле `reason`;
  решение принимается только по живой анкете — `published_at is not null and blocked_at is null` (то же условие,
  что у карточки каталога), проверка `select … for update` внутри транзакции, иначе `409 vendor_not_live` с
  сообщением по случаю; `approve` по уже проверенной живой анкете идемпотентен (ревью A-02);
- счётчик очереди на дашборде и сама очередь — одна SQL-константа `MODERATION_QUEUE_FROM` (ревью A-01);
  просмотр карточки каталога сотрудником не считается в `vendors.views` (A-08); сторож NUL проверяет и ключи
  объектов тела (A-06); дубли слов словаря после приведения к нижнему регистру — 422 (A-05);
  падение `notify` после фиксации решения — предупреждение в лог, ответ 200 (A-14);
- `synonyms`: перед вставкой — `select id from categories where id = any($1)`, неизвестные → `422 validation_failed`
  с полем `synonyms.<слово>`; всё в одной транзакции с записью аудита;
- санкция по жалобе: `vendor` → `dismiss|warn|downrank|block`; `review` → `dismiss|warn|block`
  (`block` = скрыть отзыв, `downrank` к отзыву не принимается); `message|deal` → `dismiss|warn`;
  иначе `422 validation_failed` с полем `action`;
- уведомление подрядчику (владельцу анкеты, `kind: 'system'`, `link: '/vendor-app'`) при `warn`,
  `downrank`, `block` по цели `vendor`; `critical: true` при `block`; текст заметки не уходит.

## Решения

| Решение | Почему | Что отклонили и почему |
|---|---|---|
| `isStaff` в собственном профиле | меню «Мы» должно знать, показывать ли пункт, до первого запроса в панель | пробный запрос `GET /admin/metrics` и чтение 403 — код `forbidden` не отличает «не сотрудник» от «нет согласия», и меню делало бы лишний запрос при каждом открытии |
| новый `GET /admin/categories` | `PUT` заменяет словарь целиком; без чтения экран стирал бы то, чего не видел | экран без словаря, только категории — половина экрана 65; чтение словаря из `GET /catalog/categories` — там его нет и не место |
| «Предупредить», «Понизить», «Заблокировать» уведомляют подрядчика | кнопка без адресата — «только экран» с записью, R-176; План §18.2 называет это санкциями | молча писать `resolution` — так сейчас; подрядчик исчезает из выдачи и не узнаёт почему |
| неприменимая санкция → `422` | «Заблокировать» сообщение, которое ничего не блокирует, — ложь на кнопке | принимать и писать `resolution` как сейчас — экран не может честно подписать такую кнопку |
| «Отметить верифицированным» остаётся | операция есть в контракте и бэкенде; галочка в каталоге — единственный путь к ней, пока нет загрузки документов | скрыть до хранилища — тогда верифицировать нельзя никого; текст действия говорит, что документы сверены вне приложения |
| слова: «одобрить» = проверена модератором (`moderated_at`), «верифицировать» = документы сверены (`verified_at`), в списке очереди пометка «Верифицирован» по `verified` | одно слово «проверен» покрывало два состояния | «проверен» для обоих — модератор не понял бы, что уже сделано |
| `TopBar` получает необязательный `fallback` для `goBack` | с детали `/admin/moderation/:vendorId` при прямом заходе «назад» уводило бы на `/home`, вон из панели | не ставить «назад» на детали — теряется привычная навигация |
| `admin` — в `SEGMENTS` deep-link-шима `app/index.html` | иначе прямая ссылка на `/admin` на хостинге в подпапке уедет в чужой корень, а `shell.test.tsx` это ловит | — |
| подтверждение сохранения словаря — свой оверлей `role="dialog"` + `useEscape` | `window.confirm` в проекте не используется и в jsdom не реализован; `dialogs.test.tsx` требует роль и Escape | — |
| 403 на адресах панели читается как «не сотрудник» | код `forbidden` общий с «нет согласия», но без согласия человек не вошёл бы вовсе (R-182) | различать по тексту сервера — хрупко |
| деталь анкеты — отдельный маршрут `/admin/moderation/:vendorId`, читает `GET /catalog/vendors/{vendorId}` | очередь отдаёт `Vendor` без описания и медиа; карточка каталога уже содержит всё, что проверяет модератор | развернуть карточку в списке — усложняет и список, и тесты; свой путь «анкета для модератора» — дубль карточки каталога |
| один файл `pages/Admin.tsx`, один чанк `load.admin` | как у кабинета подрядчика: чанк на раздел, компоненты на экраны | по файлу на экран — шесть чанков ради шести маленьких экранов |
| без shadcn-компонентов, свои классы `card`/`press`/токены | в проекте ни один экран не использует `components/ui/*` — они на чужих токенах и рендерятся бесцветно (`DatePicker.tsx:24-31`) | подключить shadcn — дубли компонентов (R-02) и работа с токенами вне задачи |
| догрузка «Показать ещё» по `nextCursor` | как чаты и списки каталога; очередь модератора редко длиннее страницы | бесконечная прокрутка — лишняя механика для панели |
| `CHECK` на `complaints.resolution` | нужна миграция — стоп-условие сессии; проверка входа закрывает ту же дыру для клиента | — владельцу, `tasks/todo.md` «Хвосты» |
| LLM-стоимость и заполненность анкет на дашборде — не показываем | сервер не считает ни то, ни другое; заглушка с нулём нарушила бы R-178 | — владельцу, `RELEASE-BLOCKERS.md` |

## Открытые технические вопросы

- **Права на просмотр карточки заблокированного подрядчика.** `GET /catalog/vendors/{id}` отвечает 404 для
  заблокированных; в очереди модерации их нет (см. «Хранение»), а в очереди жалоб цель-подрядчик может
  быть уже заблокирована другой жалобой — экран покажет «карточка недоступна в каталоге», решение по
  жалобе всё равно доступно. Отдельный «просмотр для модератора» — не в этой фиче.
- **Просмотр сделки и переписки поддержкой** (План §19.10 п. 5 говорит «сделки/проекта») — пути нет;
  делать без владельца не стоит: это доступ к чужим деньгам и переписке. Владельцу.
- **Верификация после одобрения.** Одобренная анкета уходит из очереди, а другого списка, откуда можно
  верифицировать, нет (`vendor_verifications` наружу не отдаются). Пока документы не загружаются, это
  не мешает; с хранилищем понадобится очередь верификации — владельцу.
- **Плитка новой категории.** Колонка `categories.tile` панелью не задаётся; `Tile` в `chrome.tsx` должен
  переживать пустую плитку — проверить в T024 и при нужде дать нейтральный класс из токенов.
