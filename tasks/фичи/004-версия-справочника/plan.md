# План: Версия справочника категорий

**Спека:** ./spec.md

## Затрагивается

| Слой | Что |
|---|---|
| Фронт | `app/src/pages/Admin.tsx` (`AdminCategories`) — версия в черновике, отправка версии, ветка 409 `categories_stale` с текстом и кнопкой «Перечитать»; `app/src/lib/api/admin.ts` — тело `PUT` с `version`; `app/src/lib/i18n.en.ts`; тесты `app/src/lib/audit26.test.tsx` |
| Бэк | `backend/src/routes/admin.ts` — хелпер `categoriesVersion(client)`, `version` в `GET`, проверка в `PUT` под `pg_advisory_xact_lock`, 409 `categories_stale`, `version` в ответе; тесты `backend/test/audit27.test.ts` |
| БД | **без изменений** (версия — отпечаток содержимого) |
| Контракт | v0.27.0 (общая итерация): `AdminCategories.version`, тело `PUT` + `version?`, `CategoriesUpdated.version`, `409` у `PUT` |

## Ворота инвариантов

| Инвариант | Что нарушаем | Зачем | Почему нельзя иначе |
|---|---|---|---|
| — | нарушений нет | | |

- **§5.11.** Гонка двух сохранений закрывается транзакционной advisory-блокировкой и сравнением отпечатка — это
  проверка состояния в транзакции (как `for update` у анкеты), не инвариант данных.

## Контракт

1. `AdminCategories` + `version: string` (16 шестнадцатеричных знаков; описание: отпечаток содержимого, меняется от
   любой правки справочника, включая правки мимо панели).
2. Тело `PUT /admin/categories` + `version?: string` — «версия, с которой начата правка; не совпала — 409
   `categories_stale`, и не меняется ничего; без поля — без проверки».
3. `CategoriesUpdated` + `version: string` — новая версия после сохранения.
4. `PUT /admin/categories` + `'409': Conflict`.

## Хранение

- `categoriesVersion(client)`: `select id, name, icon, sort from categories order by id` и
  `select word, category_id from category_synonyms order by word` → каноничная строка JSON → `sha256` (`createHash` из
  `node:crypto`, уже используется в `deals/idempotency.ts`) → первые 16 hex. Порядок отпечатка — по `id`/`word`, а не как в
  `GET` (`sort, name`): отпечатку важна детерминированность, а не порядок показа (сверка K08).
- `GET`: считает версию тем же клиентом, что читает данные (одна транзакция или один клиент подряд — данные и
  версия из одного момента; проще — в транзакции `db().tx`).
- `PUT`: в транзакции первым делом `select pg_advisory_xact_lock($1)` с **фиксированной константой** `4210001`
  (advisory-блокировок в проекте раньше не было; ключ глобален на кластер, который делят тесты и dev-сервер — поэтому
  константа названа в коде и в этом плане, а не вычисляется `hashtext`; сверка K06), затем при наличии `body.version` —
  `categoriesVersion(client)`; не совпало → `conflict('categories_stale', 'Справочник изменили, пока вы его правили — перечитайте и повторите')`;
  дальше как сейчас; в конце — новая версия в ответе.
- Схема тела обработчика `PUT` (`admin.ts`, `additionalProperties: false`) получает `version: { type: 'string', maxLength: 64 }` —
  без этого панель получит отказ схемы (сверка K01).
- Существующие тесты `backend/test/audit23.test.ts:331` и `:658` сравнивают ответ `PUT` строго (`toEqual({categories, synonyms})`) —
  правятся под `version` в ответе (сверка K02).

## Решения

| Решение | Почему | Что отклонили и почему |
|---|---|---|
| отпечаток содержимого, а не счётчик и не `updated_at` | без миграции; правки мимо панели и тесты, пишущие в таблицы напрямую, тоже меняют версию | `updated_at` — колонка и триггер (миграция); счётчик по `audit_log` — не видит правок мимо API |
| версия в теле `PUT`, а не `If-Match` | клиент фронта не умеет ни слать произвольные заголовки, ни читать заголовки ответа; тело — уже типизированный путь | заголовки — правка клиента и контракта ради одного места |
| advisory-блокировка на транзакцию | две одновременных записи с одной версией — одна проходит, вторая видит новую версию | `for update` по всем строкам двух таблиц — тяжелее и не ловит вставки |
| «Перечитать» заменяет черновик, с предупреждением | слияние — вне границ; честнее сказать, что правки пропадут, чем молча их слить | автослияние — новая подсистема |
