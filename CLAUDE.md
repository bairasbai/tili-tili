# Тили-тили — инструкция для агента

PWA-планировщик свадьбы. Текущее состояние определяют код выбранной ветки, `session-handoff.md`, `tasks/todo.md` и приёмка конкретной фичи. История старых этапов — в `JOURNAL.md`; она не доказывает готовность нынешнего плана. Полный план и критерии каждого WP — `tasks/wedding-platform-master-plan/`.

Фронт: React 19 + TypeScript + Vite 7 + Tailwind 3 + shadcn/ui, react-router 7, vitest 4.
Бэк: Node 22 + Fastify 5 + TypeScript, PostgreSQL 16, Redis 7. Хостинг — Timeweb Cloud, площадка в РФ.

---

## 1. Старт сессии

1. Проверить локальные `git status --short`, ветку и последний коммит. Прочитать `session-handoff.md` и активный блок `tasks/todo.md`. Незакоммиченные правки другого агента сохранять; пересекающуюся работу выполнять в отдельном worktree.
2. Перед обращением к GitHub выполнить `node ~/.claude/hooks/github-api-guard.js --status`. При паузе или 403/429/rate limit/abuse/Bad credentials остановить обращения и сообщить владельцу. Запросы строго последовательно; не использовать watch и частый опрос CI.
3. В начале исполнения, перед новым WP и перед слиянием сверить актуальный GitHub main одним разрешённым fetch. При недоступном GitHub прямо указать, что свежесть main не подтверждена. Не подменять работающую ветку и не выполнять reset/clean для «синхронизации».
4. Выбрать один незавершённый пункт текущего реестра. Сначала проверить существующий код и результаты приёмки: не повторять уже выполненный блок. Не переписывать весь реестр после каждого теста.
5. Открыть нужный раздел `ERRORS.md` и документы §2. Старые отчёты использовать для поиска, нынешний результат подтверждать текущими файлами и проверками.

## 3. Особенности окружения — читать до первой команды

**Зависимости и Node.** CI использует Node 22 и pnpm 10.34.5 (`.github/workflows/ci.yml`). Сначала проверить версии и исправность установленного окружения; использовать существующие зависимости, если lock-файлы не менялись. Для установки применять закреплённый pnpm и `--frozen-lockfile --node-linker=hoisted`, как в CI. Историческая ошибка npm/Node 25 — ERR-0006; не считать её диагнозом любой новой ошибки.

**Лок-файлы.** В app изменения зависимостей согласуют `package-lock.json` и `pnpm-lock.yaml` через `pnpm import`; в backend основной — `pnpm-lock.yaml`. Не редактировать lock-файлы руками и не обновлять зависимости ради формальной «свежести».

**Общие службы имеют одного владельца.** Тесты и dev-сервер могут использовать одну базу. Полный прогон бэкенда при поднятом сервере и живой проверке в браузере даёт ложное красное: тесты на гонки, лимиты и OTP падают от чужой нагрузки и съеденной квоты (ERR-0158, R-177). Порядок такой: сначала прогон, потом живая проверка. Красное рядом с работающим сервером — повторить в одиночку, и только потом чинить.

**Имена файлов.** Раньше были повреждены (UTF-8 прочитан как CP866 при распаковке архива) — исправлено 2026-09-02, см. ERR-0007. Если снова появятся имена вида `╨в╨╕╨╗╨╕…` — значит, архив распаковали неправильной программой.

## 4. Команды

Общий гейт из корня проекта. Для приёмки нужны также сценарии фичи, требуемая браузерная проверка и актуальное ревью (§6):

```bash
bash init.sh        # зависимости при необходимости, затем типы → тесты → линт → сборка
```

По отдельности, из папки `app`:

```bash
npm test                                    # vitest — главный гейт
node node_modules/typescript/bin/tsc -b     # типы
node node_modules/eslint/bin/eslint.js .    # линт
node node_modules/vite/bin/vite.js build    # прод-сборка
```

Если бинарники в `node_modules/.bin` пропали (последствие сломанного npm) — запускать напрямую:
`node node_modules/vitest/vitest.mjs run`.

Бэкенд, из папки `backend`. Переменные окружения лежат в `.env` (в репозиторий не
попадает, шаблон — `.env.example`). Если его нет, сервер не стартует и жалуется на
секреты: заведи из шаблона, секреты сгенерируй любые — это локальная машина.

```bash
npm run dev            # сервер на 127.0.0.1:3001, переменные берёт из .env
npm run migrate up     # накатить схему на пустую базу
```

**Backend: сначала проверить тестовое подключение и владельца служб.** `TEST_DATABASE_URL` и `TEST_REDIS_URL` берутся из согласованного тестового окружения. Проверить host, port, имя базы, схему и отсутствие конкурирующего прогона. Guard для экосистемы — `backend/test/disposablePgPort.ts`; CI показывает отдельный PostgreSQL на 15432. Это не разрешение занять службы текущего root. Нельзя автоматически выбирать системную базу на 5432, пересоздавать существующие базы, сбрасывать схему или отключать guard.

```bash
# Только после проверки согласованных TEST_DATABASE_URL / TEST_REDIS_URL:
node node_modules/vitest/vitest.mjs run
node node_modules/typescript/bin/tsc -p tsconfig.json --noEmit
node node_modules/eslint/bin/eslint.js .
node scripts/gen-contract.mjs && node scripts/gen-schemas.mjs  # после правки контракта
```

Прогон с пропущенными интеграционными тестами не подтверждает поведение базы, Redis, денег и прав доступа. Число passed/skipped, окружение и exit code брать из свежего вывода. Не копировать старые числа тестов в статус новой версии.

Тестовое окружение фронта живёт в `vitest.config.ts` и `src/test/setup.ts`: чинит `localStorage` (Node 25 подсовывает свою заглушку поверх jsdom), `IntersectionObserver` и `scrollTo`. **Не удалять** — без него падает больше половины набора.

Результат проверки привязывать к проверенному коммиту или содержимому файлов, конфигурации и окружению.

## 5. Инварианты — нарушать нельзя

1. **R-MAP / R-BTN.** Изменил экран или кнопку — обнови `Карту экранов` и `Карту кнопок` **в той же итерации**, с записью в журнал внизу файла. Не «потом».
2. **i18n.** Ключ словаря — русская строка. В хранилище и в состоянии лежит **русский ключ**, перевод — только при рендере через `t()`. Хардкод UI-строк вне `t()` запрещён (R-07).
3. **Сериализация.** Снятое значение хранится как `null`, не как отсутствующее поле: `undefined` исчезает при `JSON.stringify`, и отменённая бронь «воскресает» после перезагрузки.
4. **Чистота рендера.** `Date.now()`, `Math.random()`, объявление компонентов — запрещены в теле компонента (линт `react-hooks/purity`, `static-components`). Время — через `useState(() => Date.now())`, случайное — в обработчике события, компоненты — на уровне модуля.
5. **Мёртвых элементов нет — и «живых» тоже.** Кликабельный элемент без обработчика запрещён. Обработчик, который меняет ТОЛЬКО экран, запрещён так же: либо за кнопкой запрос, либо кнопки нет (R-176). Проверять по следу на сервере, а не по тому, отзывается ли нажатие. Любое «назад» — через `goBack()` с fallback-роутом. Генераторы документов интерполируют строки, а не вставляют код.
6. **Дизайн-токены** из плана ч. 10.2. Хардкод цветов вместо переменных — повод отклонить правку (R-01).
7. **Деньги** — целые рубли на фронте. Формат — через `Intl.NumberFormat`.
8. **PLAN.md не меняется молча.** Конфликт с планом → запись в `JOURNAL.md` и вопрос владельцу (R-15).
9. **Контракт — источник правды для бэка.** Правка `openapi.yaml` → `gen-contract` и `gen-schemas` в той же итерации. Сгенерированные файлы коммитятся, руками не правятся; тесты сверки падают при расхождении.
10. **404 и 501 — разные ответы.** `404` — адреса нет. `501` — путь контракта есть, обработчика пока нет. Путь контракта не должен отвечать 404 никогда.
11. **Инварианты — в ограничениях БД, не в коде обработчика.** Гонки за дату, подарок и место в автобусе закрываются `PK`/`UNIQUE`/`CHECK`. Логики в ORM-хуках нет: это условие дешёвого разворота на другой язык (план §1).
12. **Настройка живёт там, где живёт действие.** Управляет поведением сервера — значит, хранится на сервере (R-173). Локально держим только то, что и правда свойство устройства: тема, язык, факт онбординга, черновик до входа.
13. **Ноль — это не «неизвестно».** Счётчик, сумма и процент показываются только вместе с ответом сервера; пока ответа нет — прочерк или ничего (R-178). `?? []` в подсчёте — признак того, что экран не различает «пусто» и «не пришло». Состояние загрузки хранится явно, а не выводится из длины результата (R-179). Индикатор, значок и код — такие же утверждения, как число: «горит всегда» — не состояние (R-180).
14. **Согласие — подпись под текстом, а не под числом.** Если сервер проверяет версию документа, а текст живёт у клиента, версию называет и клиент — и сверяет со своей; расходятся — согласие не даётся (R-181). Вход это пара «токены + согласие»: не удалось второе — снимается первое (R-182).
15. **Ничего не обещать за код.** Утверждение о деньгах, гарантиях, проверках и безопасности ставится на экран, только если под ним есть реализация (R-174). Заглушка отвечает «я пока не умею», а не правдоподобным содержанием (R-172).
16. **Секреты — только в переменных окружения.** В репозитории лежит `.env.example` без значений. `.env` не коммитится никогда.

## 6. Рабочий цикл

1. **План.** Нетривиальная задача (3+ шага или архитектура) — сначала план в `tasks/todo.md` чекбоксами. Сверить план до старта реализации. **Крупная фича** — новая подсистема, 3+ экрана, деньги, необратимое — идёт по циклу из `Тили-тили_Спека_фичи.md`: спека → вопросы → план → задачи → сверка. Порог там же, §1; в `todo.md` от такой фичи остаётся одна строка со ссылкой на её папку.
2. **Одна задача — один фокус.** Отмечать пункты по ходу, коротко объяснять изменения.
3. **Верификация до «готово».** Сначала быстрые типы/генерация/проверка оснастки, затем целевые тесты и ревью, затем полный обязательный прогон типов, тестов, линта, сборки и сценарии фичи в браузере. Сохранить команды, exit code и результат. Для изменения только фронтенда проверить весь фронтенд; неизменённый backend не считать заново проверенным. Для полной приёмки WP выполнить все его гейты, включая backend с нужными службами.
4. **Регрессия обязательна.** Закрыл дыру — закрепи тестом, который падал бы до фикса.
5. **Уроки.** Найденная и исправленная ошибка → запись в `ERRORS.md` с правилом на будущее. Значимое решение с альтернативами → `JOURNAL.md`.
6. **Баг-репорт чиню сам.** Не спрашивать «а где именно» — искать по логам, падающим тестам, коду.
7. **Гейты unlazy до работы.** Существенная задача (3+ шага, фича, ревью, живая проверка) начинается с ledger'а
   `GATES.md` по шаблону `~/.claude/skills/unlazy/templates/gates-leaf.md` — в `C:\Тили-тили\.unlazy\<задача>\GATES.md`
   (cwd сессии — `C:\Тили-тили`, там Stop-хук и ищет ledger; в репозиторий он не попадает). Гейты — наблюдаемые исходы с
   `CHECK:`/`EXPECT:` из реальных команд §4 (`bash init.sh` → `OK — фронт и бэк`, целевые `vitest`), `CWD:` — относительно
   `C:\Тили-тили` (например `Тили-тили_код_и_документация/Тили-тили/app`); записи §7 — ручными гейтами. Команды сначала
   `--status`, потом `--approve`, «готово» — только `ALL MET` от `gate-check.mjs`; глобальный Stop-хук блокирует
   остановку, пока гейты не выполнены. Невозможный гейт — `ABANDON: G<n> <причина>` и передача в handoff, а не тишина.

### Не повторять проверки без причины

- После правки кода, контракта, схемы, зависимостей или конфигурации заново выполнить затронутые проверки; перед приёмкой — требуемый полный гейт на итоговой версии. Миграции требуют своего drill.
- После исправления теста сначала подтвердить конкретный сценарий, затем повторить полный набор, если тест входит в обязательный гейт.
- После интеграции или разрешения конфликтов проверить итоговый код; не складывать результаты несовместимых версий в один «зелёный прогон».
- Правка только документации: проверить diff и ссылки; результат проверки неизменённого кода можно сохранить с явным указанием исходной версии. Сам commit или push не меняет проверенное содержимое; CI привязать к опубликованному SHA.
- Повторный прогон нужен при изменении проверяемого содержимого/окружения, сбое или новом риске. В отчёте указать причину повторения. Сохраняются все обязательные сценарии и ревью; экономится повторение одинаковой работы.
- Использовать существующую оснастку, журналы и один текущий реестр. Не создавать новую систему отчётов или вспомогательный скрипт, если существующее средство покрывает задачу. Длинный лог хранить файлом, в разговоре давать результат и следующую проверку.
- При запросе на публикацию: отдельный содержательный коммит фичи → push → PR → проверка CI итогового SHA → слияние в актуальный main и сверка результата. Без отдельного разрешения не выкладывать в production.

## 7. Конец сессии

Перед тем как закончить — три записи, иначе следующая сессия начнётся с археологии:

1. `tasks/todo.md` — отметить сделанное, оставить один явный «следующий шаг».
2. `JOURNAL.md` — что сделал, почему именно так, какие альтернативы отклонил.
3. `session-handoff.md` — перезаписать целиком: состояние проверок, что изменено и не закоммичено, блокеры, следующий шаг.

Если по пути была ошибка — она уходит в `ERRORS.md` с правилом на будущее, а не только в чат.

## 8. Субагенты

Субагенты используются при разрешённом делегировании и полезной независимой задаче. Небольшую правку выполнять одним агентом. У каждого помощника — точные файлы, критерии и запрет трогать общие службы. Для существенного поведения или безопасности — свежее независимое ревью; root проверяет фактический diff и интегрирует результат. Не поручать двум агентам один участок.

## 9. Базовые принципы

- **Простота.** Каждое изменение — минимально возможное. Меньше кода лучше.
- **Без лени.** Корневая причина, а не временная заплатка.
- **Минимальное воздействие.** Трогать только необходимое. `app/src/components/ui/*` — вендоренный shadcn/ui, не править без причины.

## 10. Открытые вопросы — решать с владельцем, не молча

**Полный список хвостов — в `tasks/todo.md`, раздел «Хвосты».** Там же причина каждого и то, кто его закрывает. Коротко:

## 11. Разработка и приёмка PWA

1. Проверять production-сборку на HTTPS (локально допустим localhost). В dev service worker отключён: успешный Vite dev не подтверждает offline или обновление установленной PWA.
2. Манифест и иконки должны работать от корня и подпапки. Не менять идентичность установленного приложения без проверки миграции: относительный `id` разрешается от origin start_url, а при отсутствии id действует start_url. Установку и вид иконок подтверждать на целевых Android/iOS; отсутствие beforeinstallprompt на iOS не считать поломкой.
3. Кэшировать только собственную статическую сборку и оболочку. API, токены, пользовательские файлы и ответы с HTML вместо JS не помещать в CacheStorage. Не сохранять redirected/error ответы под адресом файла сборки. Фоновую запись в кэш держать через event.waitUntil; отказ квоты не должен терять уже полученный сетевой ответ.
4. Критические offline chunks брать из фактической сборки (`app/build/criticalAssets.ts`). Неполная установка worker должна отказать без активации; cache version зависит от сборки. Удалять только собственные старые кэши своего scope. sw.js и HTML — no-cache, хешированные assets — immutable (`deploy/nginx.conf`).
5. Обновление требует явного согласия пользователя и предупреждения о несохранённых изменениях. Проверить ожидание нового worker, обновление и перезагрузку нескольких вкладок; не включать безусловный skipWaiting для последующих версий.
6. Offline-копии приватных данных — минимальные, с временем чтения, областью пользователя/сессии/свадьбы и очисткой при выходе, смене аккаунта и подтверждённом отзыве доступа. Отсутствие сети не является разрешением на запись или доказательством действующих прав. Offline ограничен реализованными сценариями, а не всем приложением.
7. Для изменений worker/manifest/offline выполнить целевые регрессии, весь фронтенд (типы/тесты/линт/production build), затем браузерные сценарии: первый запуск онлайн → offline reload/deep-link → возврат сети; обновление; выход/смена аккаунта. Физическую установку, push, HTTPS и заголовки на production подтверждать отдельным наблюдением; unit-тесты этого не доказывают.
