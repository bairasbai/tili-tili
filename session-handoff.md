## Как поднять окружение для ручной проверки

Бэкенд стартует без `.env` — он не хранится в репозитории. Переменные передаются
процессу; готовый скрипт для локальных проверок лежал в скретчпаде сессии, его
содержимое воспроизводится по `.env.example`. Обязательный минимум:

```
PORT=3001 HOST=127.0.0.1 DATABASE_URL=postgres://tili:tili@localhost:5432/tili
JWT_ACCESS_SECRET=<48+ символов> JWT_REFRESH_SECRET=<48+ символов>
POLICY_VERSION=2026-09-02 OTP_MAX_PER_HOUR_TOTAL=100000
```

Последняя строка важна для ручных проверок: заводской лимит на отправку кодов
упирается в первый же прогон, и вход перестаёт работать с `too_many_requests`.
Код подтверждения при пустом `SMS_PROVIDER` уходит в лог процесса — оттуда его и
берут при проверке в браузере.

Фронт — `app`, порт 3000, `/api` проксируется на `127.0.0.1:3001`.

**Смена секретов гасит все выданные токены.** После перезапуска бэкенда с новыми
секретами в браузере нужно войти заново, иначе запросы отвечают
«Сервер не настроен для проверки токенов» или 401.

## Следующий шаг

**Этап 7 — гостевые сценарии по токену.** Файлы: `app/src/pages/Invite.tsx`,
`app/src/pages/Logistics.tsx`. Гость по ссылке отвечает на RSVP без входа в аккаунт,
и ответ виден паре в списке гостей; туда же опрос по меню, шаттлы и отели.

Осторожно с одним местом: сырой `guestToken` паре не отдаётся никогда — иначе пара
откроет гостевую страницу и увидит резерв подарка, что ломает анонимность (§9
бизнес-логики). Пара получает одноразовую ссылку, которая гаснет при первом открытии.
