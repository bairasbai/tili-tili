# Тили-тили — Бизнес-логика и задание на бэкенд

> Документ для ИИ-разработчика / команды бэкенда. Описывает продуктовую логику PWA «Тили-тили» (tili-tili.ru) так, как она реализована во фронтенде на моках. **Источник правды по API — `Тили-тили_API_openapi.yaml`** (48 эндпоинтов, 25 схем). Этот файл объясняет *почему* и *как* всё работает, openapi — *в каком формате*.
>
> Фронтенд: React 18 + TypeScript + Vite + Tailwind, SPA, моки в `src/lib/data.ts`. Первый город — Уфа. Языки: RU (ключ-источник) и EN.

---

## 1. Продукт в одном абзаце

«Тили-тили» — свадебный планировщик «всё в одном» для пар в России/СНГ. Пара проходит квиз, получает план свадьбы: каталог подрядчиков по 25 категориям, «команду» из слотов (площадка, фотограф, …), бюджет с лимитами, чек-лист по месяцам, гостей с RSVP и рассадкой, приглашения-сайты, договоры, чаты, тайминг дня X и режим «День X». Подрядчики имеют свой кабинет (анкета, лиды, сделки, отзывы, аналитика). Встроен ИИ-координатор «Тиль», который даёт проактивные советы. Монетизация: комиссия со сделок + премиум-функции (реферальная программа начисляет бонусы на премиум).

## 2. Роли

| Роль | Кто | Доступ |
|---|---|---|
| `couple` | Молодожёны (владельцы свадьбы) | Полный: бюджет, сделки, оплаты, всё |
| `helper` | Помощник (друг/родственник), приглашён по ссылке | Орг-разделы (чек-лист, гости, тайминг), **без бюджета и сделок** |
| `coordinator` | Координатор свадьбы (профи, нанят парой) | **Командует днём X**: тайминг и план Б, чаты со всеми подрядчиками, чек-лист, гости. **Без бюджета, сделок и оплат** — финансы только у пары |
| `vendor` | Подрядчик | Свои сделки, лиды, чаты, анкета, отзывы, аналитика |
| `guest-vendor` | Гость-подрядчик (свой, не из каталога) | Только дата/тайминг/чат своего слота — по ссылке-приглашению, без регистрации (§11) |
| `guest` | Гость | Только RSVP по ссылке приглашения `/join/:code`, без аккаунта |

Одна свадьба = одна пара (`couple`, 2 человека на аккаунте) + N помощников + N подрядчиков (через сделки) + N гостей.

## 3. Доменная модель

### 3.1 Пользователь и свадьба
- **User**: id, phone (`+7 …`, вход по SMS-коду), name, role, lang (`ru|en`), theme (`light|dark`), city+region, push-настройки (4 тумблера: дедлайны задач / сообщения / сделки и оплаты / советы ИИ), тихие часы (дефолт 22:00–09:00, **в день X отключены автоматически**), сессии (устройства).
- **Wedding** (создаётся квизом): date (ISO `2027-06-14`), city, venue, style (`Люкс` и др. из квиза), guestsTotal (80), budgetTotal (1 200 000 ₽), bride/groom names.
- Производные на фронте: `daysLeft` = date − today; `guestsConfirmed`; `teamBooked/teamTotal` (слоты); `budgetSpent` = Σ оплаченных сделок + ручные расходы. **На бэкенде считать на лету, не хранить.**

### 3.2 Каталог
- **Category**: 35 категорий (id: `photo, video, venue, host, dj, florist, decor, stylist, catering, light, cake, transport, dress, suit, rings, print, photobooth, firework, reels, painter, nanny, bar, dance, agency, rental, ceremony, hair, coordinator, show, staff, accessories, hotel, honeymoon, vykup, registrar`). Список фиксированный, с эмодзи-иконками; `count` — число анкет в городе (считать).
- **Vendor** (анкета подрядчика): id, name, categoryId, rating (0–5, 0 = новичок), reviews (число), priceFrom (₽, integer), years, desc, photos[], hasVideo, freeOnDate (вычисляется по календарю занятости относительно даты свадьбы!), isNew (< 3 сделок), packages[] — `{ name, price, items[] }` (2–3 тарифа).
- **Review**: vendorId, author (пара), rating, text, date, ответ подрядчика.
- **Favorite**: userId + vendorId.
- **Note**: заметки пары (текст, привязка к vendorId опционально).

### 3.3 Команда свадьбы — слоты (ключевая сущность)
**Slot** = позиция в команде: `{ id, categoryId, label, icon, state, vendor?, price?, status? }`.

Слот — это место в команде. Он либо пуст, либо занят сделкой; собственных состояний у него всего два, а всё остальное — состояние сделки (§3.4):

```
empty ←→ занят сделкой (состояние сделки см. §3.4)
```

- `empty` — исполнителя нет: не ищем или ещё не выбрали.
- занятый слот отражает текущее состояние своей сделки; отмена в любой момент возвращает слот в `empty`.

Во фронтенде слот дополнительно хранит поле `state` с укрупнёнными значениями (`empty | candidate | hold | booked`) — это проекция для мозаики команды, а не отдельная машина состояний. Источник правды — состояние сделки.

Дефолтный набор из 12 слотов создаётся после квиза (venue, photo, video, host, florist, cake, stylist, dj, decor, transport, dress, rings); пара может добавлять/убирать. `teamTotal` сейчас 14 в моке профиля — допустимо больше 12.

### 3.4 Сделка (Deal/Booking)

Сделка = слот × подрядчик.

**Шесть состояний** — решение владельца 2026-09-02, канонический список из Плана §8.1. Раньше документы описывали сделку по-разному (здесь — четыре состояния, в Плане — шесть); теперь список один, и его же показывает экран сделки.

```
candidate → contacted → negotiating → booked → paid_deposit → done
     ↑___________|____________|__________|            |          |
                     (отмена возвращает слот в empty) |          |
```

| Состояние | Что произошло | Что видит пара |
|---|---|---|
| `candidate` | Подрядчик добавлен в слот как кандидат | «Кандидат» |
| `contacted` | Пара написала, диалог открыт | «Написали» |
| `negotiating` | Обсуждаются условия и цена | «Переговоры» |
| `booked` | Дата закреплена, договор подписан | «Забронировано» |
| `paid_deposit` | Внесён аванс | «Аванс внесён» |
| `done` | Услуга оказана, можно оставить отзыв | «Выполнено» |

**Мягкая бронь (hold 72 ч) — не отдельное состояние**, а срок жизни этапа `negotiating`: дата держится за парой без оплаты 72 часа (см. §18.3 Плана). По истечении — автоматический возврат в `candidate` (нужен scheduled-job) и push за 12 часов до истечения.

**Отмена** парой: возврат по правилам договора, сделка → `cancelled`, слот → `empty`. Все мутации оплаты идемпотентны (`Idempotency-Key` header, см. openapi).

**Деньги — минорные единицы.** Решение владельца 2026-09-02: суммы передаются и хранятся в **копейках** (`integer`) вместе с кодом валюты по ISO 4217 (`RUB`). Целые числа не копят ошибку округления, а дробный рубль в JSON — источник расхождений на копейку между фронтом, бэкендом и платёжным шлюзом.

Пример: `{ "amount": 8500000, "currency": "RUB" }` — это 85 000 ₽.

Показ пользователю — рубли, через `Intl.NumberFormat`. На фронтенде это уже так: единицы вносятся через `rub()`, печатаются через `fmt()` (`src/lib/money.ts`).

### 3.5 Бюджет
- 5 категорий расходов (фиксированные): `Площадка и кейтеринг`, `Фото и видео`, `Одежда и красота`, `Развлечения и декор`, `Прочее` — у каждой `limit` (план) и `amount` (факт = Σ сделок категории + ручные расходы).
- Ручные расходы: пара добавляет свои (название, сумма, категория), может удалять **только свои** ручные записи, не сделки.
- Процент освоения = amount/limit; предупреждение при > 85% лимита (используется ИИ-координатором).
- **Лимит и резерв (018-B, ветка ревью 2026-09-26).** Лимит категории — автоматическая доля общего бюджета или сумма,
  заданная парой (`budget_category_limits`: сумма в копейках, `currency` = RUB, версия, `is_custom`); сброс к автоматической
  доле строку не удаляет, а поднимает версию — клиент со старой версией не «воскресит» снятый лимит. Резерв — доля бюджета
  в базисных пунктах 0–5000, по умолчанию 1000 (`wedding_budget_settings`, версия). Резерв не расход и не категория:
  он уменьшает «свободно». Правит только пара; запись берёт свадьбу `FOR UPDATE`, затем перепроверяет права.
- **График платежей (018-A).** Этап оплаты (`payment_installments`): сделка, название, сумма, валюта, срок 2000–2100,
  версия, отмена с причиной, `paid` — сумма привязанных отметок (возвраты со знаком минус, отменённые не считаются;
  ведёт триггер, CHECK держит в [0; сумма этапа]). Отметка оплаты (`payments`) привязывается к одному этапу своей
  сделки или ни к одному. Статус этапа: `pending` → `partial` → `paid`; `covered` — закрыт неразнесёнными деньгами
  сделки (они ложатся на этапы по сроку); `cancelled`. Этап не создаёт расхода и не увеличивает смету; отмена сделки
  отменяет её этапы; даты этапов не следуют за переносом свадьбы. `spent` бюджета — по-прежнему цены обязательств,
  а не оплаты (двойного учёта нет).
- **Подтверждение оплаты (018-B).** Файл PDF/JPEG/PNG/WebP до 512 КиБ к отметке оплаты (`payment_receipts`, до 5 на
  отметку, квота свадьбы 50 файлов / 25 МиБ), тип — по содержимому. Видит и удаляет только пара; автор обнуляется при
  стирании аккаунта, файл остаётся у свадьбы. Хранение в базе включает владелец (`RECEIPTS_STORAGE=db`); это файл пары,
  а не проверка банка.

### 3.6 Чек-лист (Task)
`{ id, title, done, due, period, urgent }`. `period` ∈ `9 | 6 | 3 | 1` — за сколько месяцев до свадьбы. 12 дефолтных задач генерируются квизом по дате свадьбы (due считается от даты); `urgent` = просрочено или < 2 недель. Фронт показывает прогресс `done/total` (21%).

### 3.7 Гости и рассадка
- **Guest**: `{ id, name, status: yes|no|pending, plus: bool, table?: number }`. Статус циклически меняется тапом (yes→no→pending). `plus` = «+1».
- RSVP приходит по ссылке приглашения (роль `guest`, без аккаунта): гость открывает сайт-приглашение → жмёт «Подтвердить/Отклонить» → статус обновляется.
- **Table**: рассадка — столы с capacity, гости назначаются на столы. Финальная рассадка — задача чек-листа за 1 месяц.

### 3.8 Приглашения (Invite)
- 10 тем оформления (`inviteThemes.ts`): у каждой id, name, desc, emoji, тип открытия (`curtains | doors | lift | fade` — анимация стартового экрана), палитра (overlay/ink/bg/card/accent).
- Пара выбирает тему + редактирует текст приглашения (дефолтный текст есть) → получает публичную ссылку `/join/:code`.
- Публичная страница: стартовый экран с анимацией → история пары → программа дня → кнопки RSVP → (после «Да») детали: дресс-код, карта, трансфер.
- Хранить: weddingId, themeId, customText, code (короткий уникальный), stats (просмотры/RSVP).

### 3.9 Тайминг дня (Timeline)
События `{ id, icon, name, loc, time ("08:00 — 13:00"), who }`. Дефолтный автоплан из 6 событий (сборы невесты/жениха, доставка деталей, церемония, банкет, финал). **Бизнес-правило для ИИ**: пустой слот «Флорист» блокирует автоплан (букет нужен к сборам) — подобные зависимости отражены в советах.

### 3.10 Договоры (Documents)
6 шаблонов (фотограф, площадка, ведущий, декор/флорист, кондитер, универсальный). Wizard генерирует HTML-текст договора из данных свадьбы и сделки (стороны, дата, г. Уфа, сумма, «подписан обеими сторонами»). На бэкенде: шаблоны с плейсхолдерами, версионирование, статус подписи (draft/sent/signed), PDF-генерация.

### 3.11 Чаты
Три вида (`kind`):
- `vendor` — пара ↔ подрядчик (создаётся при первом контакте/лиде; вложения: договор, презентация).
- `team` — общий чат команды свадьбы (пара + помощники + забронированные подрядчики).
- `day` — **«Чат дня X · гости»: открывается 13 июня в 09:00** (за день до свадьбы) — до этого заблокирован с подписью «Откроется …». Правило: `opensAt = weddingDate − 1 day, 09:00 local`.
Сообщения: `{ id, me, text, time, attachments? }`, непрочитанные (unread counter), typing-индикатор. Realtime — WebSocket/SSE.

### 3.12 День X (DayX) и «После свадьбы»
- **DayX**: режим на дату свадьбы — живой тайминг («идёт сейчас / далее»), статусы подрядчиков (напр. `едет · 20 мин`), быстрые действия (позвонить, чат, SOS-координатору). Тихие часы отключены.
- **After**: после даты — отзывы подрядчикам, сохранение воспоминаний (ссылки на фото/видео от вендоров), финальный расчёт.

### 3.13 Кабинет подрядчика (`/vendor-app`)
- **Profile wizard**: категория → пакеты (название/цена/состав) → портфолио (фото/видео) → календарь занятости.
- **Leads**: входящие заявки от пар (`lead` = интерес к дате; ответить → чат; отказ с причиной).
- **Deals**: сделки по этапам оплаты (зеркало §3.4).
- **Reviews**: отзывы, возможность ответить.
- **Analytics**: просмотры анкеты, конверсия лид→сделка, выручка по месяцам.

### 3.14 ИИ-координатор «Тиль»

**Иерархия управления днём X** (важно не путать роли):
1. **Пара** — владельцы: деньги, договоры, финальные решения.
2. **Координатор (человек)** — главный по логистике дня: командует подрядчиками в чате команды, правит тайминг, объявляет план Б. Подрядчики подчиняются ему по орг-вопросам, но не по финансам.
3. **Тиль (ИИ)** — помощник координатора и пары, а не замена: следит за дедлайнами и рисками, отвечает на типовые вопросы гостей, собирает статусы подрядчиков. Эскалация: Тиль → координатор → пара. В DayX кнопка SOS ведёт к человеку-координатору; Тиль остаётся второй линией.

Правила подсказок Тиля — **на бэкенде** (сейчас моки):
1. Дефицит категории: «Свободных подрядчиков категории X на дату осталось N» — когда N ≤ 6 и до свадьбы < 8 мес.
2. Блокирующий слот: пустой слот, от которого зависит тайминг (флорист → сборы 10:00).
3. Лимит бюджета: категория > 85% лимита → «зафиксируйте меню до …».
Чат-ассистент `/assistant` — диалог с Тилем (на бэкенде: LLM с контекстом свадьбы). Тиль — мужской персонаж («Тиль сказал»), в EN — "Til".

### 3.15 Инструменты и прочее
- **Калькулятор алкоголя** (`/tools/alcohol`): вход — число гостей, длительность банкета, предпочтения; выход — бутылки по типам. Чистая формула, может жить на фронте.
- **Вдохновение** (`/inspiration`): лента идей/фото по стилю свадьбы.
- **Карта площадок** (`/venues`): гео-поиск venue по городу.
- **Сравнение** (`/compare`): до 3 подрядчиков одной категории бок о бок (цена, рейтинг, пакеты).
- **Реферальная программа**: код `ТИЛИ-<ИМЯ>`; приглашённая пара → обеим 3 000 ₽ бонусами на премиум **после её первой сделки**. Хранить: код, приглашения, начисления.

## 4. Потоки пользователя (user flows)

1. **Онбординг**: 4 слайда → квиз (дата? город, стиль, гостей, бюджет) → `/auth` (телефон + SMS-код) → генерация свадьбы: 12 слотов, 12 задач чек-листа, 5 категорий бюджета, автоплан тайминга. `finishOnboarding`.
2. **Поиск и бронирование**: каталог → категория → список (фильтры: свободен на дату, есть видео, цена) → анкета → «Написать» (создаёт чат/лид) / «Забронировать» (hold 72 ч) → сделка → аванс → полная оплата. По машине состояний движется СДЕЛКА; у слота своего статуса нет — он либо пуст, либо несёт сделку (контракт v0.2, `Slot.deal`).
3. **Приглашения**: выбор темы → редактирование текста → публикация → ссылка `/join/:code` → гости RSVP → статусы в списке гостей → рассадка.
4. **Подрядчик**: регистрация → wizard анкеты → получает лиды → чат → сделка → выполнение → отзыв.
5. **День X**: автоматический режим в дату свадьбы. 6. **После**: отзывы, воспоминания, финальный расчёт.

## 5. Соответствие фронтенд-состояния и API

Сейчас всё состояние — localStorage/моки. При подключении бэкенда ключи заменяются API:

| localStorage / мок | Назначение | Замена |
|---|---|---|
| `tt_onboarded` | Прошёл онбординг | `GET /weddings/me` (404 = не прошёл) |
| `tt_lang` (`ru|en`) | Язык | `PATCH /users/me { lang }` |
| `tt_theme` (`light|dark`) | Тема | можно оставить локально |
| `tt_city`, `tt_city_region` | Город свадьбы | `PATCH /weddings/me { city }` |
| `tt_fav` (JSON array) | Избранное | `GET/PUT /favorites` |
| `tt_invite_tpl`, `tt_invite_text` | Тема и текст приглашения | `PATCH /invites/me` |
| `tt_slots` (store) | Команда: изменяемая часть слотов | `GET/POST/PATCH /weddings/me/slots` |
| `budgetItems`, ручные расходы | Бюджет | `GET /budget`, `POST /budget/expenses` |
| `tasks` | Чек-лист | `GET/PATCH /tasks` |
| `guests`, столы | Гости | `GET/PATCH /guests`, `/seating` |
| `chats`, `chatMessages` | Чаты | `GET /chats`, `WS /chats/:id` |

Смок-покрытие фронта: 43 роута (см. §6), 66 автотестов vitest — регрессионная сетка при интеграции.

- **Гео**: справочник городов РФ/СНГ (`src/lib/cities.ts` — поиск с подсказками, можно переиспользовать список); первый запуск — Уфа/Башкортостан.

## 9. Вишлист подарков (новое)

**Задача**: гости дарят нужное, без дублей, без неловких вопросов.

- **Gift**: `{ id, name, icon, price, desc?, group: bool, funded: number, reserved: bool }`.
- **Анонимность — ключевое правило**: пара видит только статус («Свободен» / «Зарезервирован») и прогресс складчины, но НИКОГДА не видит, кто зарезервировал. На бэкенде: таблица резервов хранит `guestToken` (анонимная сессия гостя по ссылке-приглашению), но API для пары его не отдаёт. Раскрытие — только если сам гость подписался в открытке.
- **Защита от дублей**: резерв атомарный (`reserved=false → true` одним запросом, unique constraint / conditional update). Занятый подарок недоступен остальным. Гость может снять СВОЙ резерв (по своему токену).
- **Складчина (group=true)**: дорогие подарки закрываются частями — `funded += amount` до `price`; при 100% подарок закрывается. Имена участников складчины тоже анонимны для пары.
- Доступ гостя — по ссылке приглашения `/join/:code` → вкладка «Подарки» (гостевой токен, без регистрации).
- Эндпоинты (добавить в openapi): `GET/POST/PATCH/DELETE /weddings/me/wishlist` (пара), `GET /gifts/:code`, `POST /gifts/:code/:giftId/reserve`, `DELETE …/reserve`, `POST …/fund { amount }` (гость).

1. **Денежный фонд / «конверт»** ✅ — сущность `Fund { id, name, icon, target, collected }`; пара заводит цели в /wedding/wishlist, гости анонимно вносят суммы в /gifts. Бэкенд: `POST /gifts/:code/funds/:id { amount }`, платёжный шлюз, выплата паре после дня X.

9. **Маркетплейс вишлиста** ✅ — «Купить в приложении» у свободных подарков: заказ оформляется, подарок резервируется, доставка паре. Бэкенд: заказы, платежи, логистика.

## 11. Свои (внешние) подрядчики — не из каталога

**Сценарий**: пара нашла фотографа на Авито / по знакомству — аккаунта в приложении нет. Подрядчик должен вписаться в команду, бюджет и тайминг, даже если приложение ему не нужно.

### Модель

- `Slot` расширен полями: `external?: boolean`, `invited?: boolean`, `phone?: string`.
- Внешний подрядчик НЕ является записью в каталоге (нет профиля, рейтинга, отзывов). Это привязка свободного исполнителя к слоту: `{ slotId, vendorName, price, phone? }` + `status = 'Свой подрядчик'` + флаг `external: true`.
- Состояние слота при этом — обычное `booked`: он участвует в сводке команды, бюджете и тайминге наравне с каталожными.

### Добавление (пара)

1. На пустом слоте (`/wedding/slot/:id`) — карточка «Свой подрядчик» с формой: имя, цена, телефон (опц.).
2. `bookExternal(slotId, vendorName, price, phone?)` → слот `booked`, `external: true`.
3. В карточке слота у внешнего бейдж «не из каталога», отображается телефон; кнопка отмены называется «Удалить подрядчика» (двухтаповая).

### Гость-подрядчик (без регистрации)

- Пара нажимает «Создать ссылку-приглашение» → ссылка вида `tili-tili.ru/guest-vendor/<token>` + кнопка копирования; `invited: true`.
- По ссылке человек входит как **гость-подрядчик** (отдельный scope токена, без регистрации в каталоге): видит дату, тайминг и чат с парой — и больше ничего.
- Бэкенд: таблица `external_invites { token, weddingId, slotId, expiresAt, acceptedAt }`; токен одноразового входа, JWT scope `guest_vendor`, TTL сессии (например, 30 дней), привязка к `slotId`.
- Если приглашённый захотел полноценный аккаунт — миграция гость-подрядчик → vendor (данные слота переносятся в сделку).

### Удаление

- `cancelBooking(slotId)` очищает `external/invited/phone` — слот возвращается в `empty`, приглашённый токен аннулируется на бэкенде.

### Эндпоинты (добавить в openapi)

- `POST /weddings/me/slots/:slotId/external` `{ vendorName, price, phone? }` — добавить своего.
- `POST /weddings/me/slots/:slotId/external/invite` → `{ token, url }` — ссылка-приглашение.
- `GET /guest-vendor/:token` — страница гостя-подрядчика (дата, тайминг, чат).
- `DELETE /weddings/me/slots/:slotId/external` — удалить своего подрядчика (токен аннулируется).

## 12. День X end-to-end: логистика, кейтеринг-опрос, рассадка, десктоп

Проход по идеальному дню (утро → отъезд гостей) выявил четыре пробела, теперь закрытых:

### 12.1 Логистика гостей (`/wedding/logistics`)

- **Трансфер (автобусы)**: `BusRoute { id, name, from, time, seats, taken, dealId, carrier }`. Пара заводит маршруты (точка сбора, время, места); гость при RSVP отмечает «нужен трансфер» и выбирает автобус — `taken` считает база по персонам (гость «с +1» — двое, фича 005), переполнение запрещено. Кнопка «Разослать точки сбора» — уведомление команде в приложении (гостям канала нет).
- **Перевозчик — подрядчик (фича 006)**: лимузин, общий автобус, частный перевозчик — это сделка в слоте «Транспорт» (каталог или свой подрядчик, цена, дата, чат, договор). Маршрут для гостей может ссылаться на такую сделку (`dealId`, необязательно): у маршрута появляется имя перевозчика (`carrier`, видят пара, команда и гость), в карточке сделки — «Маршруты для гостей» и кнопка «Добавить маршрут», в форме маршрута — выбор перевозчика, маршрут можно изменить (`PATCH`). Перевозчик в кабинете видит маршруты своей сделки и число записавшихся — без имён и телефонов гостей. Отмена сделки маршрут и записи гостей не трогает — «перевозчик убран». Лимузин пары — сделка без маршрута; своего типа транспорта у маршрута нет.
- **Отельный блок**: `HotelBlock { id, name, rooms, booked, pricePerNight, deadline, promo }`. Пара договаривается с отелем о блоке номеров со скидкой; гости бронируют по промокоду из приглашения до дедлайна; пара видит заполнение и НЕ платит за невыкупленные номера (блок тает к дедлайну). Эндпоинты: `POST/DELETE /weddings/me/logistics/buses`, `POST/DELETE …/hotels`, `POST …/notify-pickup`; гостевые: `POST /join/:code/shuttle { busId }`, `GET /join/:code/hotels`.

### 12.2 Опрос гостей по еде (`/wedding/catering`)

- `MenuPoll { question, options: [{ id, name, icon, votes }], sent }` — встроен в приглашение: гость отвечает на RSVP и одним тапом выбирает горячее (без регистрации).
- Сводка для кейтеринга: количество по каждому блюду + аллергии/пожелания (из RSVP+); авто-отправка кейтерингу за 14 дней до даты, правки до -7 дней (scheduled-job).
- «Напомнить» — пуш/SMS гостям, не выбравшим блюдо. Эндпоинты: `GET/PUT /weddings/me/menu-poll`, `POST /join/:code/menu-vote { optionId }`, `POST …/menu-poll/remind`.

### 12.3 Рассадка (`/wedding/seating`)

- Тап-сажание уже было; добавлено: **авто-расстановка** («Рассадить автоматически» — раскидывает гостей без стола по свободным местам; на бэкенде — с учётом ограничений «не сажать вместе» и семейных групп), **маркеры блюд** 🥩🐟🥦 у каждого гостя (связка с опросом меню — официант видит, кому что нести), легенда, PDF А3 для печати. Модель: `Table { n, capacity, guestIds[] }`, гость несёт `menuChoice`.

### 12.4 Десктоп и телефон — одно приложение

- Приложение адаптивное: на экранах ≥900px нижняя панель превращается в боковое меню, колонка контента расширяется до 1180px. Одна кодовая база, PWA — пара может начать на телефоне и продолжить на компьютере (после бэкенда состояние синхронизируется через аккаунт; сейчас — localStorage на устройстве).

### Что уже закрыто в дне X ранее

Live-тайминг и задержки (/dayx), SOS координатору, план Б, свои подрядчики без аккаунта (§11), RSVP+ (питание/трансфер), напоминания гостям, фотоальбом гостей, дресс-код, вишлист, алко-калькулятор, договоры и оплаты.

## 13. Плохие сценарии, защита сторон и устойчивость приложения

### 13.1 План Б (`/wedding/planb`) — риски дня X и готовые решения

По ресерчу свадебных форумов и гайдов (gorko.ru, weddywood, businessinsider и др.) собраны 10 самых частых сбоев — каждый закрыт механизмом приложения:

2. **Дождь/непогода** → план Б площадки согласуется при бронировании (пункт договора); активация одной кнопкой рассылает уведомления команде и новую точку сбора гостям.
3. **Отключение электричества** → генератор — обязательный пункт чек-листа площадки при бронировании.
4. **Отставание тайминга** → буфер 15 мин в каждом блоке + сдвиг тайминга одним тапом в /dayx с рассылкой команде.

6. **Пьяный гость/неловкий тост** → бриф ведущего (забрать микрофон), такси через координатора.
7. **Дети** → слот «Няня/аниматор» в каталоге; опция «18+» в приглашении.
8. **Незваные +1** → авто-запас +2 места/порции в сводке кейтеринга.
9. **Транспорт сломался/уехал не туда** → маршрут у водителя в приложении; резервный автобус/такси-контракт.
10. **Забыли кольца/паспорта** → чек-лист «накануне» отдаёт их свидетелям.

Плюс персистентный чек-лист накануне (`tt_planb`).

### 13.4 Устойчивость приложения (технические защиты)

**Фронтенд (реализовано):**
- Анти-даблтап `useBusy`: повторные нажатия во время операции игнорируются (оплата доплаты, добавление своего подрядчика); деструктивные действия — двухтаповые («Точно отменить?»).
- Офлайн-баннер: при потере сети — плашка «работаем офлайн, всё сохранится»; все данные persist в localStorage, ничего не теряется при перезагрузке.
- ErrorBoundary на всё приложение; навигация: кнопка «назад» на всех подэкранах (TopBar back), корневые разделы — в таббаре/сайдбаре.
- Телефон не греется: нет бесконечных поллингов и тяжёлых циклов анимаций (только CSS, transform/opacity), анимации отключаемы системным reduced-motion; бандл с чанк-сплиттингом Vite.

**Бэкенд (требования):**
- Идемпотентность: все POST (резерв, оплата, голос, RSVP) принимают `Idempotency-Key`; повторная отправка возвращает первый результат.
- Атомарность критичных переходов: резерв подарка, место в автобусе, номер в отельном блоке — conditional update/транзакция (нельзя занять дважды).
- Rate limiting: 10 req/s на токен, очередь на массовые рассылки (гостям/команде), дебаунс push-уведомлений (схлопывание серии правок рассадки в одно уведомление за 30 с).
- Деньги: двойная запись платежей, webhooks платёжного шлюза с подписью, эскроу-счета, возвраты только через исходный метод.
- WebSocket для живых обновлений с автопереподключением; превью-режим без WS — поллинг раз в 30 с.

Бэкенд-правила новых механик:
- **План от даты**: `weddingDate` в профиле свадьбы; этап вычисляется от неё; «следующий шаг» — первая невыполненная задача текущего этапа (задачи могут генерироваться шаблоном по типу свадьбы).
- **Бюджет**: `paid = Σ escrow_deposits`, `upcoming = Σ остатков по сделкам` с due=дата-7д; резерв 10% — рекомендательный, не блокирующий; алерт при `total + reserve > budgetTotal`.
- **Верификация**: `vendor.verified { fnsCheckedAt, dealsCount }`; бейдж показывается только при пройденной сверке; отзыв создаётся только по завершённой сделке (`dealId` обязателен, 1 отзыв на сделку).
- **Календарь**: `vendor_busy_dates` (источник — кабинет подрядчика + подтверждённые сделки); при бронировании дата атомарно закрывается; двойное бронирование одной даты невозможно (unique constraint vendor+date).

## 15. Отзывы гостей подрядчикам

**Зачем.** После свадьбы о работе команды могут сказать не только молодожёны: гости видят ведущего, кейтеринг и площадку «снаружи». Их отзывы — дополнительный сигнал качества, но они не должны смешиваться с отзывами пар (у пары — подтверждённая сделка, у гостя — впечатление участника).

**Правила.**
- Оставить отзыв может только гость с действующим токеном приглашения (`guestToken`), и только после даты свадьбы (`weddingDate < now`).
- Отзыв создаётся с `source='guest'`; UI везде показывает значок «Гость свадьбы». Отзывы пары идут с `source='couple'` + обязательным `dealId` и пометкой «сделка подтверждена». Два потока хранятся в одной таблице, но в рейтинге учитываются отдельными весами (отзыв пары весомее).
- Лимит: 1 отзыв на подрядчика на гостя (`unique(guestToken, vendorId)`); повторная отправка — редактирование.
- Молодожёны видят отзывы гостей анонимно (без имени гостя) на странице «После свадьбы»; подрядчик видит их в анкете рядом с отзывами пар, но с явной пометкой.
- Модерация: автофильтр мата/спама + ручная проверка по жалобе; подрядчик может ответить на отзыв, но не удалить.

**Эндпоинты (для openapi.yaml):**
- `POST /weddings/{id}/guest-reviews` — тело `{ vendorId, stars 1-5, text? }`, auth: guestToken; 409 при повторе.
- `GET /weddings/{id}/guest-reviews` — список для пары (анонимизированный).
- `GET /vendors/{id}/reviews?source=guest|couple|all` — публичная лента с пометкой источника.

**В приложении (моки):** форма «Как прошла свадьба?» на странице подарков (гостевая зона), список «Отзывы от гостей» у пары на «После свадьбы», пример отзыва с бейджем «Гость свадьбы» в анкете подрядчика.

## 16. Технический аудит UX-дыр (сентябрь 2026)

Глубокий автоматический аудит всего кода (скрипты поиска мёртвых кнопок + клик-шторм-тест: все 48 роутов, клик по каждой кнопке в 4 волны). Найдено и закрыто:

1. **Авто-тёмная тема по `prefers-color-scheme`** — главный баг со скриншота: на iPhone с тёмной системной темой приложение становилось тёмным без ведома пользователя. Теперь тёмная тема включается ТОЛЬКО явным переключателем в Настройках (`tt_theme === 'dark'`); в CSS `color-scheme: light` — системные контролы (инпуты, скроллбары) не темнеют.
2. **Мёртвые кнопки «Назад»** при входе по прямой ссылке (пустая история): `nav(-1)` ничего не делал. Введён хелпер `goBack()` (lib/utils.ts): если `history.state.idx > 0` — назад, иначе переход на fallback-роут. Применён в TopBar и на всех экранах с ручной кнопкой назад.
3. **Мёртвые подсказки AiTip**: 5 карточек выглядели кликабельными, но `onPress` не передавался. Теперь без обработчика рендерится обычный блок, а не кнопка.
4. **Копирование в буфер** молча падало вне HTTPS: хелпер `copyText()` с legacy-fallback (textarea + execCommand).
5. **Код приглашения команды**: `Math.random()` в рендере — код менялся при каждом перерисовке, кнопки копировали другой код. Теперь `useMemo`, один код для показа и обеих кнопок копирования.
6. **Шаблон договора**: в генерируемый HTML попадали литералы `{t('…')}` — договор печатался с мусором вместо города, даты и реквизитов. Переписано на интерполяцию переведённых констант.
7. **Точки прогресса онбординга** стали кликабельными кнопками (прыжок на слайд).
8. **Скролл сохранялся между экранами** — на телефоне выглядело как «ничего не произошло». Добавлен `scrollTo(0,0)` при смене роута.
9. **Страница подарков для гостей** показывала нижнее меню пары — убрано (TabBar скрыт на /gifts).
10. **SOS «Позвонить»** на «Дне X» просто закрывал панель — заменён на настоящую `tel:`-ссылку.

**Правило на будущее (фронт и бэкенд):** никаких кликабельных элементов без обработчика; любое «назад» обязано иметь fallback-роут; любые генераторы документов обязаны интерполировать строки, а не вставлять код; тест клик-шторма (src/lib/clickstorm.test.tsx) — обязательный гейт перед релизом: 48 роутов × все кнопки, 120 тестов зелёные.

## 17. Устойчивость данных на фронте: что где хранится

Пока бэкенда нет, состояние живёт в localStorage. Это временно, но правила ниже переносятся на API один в один.

### 17.1. Правило хранения ключей i18n

Всё, что пишется в хранилище, хранится **русским ключом словаря**, а переводится в момент рендера через `t()`. Иначе пользователь, переключивший язык на EN, навсегда получает английскую строку в базе — и обратный перевод уже невозможен.

Пример: состояние сделки сохраняется как `Забронировано`, а не `Booked`. **На бэкенде — то же самое:** статусы, роли и типы передаются кодами (`booked`, `hold`), локализация — на клиенте.

### 17.3. Правило сериализации

`undefined` исчезает при `JSON.stringify`. Поэтому «снятое» значение хранится как `null`, а не как отсутствующее поле: иначе после перезагрузки данные восстанавливаются из дефолтов и отменённая бронь «воскресает». Правило действует и для PATCH-запросов к бэкенду: очистка поля — явный `null`, а не пропуск ключа.

### 17.4. Правило чистоты рендера

`Date.now()`, `Math.random()` и создание компонентов внутри тела компонента запрещены (правила react-hooks v7 — часть линта). Текущее время фиксируется через `useState(() => Date.now())`, случайные коды выпускаются в обработчиках событий, вспомогательные компоненты объявляются на уровне модуля. Иначе React пересоздаёт поддерево на каждый рендер: теряется фокус в полях ввода, а сгенерированный код меняется между показом и копированием.

## 18. Размещение приложения и офлайн

Фронтенд собирается с `base: './'` — все ссылки на ассеты относительные, поэтому сборка одинаково работает и на `tili-tili.ru`, и в подпапке превью вроде `/preview/build-42/`. Из этого следуют требования, которые легко нарушить незаметно.

### 18.1. Ни одного абсолютного пути от корня домена

Манифест, иконки, service worker и его app-shell адресуются относительно себя. Абсолютный `/manifest.webmanifest` в подпапке даёт 404: PWA не устанавливается, офлайн не работает, и увидеть это можно только на реальном хостинге. Закреплено тестом `shell.test.tsx`.

### 18.2. Корень приложения вычисляется на лету

`appRoot()` (`lib/i18n.ts`) определяет базовый путь по адресу entry-скрипта. От него берутся `basename` роутера, регистрация service worker и возврат «на главную» из ErrorBoundary. Хардкодить `'/'` нельзя.

### 18.3. Deep-link на статическом хостинге

Прямой заход на `/wedding/guests` отдаёт `index.html`, но относительные ассеты разрешились бы от `/wedding/`. Поэтому шим в `index.html` уводит на корень приложения и восстанавливает адрес из `sessionStorage`. Корень он вычисляет по первому известному сегменту пути — **список сегментов обязан покрывать все роуты**, иначе ссылка уедет в чужой корень. Список сверяется с роутами тестом.

**На бэкенде это лечится нормально:** SPA-fallback (любой неизвестный путь → `index.html`) снимает необходимость в шиме. Шим остаётся страховкой для превью и статики.

### 18.4. Что кэшируется офлайн

Service worker: навигация — network-first с откатом на оболочку приложения, статика — cache-first с докэшированием. Версия кэша (`CACHE`) меняется при изменении набора оболочки, иначе у пользователей останется старая версия.

Критичное в день X (тайминг, рассадка, контакты, план Б) обязано открываться офлайн — это требование §12 и §13, и после подключения бэкенда данные для него надо класть в кэш явно, а не надеяться на HTTP-кэш.

### 18.5. Бюджет загрузки

Код разнесён по маршрутам: сразу грузится только путь первого запуска (онбординг, квиз, вход, главная), остальные экраны — своим чанком по переходу. Гость, открывший приглашение, не качает кабинет подрядчика и вишлист. Ориентир — главный чанк ≤ 500 КБ без сжатия; при добавлении экранов проверять `npm run verify`, сборка предупредит о превышении.
