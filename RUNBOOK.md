# Runbook — что делать, когда сломалось

Локальный S3/ClamAV: [запуск, перезапуск и сохранённая operation lock](deploy/local-media/README.md).
В development разрешён отдельный unbounded POST mode с SQL infinity и offline
fence. В production этот флаг запрещён; требования §9 остаются обязательными.

> Этап 9 плана. Документ для того, кто дежурит ночью и видит эту страницу
> впервые. Здесь нет объяснений «почему так устроено» — только что нажать.
> Почему — в `BACKEND-PLAN.md` и `JOURNAL.md`. Как выкладывать и в каком
> порядке включать переменные окружения (SMS, Redis, S3, VAPID, Тиль) —
> `DEPLOY.md`; состав контейнеров — `deploy/docker-compose.prod.yml`.

## 0. Где что физически лежит

**Заполняется по факту, из панели Timeweb, а не по памяти.** Это единственный
способ поймать площадку вне РФ: по работающему приложению она неотличима,
а 152-ФЗ требует хранения персональных данных в России.

| Ресурс | Что это | Локация (из панели) | Проверено |
|---|---|---|---|
| VPS приложения | Node 22, Fastify | _заполнить_ | _дата_ |
| PostgreSQL | управляемая БД | _заполнить_ | _дата_ |
| Redis | очередь, ограничитель, живой канал | _заполнить_ | _дата_ |
| S3 | фото, видео, сканы верификации | _заполнить_ | _дата_ |
| Резервные копии | `BACKUP_DIR`, 30 дней | _заполнить_ | _дата_ |
| Отправка SMS | SMSAero | РФ | _дата_ |

Проверять при каждом переезде и раз в квартал. Строка «проверено» без даты
означает «не проверено».

## 1. Приложение не отвечает

**Признак:** `GET /health` не отвечает или отвечает не 200.

1. `GET /health` — жив ли процесс вообще.
2. `GET /health/ready` — что именно упало: в ответе видно `db` и `redis`.
3. Логи процесса: `docker logs <контейнер> --tail 200`.
4. Если процесс мёртв — перезапуск. Он поднимается и при мёртвой базе:
   `/health/ready` честно отвечает 503, и балансировщик не пустит трафик.

**Чего не делать:** не «перезапускать на всякий случай» до того, как
посмотрели `/health/ready`. Он называет причину за две секунды.

---

## 2. База недоступна

**Признак:** `/health/ready` → `"db": "down"`, в ответах 503 `db_unavailable`.

1. Панель Timeweb: жива ли managed-БД, не идёт ли обслуживание.
2. Число соединений: приложение держит пул, а миграции и репетиция
   восстановления берут свои. Лимит управляемой БД конечен.
3. Если БД жива, а приложение её не видит — сеть и `DATABASE_URL`.

**Что при этом работает:** ничего. Приложение честно отвечает 503, а не
показывает пустые экраны — это выбор, а не поломка.

---

## 3. Redis недоступен

**Признак:** `/health/ready` → `"redis": "down"`.

Что перестаёт работать и что нет:

| Работает | Не работает |
|---|---|
| Все обычные пути | Живой канал чата (клиент переходит на опрос раз в 30 с) |
| Чат через историю и отправку | Ограничитель частоты — запросы идут без счёта |
| Уведомления в приложении | Фоновые задачи: push, уборка, дайджесты |

1. Перезапустить Redis, проверить `/health/ready`.
2. После подъёма очередь разбирает накопившееся сама: задачи идемпотентны,
   повтор — пустой.
3. **Отдельно проверить:** пока Redis лежал, ограничителя не было. Если это
   совпало с наплывом — посмотреть логи на предмет одного источника.

## 4. Нужно восстановить данные

Скрипт `scripts/backup.sh` читает весь дамп в закрытом временном каталоге через `pg_restore --exit-on-error --file=-` и отбрасывает сгенерированный SQL. Имя `tili-…Z.dump` появляется после успешного чтения. `BACKUP_DIR` должен поддерживать жёсткие ссылки на той же файловой системе. При сбое записи, проверки или совпадении имён предыдущие копии сохраняются, а ротация не запускается. Применимость SQL и чтение данных через API проверяйте отдельной репетицией восстановления.

После принудительного завершения может остаться скрытый каталог `.tili-…`. Перед ручной уборкой убедитесь, что его процесс завершился. Для восстановления выбирайте опубликованный `tili-…Z.dump` и проверяйте чтение данных на отдельном стенде.

**Цель RTO — 4 часа** (План §19.9). Репетиция проходит за секунды на текущем
объёме, но порядок один и тот же.

```sh
# 1. Найти копию: они лежат в $BACKUP_DIR, имя — время UTC
ls -la "$BACKUP_DIR"

# 2. Развернуть выбранную копию в новую базу на отдельном стенде.
#    DATABASE_URL — источник для свежей копии. ADMIN_URL — служебная
#    база на стенде восстановления и роль с правом CREATE DATABASE.
#    Укажите свободное имя DRILL_DB. При занятом имени скрипт остановится.
#    Перед восстановлением он сверит фактическое имя подключения.
#    Без DUMP он снимет свежую копию для плановой репетиции.
DUMP="$BACKUP_DIR/tili-<время>.dump" DRILL_DB=tili_restore \
  ADMIN_URL=postgres://postgres:…@restore-host:5432/postgres sh scripts/restore-drill.sh

# 3. Убедиться, что данные на месте: скрипт печатает число таблиц,
#    миграций и пользователей. Пустая схема — самый частый вид
#    «успешного» восстановления.

# 4. Проверить живьём ДО переключения: схема может развернуться, а приложение
#    с ней не заработать. Поднять второй экземпляр api с
#    DATABASE_URL=postgres://…/tili_restore на свободном порту и спросить
#    GET /health/ready — ждём "db": "up"; затем войти и открыть свадьбу.
#    (contract.test.ts для этого не годится: он не ходит в базу вовсе.)

# 5. Переключить приложение на восстановленную базу через DATABASE_URL
#    и перезапустить.
```

При ошибке чтения архива PostgreSQL откатывает восстановление целиком. Созданная для репетиции база остаётся пустой. Для повтора с исправной копией выберите новое свободное имя `DRILL_DB`.

**Репетиция — не формальность.** Копия, которую ни разу не разворачивали,
это файл, а не резервная копия. Прогонять `restore-drill.sh` раз в месяц
и записывать дату сюда:

| Дата репетиции | Время | Кто | Результат |
|---|---|---|---|

## 5. Утёк секрет

**Признак:** секрет попал в репозиторий, в скриншот, в переписку.

| Что утекло | Что делать | Что сломается у людей |
|---|---|---|
| `JWT_ACCESS_SECRET` | Заменить и перезапустить | Все выходят из аккаунтов; вход по коду работает |
| `JWT_REFRESH_SECRET` | Заменить **и** пометить `sessions.revoked_at` | То же плюс придётся войти заново; неиспользованные коды входа перестают подходить — ими подписан этот же секрет (`otpSecret()`, отдельного секрета кодов нет) — просят новый код |
| Ключи VAPID | Сгенерировать заново, очистить `push_subscriptions` | Подписки на push переоформляются с телефона |
| Ключ SMSAero | Отозвать в кабинете провайдера | Пока не заменён — вход по коду не работает |
| Доступ к БД | Сменить пароль, проверить `audit_log` за период | Кратковременный 503 |

**Всегда после утечки:** запись в `JOURNAL.md` — что утекло, когда заметили,
что заменили. Без этого следующая утечка расследуется с нуля.

## 6. Наплыв запросов

**Признак:** 429 в логах массово или, наоборот, база под нагрузкой без 429.

1. Ограничитель — 10 запросов в секунду на токен (`RATE_LIMIT_PER_SECOND`),
   считается в Redis. **Без Redis его нет вовсе** — это первое, что надо
   проверить.
2. Ключ ограничителя — токен, а не адрес: за одним адресом сидит целый
   свадебный чат с общим Wi-Fi.
3. Если поток идёт от одного токена — забрать сессию:
   `update sessions set revoked_at = now() where user_id = …`.
4. Если поток распределённый — понижать `RATE_LIMIT_PER_SECOND` временно,
   не трогая код.

## 7. Жалоба на данные (152-ФЗ)

**Человек просит удалить данные или прислать их.**

- Экспорт: `GET /users/me/export` — отдаёт всё одним файлом.
- Удаление: `DELETE /users/me` — мягкое, 30 дней. На 31-й ночная уборка
  сносит всё, кроме `audit_log`; это проверяется тестом, который обходит
  все таблицы базы.
- Просмотр карточки и сделок доступен сотруднику, которому назначено открытое
  обращение по этой свадьбе. В `audit_log` сохраняются номер обращения и причина
  просмотра.

## 8. Чего в этом runbook нет

- **DSN для Sentry** — сбор ошибок подключён, но без `SENTRY_DSN` молчит
  и пишет об этом в лог при старте. Завести проект в Sentry и положить DSN
  в окружение. Уходят только неожиданные ошибки (500 и выше) и падения
  фоновых задач; адреса в отчётах маскируются так же, как в логе.
- **Статус-страница** — внешняя служба, заводится владельцем.
- **Автопереключение на резервную БД** — не настроено; восстановление
  ручное по разделу 4.

### Сводка оператора WP16

Из каталога `Тили-тили/backend` запустите `node scripts/wp16-ops-check.mjs` и подайте в stdin свежий JSON-журнал API по одной записи на строку. Перед запуском задайте адрес `OPS_HEALTH_URL` с путём `/health/ready`, строку подключения `OPS_DATABASE_URL` и каталог `OPS_BACKUP_DIR`. Используйте роль PostgreSQL с правом чтения таблиц `users`, `notifications` и `notification_push_deliveries`. Команда `pg_restore` должна быть доступна в PATH. Сам отчёт не содержит адресов, текстов ошибок, тел запросов, идентификаторов пользователей или имён файлов.

`X-Request-ID` ищется в журнале по `reqId`. Сводка считает долю 5xx и 409 от всех завершённых HTTP-ответов за окно. Конфликты 409 видны отдельно. Сбой задачи, отказ SMS, модели, файлового хранилища или сканера учитываются по фиксированным меткам журнала. Уведомления, запланированные на будущее, уже закрытые или предназначенные только для входящих, исключены из очереди. Возраст считается с назначенного времени доставки старейшего ожидающего уведомления. Отказы 404 и 410 от push-провайдера относятся к завершившимся подпискам и не считаются отказом провайдера.

По умолчанию окно журнала 900 с (`OPS_WINDOW_SECONDS`), сигнал по очереди после 300 с (`OPS_PUSH_AGE_SECONDS`), по копии после 86 400 с (`OPS_BACKUP_AGE_SECONDS`). Окно и порог очереди можно задать на стенде. Возраст копии берётся из UTC-метки имени, которое создаёт `backup.sh`. `pg_restore --list` проверяет оглавление архива. Полноту восстановления подтверждает отдельная репетиция.

Код выхода 0 означает, что все источники доступны и тревог нет. Код 1 означает, что есть тревога. Код 2 означает, что наблюдение неполное, например в окне нет ни одного завершённого запроса, или файл метрик не обновился.

### Доставка тревог WP16

Для подключения Prometheus задайте `OPS_METRICS_FILE` с абсолютным путём к файлу `wp16.prom`. Сводка обновляет файл атомарной заменой. Запускайте одну копию сводки раз в минуту с конечным снимком журнала в stdin. Отдавайте только этот файл как `text/plain` по приватному адресу мониторинга. Подключите [правила WP16](deploy/monitoring/wp16.rules.yml) через `rule_files` и добавьте один источник на стенд с `job_name: tili_wp16`, `metrics_path: /wp16.prom` и интервалом сбора не более 30 секунд. Для метки `instance` укажите постоянное название стенда.

Prometheus отправляет срабатывания в [Alertmanager](https://prometheus.io/docs/alerting/latest/overview/). Для канала оператора задайте получателя, включите уведомления о восстановлении и группировку по `alertname` и `signal`. В метриках только фиксированные коды и время обновления. При недоступности источника отдельная тревога сообщает о неполном наблюдении, а последнее подтверждённое состояние хранится в запросе за пять минут. Новая успешная проверка источника снимает тревогу сразу после очередного сбора и вычисления правил.

Отдельная тревога срабатывает для каждого настроенного стенда, если метрика времени исчезла, её возраст превышает 180 секунд или её время опережает Prometheus более чем на 60 секунд. Если источники WP16 отсутствуют целиком, срабатывает общая тревога. При нескольких стендах включите `instance` в группировку Alertmanager. Проверка правил из корня репозитория — `promtool test rules deploy/monitoring/wp16.rules.test.yml`. На стенде выпуска подтвердите получение тревоги и сообщения о восстановлении оператором.

## 9. Управляемые фотографии032-B: включение и восстановление

По умолчанию MEDIA_* пусты: новые загрузки отключены. Частичная настройка отклоняется при старте. Для включения нужен отдельный проверенный приватный bucket и сканер, а также согласованная схема99. Локальные synthetic POST/ClamD/Sharp проверки не подтверждают свойства облачного провайдера. До фактической операторской приёмки не заполнять production-переменные.

Операторская приёмка сохраняет доказательства: отсутствие anonymous GET/list и публичного ACL; точные POST key/MIME/размер/expiry и запрет произвольного key/ACL; CORS только для нужных origins; доступность настоящего ClamAV с актуальной базой; согласованные часы; lifecycle quarantine, совместимый с активными grants и clean объектами; восстановление БД вместе с объектами/namespace и private delivery. MEDIA_S3_POST_MAX_SECONDS должен отражать проверенный абсолютный предел1..60с для последнего возможного commit принятого POST, включая медленное тело/очередь, с отдельным учётом clock skew. Наличие env не заменяет такую проверку; прибавка120с в коде — дополнительный запас.

media_uploads хранит намерения и видимые состояния. media_objects — обязательства очистки, намеренно переживающие удаление user/vendor. Storage identity закреплена за endpoint/region/bucket; смена ключей доступа не меняет identity, смена bucket требует согласованного переноса metadata и объектов. Старый namespace автоматически не очищается новым клиентом. Export не содержит signing secrets, presigned fields и внутренних object keys.

### Проверка внешних файлов после восстановления WP16

Согласуйте снимки базы и хранилища по одной точке восстановления. Перед их снятием остановите новые загрузки и фоновые записи в хранилище. Дождитесь завершения ранее выданных загрузок и незаконченных записей по процедуре ниже. Сохраните метаданные и обязательства очистки в дампе PostgreSQL, а объекты и их ключи — в резервной копии хранилища. Запишите время обеих копий.

Разверните дамп по разделу 4 и объекты в отдельной среде. Сохраните логический endpoint, регион и имя bucket в конфигурации изолированного стенда. Проверьте, что этот адрес на стенде ведёт в восстановленное хранилище. Ключи доступа для стенда выдайте отдельно. До завершения сверки держите фоновые записи и новые загрузки выключенными.

Из каталога `Тили-тили/backend` запустите `node --import tsx scripts/wp16-verify-media-restore.ts`. Задайте `RESTORE_DATABASE_URL` для роли с правом чтения `media_uploads` в восстановленной базе и заполните конфигурацию `MEDIA_*` восстановленной среды. Для S3 используйте ключ с правом чтения объектов `clean/`. Команда читает записи в состоянии `ready` и сверяет принадлежность хранилищу, размер и SHA‑256. В результате только числа. Код 0 означает, что все найденные файлы совпали. Код 1 означает несовпадение хранилища, недоступный объект или несовпадение содержимого. Код 2 означает отсутствие готовых файлов для сверки или невозможность выполнить проверку.

Проверьте открытие восстановленного файла через обычный API с разрешённым аккаунтом. Повторите с посторонним аккаунтом и без подписи напрямую в S3. Запишите время от начала восстановления до этих проверок и возраст использованной пары копий.

При storage/scanner отказе сначала восстановить доступность, проверить media_objects по нужному storage_id и фазе записи. inflight/uncertain означает, что удалённая запись могла завершиться позже; успешный DELETE сам по себе её не закрывает. После8 попыток запись остаётся failed. Не удалять строки и не выставлять done вручную ради освобождения квоты. Оператор должен установить отсутствие старого writer и дальнейшего commit, сверить все кандидатные keys и durable версии и выполнить проверенный recovery-план в отдельном тестовом namespace. Конкретный production recovery/ручные изменения требуют решения владельца.

Удаление фотографии сразу скрывает её в портфолио; физическая очистка асинхронная. Завершение всех обязательств до истечения grant/lease/external_until не обещается. Down99 с любой строкой media_uploads или media_objects (включая done) намеренно отказывает до DDL с SQLSTATE23514/media_preserving_down_032. Это безопасный отказ, а не успешный downgrade управляемых данных. Legacy-only down/up подтверждается отдельным preserving drill; откат приложения при существующих managed данных должен сохранять schema99 и metadata до проверенного восстановления.
